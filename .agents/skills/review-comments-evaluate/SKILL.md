# レビューコメント検討

PR でレビュー依頼した Copilot、Codex、kokufu によるレビューを全て読み込み、各指摘について修正すべきか・修正不要かをフラットに検討し、**識別子 `RC-n` 付きの検討結果をユーザーに伝える**。1コメントに複数指摘があるときは指摘ごとに評価する。さらに**同じ内容をリポジトリ内ドキュメントに追記**し、読み込み・検討・伝達・記録まで本スキルで完結させる。

**記録ファイルのパス**は [review-doc-path.md](references/review-doc-path.md) を正本とする（新規: `review-<ブランチslug>.md`、既存 `pr-*.md` はレガシー）。

## 呼び出しコンテキスト

| モード | 入口 | 手順の順序 | 完走条件 |
| ------ | ---- | ---------- | -------- |
| **manual** | ユーザーが `/review-comments-evaluate` | 1 → 2 → 3 → **4a** → 4 → 5 | `review-<slug>.md` 追記 + 自動修正（該当時）+ consume（該当時） |
| **auto** | wait sentinel / pending wake（`consumed: false`） | 1 → 2 → **4a** → **4** → 5 → **3（短縮）** | **`review-<slug>.md` 追記 + 手順 4a まで必須**。チャット要約のみで終了しない |

**auto 入力**（wait から受け取る）:

- `PR_NUM`（必須）
- `REVIEW_REQUEST_SINCE`（wake JSON の `since`。必須）
- `partial`（任意。Codex limits/connect のみ等。評価セッションのメタデータに記載してよい）

**auto 専用ルール**:

1. **対象コメント**: `created_at >= REVIEW_REQUEST_SINCE` のコメントのみ RC 化する（それ以前は読まない・重複 RC 防止）
2. **重複除外**: [指摘の分割と重複](#指摘の分割と重複) に従う。同一 GitHub id でも、未記録の指摘塊は採番する。差分のない再掲だけ採番せず、レビュー非該当には入れない
3. **RC 0 件でも追記**: 新規 RC が無くても「評価セッション」ブロックを末尾に追記する（メタデータに `新規 RC なし`、partial 情報を含めてよい）
4. **手順 3**: auto では手順 4a・4・5 の**後**。チャットは RC 一覧（サマリ）表 + 自動修正サマリ（該当時）+ 「`documents/レビューコメント/review-<slug>.md` に追記済み」。13 項目詳細は省略可
5. **禁止**: auto で手順 4 未完了のままターン終了 / wake consume。🚨 + 📌 または条件付き 🟡 + 📌 があるのに手順 4a をスキップして終了しない（ユーザーが「修正しない」「自動修正しない」と明示した場合を除く）

## 他スキルとの役割分担

| スキル | 役割 | レビュー記録ファイル |
|--------|------|----------------------|
| **本スキル**（review-comments-evaluate） | **外部**レビュー（Copilot / Codex / kokufu）コメントの妥当性評価 + **自動修正**（手順 4a） | 追記（手順 4） |
| [/shokujii-code-review](../shokujii-code-review/SKILL.md) | **能動的**な差分レビュー（規約チェックリスト）+ **自動修正**（手順 3a・3b） | 指摘があれば追記（手順 4） |

- 同一ブランチ（= 同一 `review-<slug>.md`）では **RC 番号を通し**で共有する（evaluate の続き番号ルールに従う）。
- 推奨フロー（目安）: shokujii-code-review → 外部 AI レビュー依頼 → 本スキルで evaluate（評価 + 自動修正）→ review-comments-reply。
- **自動修正**の対象・対象外・最大周回は [auto-fix-policy.md](references/auto-fix-policy.md) および [shokujii-code-review 手順 3a・3b](../shokujii-code-review/SKILL.md#手順-3a-必須修正の自動修正agentsmd-から起動された場合) と同一。
- 既存 `pr-*.md` に `🚨 修正推奨` / `❌ 未対応` / 旧 **判断** 列の `✅ 対応済み` 等が残っていてもよい。**新規セッション**からは [評価 + ステータス（共通区分）](#評価--ステータス共通区分プロジェクト共通) のみ使う。

## 手順

0. **pending wake 確認**（**manual 時のみ**・任意）
   - **manual**: `.agents/state/pr-review-pending-wake.json` に `consumed: false` があれば、先に [`wait-ai-pr-review`](../wait-ai-pr-review/SKILL.md) 手順 6 に従い evaluate 未処理をユーザーへ報告する（本スキル本編と競合しない範囲で）
   - **auto**: 手順 0 をスキップし本編を即実行する（報告だけで止めない）

1. PR のレビューコメントを全て取得する

   **auto モードでの取得範囲**

   - `REVIEW_REQUEST_SINCE` 以降（`created_at >= REVIEW_REQUEST_SINCE`）に作成されたコメントのみ RC 対象とする
   - 既存レビュー記録ファイル（`review-<slug>.md` またはレガシー `pr-<n>.md`）に、同じ GitHub id の同じ指摘塊が記録済みなら、その塊は再採番しない。同じ id に未記録の指摘塊があれば採番する
   - PR 番号は auto 入力の `PR_NUM` を使う（現在ブランチの PR 推定に頼らない）

   **取得対象**
   - トップレベルコメント（PR の issue コメント。`GET /issues/{number}/comments`）
   - インラインコメント（コード上のレビューコメント。`GET /pulls/{number}/comments`）
   - レビュー本文（`GET /pulls/{number}/reviews` の `body`。Copilot の review overview はここにある）
   - Copilot・Codex・kokufu・その他のレビュワーを区別せず全て対象とする
     - Copilot: AI レビュワー
     - Codex: AI レビュワー
     - kokufu: エンジニアのレビュワー

   **除外対象**
   - Outdated（修正済み・対応済み）のインラインコメントは読み込まない。該当コードが push 等で変更されたため、GitHub 上で「Outdated」と表示されるコメントは検討対象から除外する。API レスポンスで `position` が `null` のコメントは Outdated とみなす。
   - Outdated のコメントは評価を行わない。依頼者に対してログへの出力やコメントを行わない。Outdated の件数のみを出力する。

   **レビュー非該当（スキップ）**

   コードレビューに言及していないコメントは、Outdated と同様 **評価・RC 採番・レビュー記録ファイルへの RC 記録ブロック記載を行わない**。件数のみ報告する（チャットでは 1 行サマリ可）。

   **現時点の除外リスト（狭く始める）** — 次のいずれかに該当すればスキップする:

   1. **Codex 問題なしのみ** — 具体指摘がなく、問題なし・称賛のみのサマリ（例: `Didn't find any major issues`）。接続案内の `<details>` ボイラープレートが付いていても同様。`wait-ai-pr-review` では `no_issues` としてレビュー完了扱いだが、本スキルでは RC 採番しない。
   2. **レビュー依頼の定型文** — `@copilot @codex review` で始まる依頼コメント（旧手順 12）、または `@codex この PR の Files changed をコードレビュー` / `@copilot この PR の Files changed をコードレビュー` で始まる依頼コメント（手順 12 の 2 行固定文を含む）
   3. **Copilot 承知返信** — コード変更・設計・仕様への言及がなく、レビューの書き方確認・次回厳守・承知のみのトップレベル返信
   4. **接続案内ボイラープレートのみ** — Codex / Copilot コネクタのセットアップ案内や `About Codex in GitHub` の `<details>` のみで、コード変更・設計・仕様への言及がないもの。レビュー本文がこの定型だけ（Codex の "Here are some automated review suggestions" と接続案内のみ等）のときも含む

   **レビュー非該当に入れない**（件数にも混ぜない）:

   - 差分のない再掲。採番しないだけで、セッションの **重複除外** に残す（[指摘の分割と重複](#指摘の分割と重複)）
   - `>` 引用のあとに指摘本文がある Copilot の会話返信。引用はエコーであり、その後ろが本体
   - `## Copilot review overview`（目次だけでも RC 対象）

   **様子見（現時点ではスキップしない）**:

   - Copilot の `Pull request overview`（目次だけでも 1 RC。分割しない。リンク先の照合は [指摘の分割と重複](#指摘の分割と重複)）
   - 対応完了の返信のみのコメント
   - 上記以外で判定に迷うコメント → ユーザーに確認するか、保守的に RC 対象に含める

   **RC 番号**はスキップしたコメントを除いた残りにのみ付与する。並び順の計算もスキップ分を除いてから行う。

   **取得方法**

   - **PR URL が渡された場合**: 渡された URL を `gh pr view` の引数に渡し、その PR のコメントを取得する
   - **URL が渡されていない場合**: 現在のブランチに対応する PR を対象にする
   - 一覧 API は必ず `--paginate` を付ける（1ページ 30 件で打ち切らない）
   - 本文の正本は API の `body`。`gh pr view --comments` は id が取れず、先頭の `>` 引用だけを見て後ろの指摘を落としてはならない

   PR 番号が決まったら、次の 3 つを取る。`<PR番号>` は URL 指定時 `gh pr view <URL> --json number -q '.number'`、未指定時 `gh pr view --json number -q '.number'`。

   ```
   # インライン。Outdated は position == null を除く
   gh api --paginate "repos/{owner}/{repo}/pulls/<PR番号>/comments" | jq 'map(select(.position != null))'

   # 会話コメント（id と body）
   gh api --paginate "repos/{owner}/{repo}/issues/<PR番号>/comments"

   # レビュー本文（id と body。Copilot overview はここ）
   gh api --paginate "repos/{owner}/{repo}/pulls/<PR番号>/reviews"
   ```

   ※ `position` が `null` のインラインは、該当行が修正済みで GitHub 上で「Outdated」と表示される。これらは検討対象から除外する。
   ※ レビュー本文が空、または接続案内だけのもの（上記の除外リスト 4）はレビュー非該当。`## Copilot review overview` は対象に残す。
   ※ 現在のブランチに PR が紐づいていない場合は、PR 番号または URL の入力を促す
   ※ ユーザーが貼り付けたテキストを読み込む方法も可（この場合、手順 4 の記録用に **PR 番号をユーザーに確認**する。確認できないときだけ `manual-<YYYYMMDD-HHmm>.md` で記録してよい）

   **インラインコメントのメタデータ（RC 記録ブロック用）**

   `gh api "repos/{owner}/{repo}/pulls/{number}/comments"` の各要素から、RC 記録に使う:

   | フィールド | 用途 |
   |------------|------|
   | `id` | GitHub id（識別子行に併記） |
   | `user.login` | **レビュワー** |
   | `path` | **指摘箇所**のファイルパス |
   | `line` または `original_line` | **指摘箇所**の行（`line` 優先、無ければ `original_line`） |
   | `body` | **レビュワーのコメント（原文）** — 一字一句そのまま |
   | `diff_hunk` | **該当コード（レビュー時点の diff）** — 改変禁止 |

   ※ `diff_hunk` が空・未取得のインラインは、記録前に API 再取得または [該当コードの取得（共通）](#該当コードの取得共通) で補完する。補完できない場合のみ **該当コード** に `(diff_hunk 未取得)` と1行明記し、**指摘箇所**は必ず書く。

   **`diff_hunk` の補完（REST に無いコメント）**

   新規インラインが REST `GET .../pulls/{number}/comments` に出てこない場合がある（レビュー直後など）。**GraphQL** の `reviewThreads` → `comments.nodes.diffHunk` で取得する。

   ```
   gh api graphql -f query='
   query($owner: String!, $name: String!, $number: Int!) {
     repository(owner: $owner, name: $name) {
       pullRequest(number: $number) {
         reviewThreads(first: 100) {
           pageInfo { hasNextPage endCursor }
           nodes {
             comments(first: 20) {
               nodes { databaseId path line body diffHunk }
             }
           }
         }
       }
     }
   }' -f owner=nijuniinc -f name=bokudeli-event-new -F number=<PR番号>
   ```

   ※ `databaseId` を GitHub id として識別子行に併記する。
   ※ `pageInfo.hasNextPage` が true の間、`reviewThreads(first: 100, after: "<endCursor>")` に変えて同じクエリを繰り返す。`first: 100` で打ち切らない。目次の `#discussion_r<id>` がこの結果に無いときは `GET /repos/{owner}/{repo}/pulls/comments/{id}` でその1件を取る。

   **検討対象の並びと識別子（RC-n）**

   - 検討結果に載せる各指摘には、後続の作業依頼で参照できるよう **`RC-1`, `RC-2`, …** 形式の識別子を付与する（**R**eview **C**omment の略）。1コメントに複数指摘があるときは [指摘の分割と重複](#指摘の分割と重複) のとおり指摘ごとに振る。
   - **並び順**（同一 PR 内で一貫させる）:
     1. 会話コメント（issue コメント）を **`created_at` 昇順**。同一コメント内の分割指摘は本文の出現順
     2. レビュー本文を **`submitted_at` 昇順**
     3. インラインコメント（`position != null` のみ）を **`path` 文字列昇順**、同一 `path` 内は **`position` 昇順**（`position` が無い場合は `line` 等で安定順）
   - API で取得する場合は、**レビュー非該当と、差分なしの再掲を除いたうえで**上記のキーでソートし、`RC-1` から通し番号を振る。貼り付けテキストのみのときも、スキップ対象を除いた順を `RC-1` から付与してよい。
   - **同一ブランチの追加評価セッション（既存 `review-<slug>.md` がある場合）では、番号をリセットせず前セッションの最終 RC 番号の次から連番で付与する**（例: 前回が `RC-15` で終わっていれば、新セッションの新規コメントは `RC-16`, `RC-17`, … と続ける）。これにより RC 識別子はブランチ（ファイル）ごとにグローバルに一意となり、既存ドキュメントの参照（後続タスクの「`RC-3` に対応して」等）と矛盾しない。
   - GitHub API の `id` が取得できている場合は、識別子行に **`RC-1（GitHub id: 123456789）`** のように併記する。分割した指摘は同じ id を複数 RC に付けてよい。

### 指摘の分割と重複

会話コメントやレビュー本文の先頭にある `>` 引用は、依頼コメントのエコーである。引用の途中で `...` になっていても、そこまでがエコーで、その後ろが本体である。評価・原文・要約は引用を除いた本文で行う。引用だけを見て指摘なしと判断しない。引用を除いて本文が空のときだけ、そのコメントをスキップする。

引用を除いた本文に独立した指摘が複数あるときは **指摘ごとに 1 RC** とする。1コメントを 1 RC にまとめ、全体を 👌 修正不要にしない。

分割する単位:

- `🚨` または `🟡` で始まるブロック（次の同種ブロック、または本文末まで）
- ファイルパスと修正要求が別々で、空行で区切られた不具合

分割しないもの:

- 目次だけの Copilot review overview（`## Copilot review overview` で、本文がタイトルと `#discussion_r<id>` のリンクだけ）。これは 1 RC

分割した各 RC の **レビュワーのコメント（原文）** には、その指摘の原文だけを削らず載せる。`>` 引用は載せない。

**採番しない（差分なし）** — 次をすべて満たすときだけ、新しい RC を付けない。

1. その GitHub id の、その指摘塊が既存 RC に記録済みである。同じ id でも未記録の塊は採番する
2. 同一指摘である。不具合・対象・求める修正が、既存 RC の **レビュワーのコメント（原文）** に既に書かれている。言い換えや、同じ処理の行番号が具体化しただけは差分なし。次のいずれかがあるときは同一指摘ではない
   - 新しいファイル、または既存原文に無い処理経路
   - 修正方針が変わる（例: 「UI か API か未定」が「両方の確定処理をトランザクション内で検証」に具体化した）
   - 既存 RC の評価が 🟡 で、新しい文言が 🚨 である

採番しないとき:

- レビュー非該当スキップに入れない。スキップ件数にも混ぜない
- 評価セッションの **重複除外** に `GitHub id → 既存 RC-n、差分なし` と書く
- 既存 RC の **評価** は変えない

差分があるとき:

- 既存 RC の **評価** は変えない（評価は不変）
- 増えた点だけを新しい RC にする。**判断理由**に「RC-n の続き。増えた点は …」と書く
- コメント全体を 👌 修正不要にしない

目次 RC を 👌 にする前に、本文中の `#discussion_r<id>` がインライン取得結果にあることを確認する。無い id は `GET /repos/{owner}/{repo}/pulls/comments/{id}` で取り直す。取れた指摘は通常どおり評価する。リンク先がすべて RC または重複除外になっていて、目次自体に修正要求が無いときだけ、目次 RC を 👌 修正不要にしてよい。

2. **RC 対象**の各指摘（分割後）について以下を検討する（レビュー非該当は手順 1 の除外リストに従いスキップ。差分なしの再掲は採番せず **重複除外** に残す）
   - 指摘内容の妥当性（プロジェクトの規約・shokujii-code-review に照らして）
   - 修正すべきか、修正不要か
   - 修正不要の場合、その理由（誤解・プロジェクト固有の判断・過剰指摘等）
   - **PRスコープ**（[PRスコープ](#prスコープ) の固定語彙から 1 つ）
   - **ラベル**（[ラベル](#ラベル) の固定語彙から **0 個以上**。該当なしは `—`）
   - **変更種別**（[変更種別](#変更種別) の固定語彙から 1 つ）
   - **想定工数**（[想定工数](#想定工数) の S / M / L。修正不要・確認のみは `—`）

3. 検討結果をユーザーに伝える

   - **manual**: 手順 4 の**前**（現行どおり）
   - **auto**: 手順 4・5 の**後**（短縮サマリのみ。13 項目詳細は省略可）

   - **RC 一覧（サマリ）** 表を出力する（[表形式](#rc-一覧サマリ表形式)。**要約列を含む1表**）
   - 続けて **RC 対象**の各指摘について、**RC 記録ブロック（必須13項目）** に従って詳細を出力する
   - **レビュー非該当**は RC 記録ブロックを書かない。先頭で `Outdated 除外件数` と **`レビュー非該当スキップ件数`** を報告し、必要ならスキップ理由を 1 行ずつ列挙する（GitHub id・種別のみでよい）
   - **重複除外**（差分なしで採番しなかった指摘）も先頭で `GitHub id → 既存 RC-n` を列挙する。レビュー非該当の件数には混ぜない
   - **チャット**: サマリ表のあと 13 項目すべて載せる。`diff_hunk` が長い場合のみ末尾 40〜80 行に省略してよい（省略時は「末尾抜粋」と明記し、ドキュメントには全文または末尾優先ルールで記載）

### 手順 4a: 自動修正（🚨 必須修正 / 条件付き 🟡）

手順 2 の評価結果のうち、[auto-fix-policy.md](references/auto-fix-policy.md) の **🚨** または **条件付き 🟡** に該当し、**ステータス** が未着手の RC が 1 件以上ある場合、手順 4 の記録の**前**に次を実行する（**ユーザー確認不要**）。ユーザーが「修正しない」「自動修正しない」と明示した場合のみスキップ。

**4a-1: 🚨 必須修正**（すべて満たす RC）:

| 条件 | 値 |
|------|-----|
| **評価** | 🚨 必須修正 |
| **PRスコープ** | 📌 スコープ内 |
| **ステータス** | 未着手 |

**4a-2: 🟡 修正提案（条件付き）** — [auto-fix-policy.md](references/auto-fix-policy.md) の 🟡 表を参照（S + 🔧/📄 + 📌 + 除外ラベルなし 等）。

**自動修正しない**: 👌 修正不要、**PRスコープ** が 📤 スコープ外 / ❓ 要確認 の RC、条件を満たさない 🟡、評価時点で既に **ステータス** が ✅ 対応済み の RC。

1. **自動修正対象外**（一覧を報告し、人間判断を待つ）— [auto-fix-policy.md](references/auto-fix-policy.md) の共通対象外と同一
2. **4a-1（🚨）を先に**修正し、続けて **4a-2（条件付き 🟡）**を修正する
3. ソースコードを変更した場合は [`/lint-and-format`](../lint-and-format/SKILL.md) を実行する
4. 修正した RC の **ステータス** を **✅ 対応済み**、**対応**列を **`[x]`** に更新する（手順 4 記録時に反映。**評価**は変更しない）
5. 未対応の自動修正対象 RC が残る場合、手順 4a を**最大 2 周**繰り返す（同一 evaluate セッション内・🚨 と 🟡 合算）
6. 2 周後も自動修正できない RC（対象外含む）が残る場合は一覧を完了報告に含める
7. **標準フロー**: 修正で HEAD が変わったら、同じ予約のまま [`github-actions-deploy`](../github-actions-deploy/SKILL.md) を再実行する。fixture は戻さない。必須修正が残るときは完了にしない

条件を満たさない 🟡 は未着手のまま手順 4 に進み、完了報告に列挙する。

4. 評価内容をドキュメントに追記する（**1 ブランチ = 1 ファイル**）

   - **auto**: 手順 **4a の後**・手順 3 の**前**に実行（**必須**）。成功するまでターンを終了しない
   - **RC 0 件**（auto / manual 共通）: 評価セッションブロックを追記し、メタデータに `新規 RC なし` を明記する

   **保存先**

   - ディレクトリ: `documents/レビューコメント/`（存在しなければ作成する）
   - パス解決: [review-doc-path.md](references/review-doc-path.md) に従う

   **ファイル名（新規作業）**

   - **`documents/レビューコメント/review-<slug>.md`**（例: ブランチ `fix/2500` → `review-fix-2500.md`）
   - **manual** で **PR URL または PR 番号**が分かる場合: `gh pr view <URL_or_NUM> --json headRefName` でブランチ名を取得して slug 化（**checkout 中のブランチより優先**。別 PR を evaluate しても記録が分裂しない）
   - **manual** で PR が不明なときのみ: `git branch --show-current` で slug 化
   - **auto** で `PR_NUM` のみの場合: `gh pr view <PR_NUM> --json headRefName` でブランチ名を取得して slug 化
   - 記録対象外ブランチ（`release/` `sync/` 等）は [review-doc-path.md](references/review-doc-path.md) に従いスキップ
   - 新規に本文を組み立てるときは **[review-xxxx_template.md](../../../documents/レビューコメント/review-xxxx_template.md)** の見出し・ブロック順に合わせてよい

   **レガシー**

   - 既存 **`pr-<PR番号>.md`** への追記依頼・当該ファイル上の RC 更新は、そのファイルを正本として継続（マイグレーションしない）

   **記載方針**（レビュー記録ファイル冒頭または評価セッションに書いてよい）

   - **レビュワーのコメント（原文）**
     - **GitHub コメント**: 分割しないときは `body` を**一字一句そのまま**（要約禁止）。分割した指摘はその塊の原文だけを、文言を削らず載せる。`>` 引用は載せない。Markdown のまま掲載してよい（``` フェンスは任意。Badge 等を壊さないため）
     - **エージェント指摘**（[/shokujii-code-review](../shokujii-code-review/SKILL.md)）: チャットで出した 🚨 / 🟡 / 👌 付き指摘文をそのまま。識別子行は `（GitHub id: なし・エージェントレビュー）` 等と明記
   - **該当コード**: [該当コードの取得（共通）](#該当コードの取得共通) に従う

   **同一ファイルの扱い**

   - 対象パスに**既にファイルがある場合は上書きしない**。ファイル**末尾**に水平線（`---`）を入れてから、**新しい「評価セッション」ブロックを追記**する。これにより **1 ブランチあたり 1 ファイル**で複数回の評価履歴を残す。
   - ファイル**最上部**（`# ブランチ … レビュー記録` の直後）に **通し `### RC 一覧（サマリ）`** 表を置く（[review-xxxx_template.md](../../../documents/レビューコメント/review-xxxx_template.md) 参照）。RC を記録するたびに、この冒頭表の末尾へ新セッション分の RC **行**を追記する（前セッションの行は書き換えない）。冒頭の通し表は「ブランチ全体の RC 一覧」として **全 RC** が RC 昇順で並ぶ状態を維持する。`[x]` / `[ ]` のチェック状態は**本文末尾のセッション内サマリ表と一致**させる。
   - 既存ファイルに冒頭の通しサマリ表が無い場合は、次回 RC 記録時に**冒頭へ通し表を新設**し、過去セッション分の RC 行も可能な限り移す（移行できないレガシーは次回以降の追記分から適用）。
   - 旧形式の **`### RC 別対応チェックリスト`**（箇条書き）のみのファイルがある場合は、次回追記から表形式に移行する。旧行は書き換えない。

   **追記するブロックの構成（この順・この粒度を守る）**

   1. `## 評価セッション（<日時 JST>・review-comments-evaluate）`（見出し。日時は **JST ローカル**、`YYYY-MM-DD HH:mm` 形式。[`/shokujii-code-review` 手順 4](../shokujii-code-review/SKILL.md) と同形式で、サフィックスのみ `review-comments-evaluate`）
   2. メタデータ（箇条書き）: **評価日時**（例: 2026-04-23 15:04 JST）、**ブランチ名**（`git rev-parse --abbrev-ref HEAD` 等で取得できる場合）、**PR**（URL または `#番号`）、**Outdated 除外件数**、**レビュー非該当スキップ件数**、**重複除外**（無いときは `なし`。形式は `GitHub id → 既存 RC-n、差分なし`）
   3. **`### RC 一覧（サマリ）`** — [表形式](#rc-一覧サマリ表形式) で **この評価セッションで RC を付けた指摘** を **RC 昇順** で並べる（初回セッションは `RC-1` から、追加セッションは前セッションの続き番号から）。レビュー非該当と差分なしの再掲は表に載せない。
      - **対応**列の `[ ]` / `[x]` は **実装・運用対応が完了したか**（手元のコード・PR の状態に合わせて更新する）。
      - **評価** が **👌 修正不要**、または **ステータス** が **✅ 対応済み** / **📤 #NNNN 別Issue化** のときは **`[x]`** で開始してよい（評価時点で既に直っている場合は **評価** を 🚨 / 🟡 のまま **ステータス** を **✅ 対応済み** にする）。
      - **評価** が **🚨 必須修正** / **🟡 修正提案** で **ステータス** が **未着手** のときは **`[ ]`**。対応完了後は **評価** は**変更せず**、**ステータス** を **✅ 対応済み** に更新し **対応**列を **`[x]`** にする。本 PR では実装せず別 Issue へ切り出す場合は [`git-create-issue`](../git-create-issue/SKILL.md) で Issue を作成し、**ステータス** を **📤 #NNNN 別Issue化**、**PRスコープ** を **📤 スコープ外**、**対応**列を **`[x]`** にする（**❌ 未対応は使わない**。「別 Issue で方針検討」等の文言だけで Issue 未作成の状態は禁止）。
      - チャットへの伝達でも、このサマリ表をそのまま載せてよい（ドキュメントと一致させる）。
   4. 各 `RC-n` ごとに **RC 記録ブロック（必須13項目）** を、この順・この見出し名で繰り返す（末尾に `---`）。
   5. **追加セッションのとき**は、上記 1〜4 の追記が完了した後に、**ファイル冒頭の通し `### RC 一覧（サマリ）`** 表にも本セッションで扱った RC **行**を追記する（**同一ファイルの扱い**の項を参照）。冒頭の通し表と本文末尾セッション内サマリ表で、新規追加分の `[x]` / `[ ]` 状態が一致していることを確認する。

   チャット向け出力とドキュメント追記の内容は**対応する RC ごとに一致**させる（評価・ステータス・PRスコープ・ラベル・変更種別・想定工数・要約・理由・指摘箇所・該当コード・原文が食い違わないようにする）。

5. **pending wake を consumed にする**（wait-ai-pr-review 経由で evaluate 待ちだった場合）

   **手順 4（レビュー記録ファイル追記）が成功した後のみ**実行する。手順 4 未完了での consume は禁止（auto モードで特に厳守）。

   手順 4 まで正常完了したら、対象 PR 番号について pending wake を消費する:

   ```bash
   python3 .agents/scripts/wait_ai_pr_review_wake.py consume \
     --wake-file .agents/state/pr-review-pending-wake.json \
     --pr <PR番号>
   ```

   - 該当 wake が無い場合はスキップしてよい（手動 evaluate 等）
   - consume 失敗時はユーザーへ報告する

## 該当コードの取得（共通）

[/shokujii-code-review](../shokujii-code-review/SKILL.md) と同一。`diff` フェンス内に貼り、**改変禁止**。

| 出典 | 取得方法 |
|------|----------|
| GitHub インライン | API の **`diff_hunk`**（REST または上記 GraphQL） |
| エージェント指摘 | `git diff origin/development...HEAD -- <path>` の該当 hunk。ベースは PR のマージ先（通常 `origin/development`） |
| 補完不可 | `(diff_hunk 未取得)` と1行明記（**指摘箇所**は必須） |

**長い diff**: 先頭1行に `…（diff 先頭省略・N 行）` を入れ、**末尾を優先して最大約 80 行**まで掲載可。

**トップレベルコメント**（インライン行なし）: `（インライン指摘なし）` と1行明記。

## 評価 + ステータス（共通区分・プロジェクト共通）

[/shokujii-code-review](../shokujii-code-review/SKILL.md) と同一。**❌ 未対応は使わない**。重要度（**評価**）と対応進捗（**ステータス**）は**別列**で記録する。**評価**は評価セッション記入時に確定し、以降**変更しない**（対応完了後も 🚨 / 🟡 が残る）。

### 評価（重要度・不変）

| 評価 | 意味 |
|------|------|
| 🚨 **必須修正** | マージ前に対応が必要（セキュリティ・バグ・データ不整合等） |
| 🟡 **修正提案** | 改善推奨（マージ必須ではない） |
| 👌 **修正不要** | 指摘はあるが対応不要（誤解・仕様どおり・過剰指摘等） |

### ステータス（対応進捗・可変）

| ステータス | 意味 | 対応列 |
|------------|------|--------|
| **未着手** | コード修正・確認が残る | `[ ]` |
| ✅ **対応済み** | コード・PR で解消済み | `[x]` |
| 📤 **#NNNN 別Issue化** | 本 PR では実装せず、別 Issue に切り出し済み | `[x]`。**PRスコープ** は **📤 スコープ外** |
| **`—`** | **評価** が 👌 修正不要（コード対応不要） | `[x]` |

**組み合わせの例**:

| 評価 | ステータス | 状況 |
|------|------------|------|
| 🚨 / 🟡 | 未着手 | 評価直後・未対応 |
| 🚨 / 🟡 | ✅ 対応済み | 対応完了（**評価の重要度は維持**） |
| 🚨 / 🟡 | ✅ 対応済み | 評価時点で既に直っている（**評価** は本来の重要度で記録） |
| 🟡 / 🚨 | 📤 #NNNN 別Issue化 | 別 Issue へ切り出し済み |
| 👌 | — | 対応不要と確定 |

**Codex / Copilot 等の評価の目安**: P1 / must / セキュリティ → 🚨 必須修正。P2 / 設計改善 → 🟡 修正提案。問題なし・誤指摘 → 👌 修正不要（**ステータス** `—`）。手元で既に直っている → **評価** を 🚨 / 🟡、**ステータス** を ✅ 対応済み。本 PR 範囲外で別 Issue 作成済み → **ステータス** を 📤 #NNNN 別Issue化。

## 実装後の記録更新

手順 4a で自動修正した RC は、手順 4 記録時に **ステータス** ✅ 対応済み・**対応** `[x]` として記載する（**評価**は 🚨 / 🟡 のまま）。

別タスクで RC 対応の実装や別 Issue 切り出しを行った場合は、**コミット前**にレビュー記録ファイルを更新する（AGENTS.md「レビューコメント対応記録」参照）。

1. 対象 RC のサマリ表行（冒頭通し表 + 直近セッション内表）の **対応**・**ステータス**・**PRスコープ**・**要約** を更新（**評価**は変更しない）
2. 該当 RC 記録ブロックの **ステータス**・**判断理由** を更新
3. 必要なら **対応セッション** 節を末尾に追記

コード変更のみでレビュー記録ファイルを更新しないまま完了報告しない。

## 変更種別

対応に必要な変更の性質。**固定語彙から 1 つ**選ぶ（`/shokujii-code-review` も同一語彙）。

| 記号 | 語彙 | 判断基準（例） |
|------|------|----------------|
| 🔧 | **微修正** | 既存仕様内の修正。規約違反修正、typo、null チェック、既存 API/UI のバグ修正 |
| 📐 | **リファクタ** | 挙動不変の整理。構造改善・重複削除・可読性向上（仕様書・UX 変更なし） |
| 🆕 | **新機能** | プロダクト上の**新しい能力**。仕様書・Issue に事前定義がない新画面・新 API・新 Function・新 UX フロー |
| 📋 | **仕様追加** | **既存仕様の未実装・不足の充足**。仕様書 § 参照、Issue で定義済み要件の実装、ドキュメントとの差分埋め |
| 📄 | **ドキュメントのみ** | コード変更なし。仕様書・コメント・README のみ |
| 👀 | **確認のみ** | コード変更不要。誤指摘・既対応・プロダクト判断で却下 |
| ➖ | **該当なし** | 👌 修正不要で上記に当てはまらない（定型コメント等） |

**ルール**:

- **🚨 必須修正** / **🟡 修正提案** → 🔧 / 📐 / 🆕 / 📋 / 📄 のいずれかを必須
- **ステータス** が ✅ 対応済み / 📤 #NNNN 別Issue化、または **評価** が 👌 修正不要 → 👀 / ➖ でも可（✅ で 🔧 微修正だった等も可）
- **📋 仕様追加** と判断したら、**判断理由**に仕様書の § や Issue 参照を明記する
- **🆕 新機能** と判断したら、**判断理由**に仕様書・Issue への新規定義の要否を明記する

## 想定工数

対応に必要な変更差分の目安。**S / M / L** または **`—`**（ハイフン）。

| 記号 | 目安 | 差分規模の目安 |
|------|------|----------------|
| **S** | 〜30 分 | 1 ファイル、数行〜数十行。テスト追加なしまたは既存テストのみ |
| **M** | 半日〜1 日 | 複数ファイル、store / schema / Functions 横断、軽いテスト追加 |
| **L** | 数日 | パッケージ横断、仕様策定、Firestore ルール / index、E2E 確認 |

**ルール**:

- **👀 確認のみ** / **➖ 該当なし** → **`—`**（変更種別が上記のとき。**評価** が 👌 修正不要、または **ステータス** が ✅ で 👀 / ➖ を選んだ場合も同様）
- **ステータス** が 📤 #NNNN 別Issue化 → **`—`**（本 PR では実装しないため。**評価**時の S / M / L は別 Issue 側の見積もりとして判断理由に残してよい）
- **🚨 必須修正** / **🟡 修正提案** → **S / M / L** を必須。迷ったら **M** とし、**判断理由**に根拠を書く
- **📋 仕様追加**: 多くは **M**。仕様が明確で差分が小さい場合は **S** もあり得る
- **🆕 新機能**: ほぼ **M〜L**。**S** は例外（**判断理由**に理由を書く）

## PRスコープ

この PR / 紐づく Issue に含めるべきか。**絵文字 + 語彙から 1 つ**（`/shokujii-code-review` も同一）。表記は **`📌 スコープ内`** 形式。

| 記号 | 語彙 | 判断基準 |
|------|------|----------|
| 📌 | **スコープ内** | この PR / 紐づく Issue の責務に含まれる（**ここで直す**） |
| 📤 | **スコープ外** | 指摘は妥当だが **別 Issue / 別 PR** が自然（**外に出す**。判断理由に Issue 化を明記） |
| ❓ | **要確認** | この PR に含めるか **人間が決める**（**保留・確認**。複数パッケージ、Issue 境界の曖昧さ、プロダクト判断、タイミング未定等） |

**ルール**:

- **🚨 必須修正** / **🟡 修正提案** → **📌 スコープ内** / **📤 スコープ外** / **❓ 要確認** のいずれかを必須
- **評価** が 👌 修正不要、または **ステータス** が ✅ 対応済み / 📤 #NNNN 別Issue化 → **`—`** でも可（スコープ外で却下・切り出しした場合は **📤 スコープ外**）
- **❓ 要確認** を選んだら **判断理由**に「なぜ要確認か」（例: `user + functions`、`Issue 範囲外の可能性`）を 1 行書く
- **📤 スコープ外** + **🟡** は多い → **判断理由**に別 Issue 化を書く。Issue 作成後は **ステータス** を **📤 #NNNN 別Issue化** に更新する

## ラベル

指摘の性質・影響域。**Issue ラベルと同様に 0 個以上**付与可（`/shokujii-code-review` も同一）。**絵文字 + 語彙**。表記は **`📑 仕様書, 🔒 セキュリティ`**（カンマ + 半角スペース）。該当なしは **`—`**（0 個と同義）。**「推測」ラベルは使わない**（AI 指摘は根拠が弱い場合も、ラベルを付けず `—` とし **判断理由**で説明する）。

| 記号 | ラベル | 付けるとき |
|------|--------|------------|
| 📑 | **仕様書** | `documents/` の § 参照、仕様書に明記 |
| 📏 | **規約** | shokujii-code-review / AGENTS に明記 |
| 💾 | **データ** | Firestore 欠損、Transaction 漏れ、withConverter 外更新、フィールド消失 |
| 💰 | **金銭** | Stripe、返金、注文、決済 |
| 🔒 | **セキュリティ** | Rules、権限、Secret、認可 |
| 👤 | **UX** | 表示・操作・通知の誤り |
| 🐛 | **実害** | 再現可能なバグ（上記ラベルに当てはまらない一般バグ） |

**ルール**:

- **複数 OK** — 該当するものをすべて付ける（例: `💰 金銭, 🔒 セキュリティ`）。1 つに絞らない
- **🚨 必須修正** / **🟡 修正提案** → **1 個以上推奨**。`—` のみの場合は **判断理由**に必ず理由を書く
- **👌 修正不要** / 定型コメント → 多く **`—`**
- **📋 仕様追加** と相性がよい → **📑 仕様書**（必要なら **👤 UX** も併記）
- 根拠が弱い・好みだけ → **`—`**（ラベルは付けない）
- **アクセシビリティ（a11y）指摘**（`aria-label` 不足、`alt` 欠落、キーボード操作、ARIA ロール等）で、個別仕様書に要件がない場合 → **👌 修正不要**。理由に「Phase 1 では a11y はレビュー対象外（`shokujii-code-review` 参照）」を記載する

## RC 一覧（サマリ）表形式

一覧は**箇条書きではなく Markdown 表1つ**で表現する（**要約列を含む**）。チャット・レビュー記録ファイル共通。

**見出し**: `### RC 一覧（サマリ）`

**列**（この順・このヘッダ名）:

| 対応 | RC | GitHub id | 評価 | ステータス | PRスコープ | ラベル | 種別 | 工数 | 要約 |
|:----:|:---|:---|:---|:---|:---|:---|:---|:---|:---|

- **対応**: `[ ]` 未完了 / `[x]` 完了（**ステータス** が ✅ / 📤、または **評価** が 👌 のとき `[x]` で開始可）
- **RC**: `RC-n`
- **GitHub id**: 数値、または `なし`（エージェントレビュー等）
- **評価**: 🚨 必須修正 / 🟡 修正提案 / 👌 修正不要（**評価時に確定・不変**）
- **ステータス**: 未着手 / ✅ 対応済み / 📤 #NNNN 別Issue化 / `—`（👌 のとき）
- **PRスコープ**: 📌 スコープ内 / 📤 スコープ外 / ❓ 要確認 / —
- **ラベル**: 📑 仕様書 / 📏 規約 / 💾 データ / 💰 金銭 / 🔒 セキュリティ / 👤 UX / 🐛 実害（**複数可**: `💰 金銭, 🔒 セキュリティ`）。該当なし **`—`**
- **種別**: 🔧 微修正 / 📐 リファクタ / 🆕 新機能 / 📋 仕様追加 / 📄 ドキュメントのみ / 👀 確認のみ / ➖ 該当なし（**変更種別**の短縮ヘッダ）
- **工数**: S / M / L / —
- **要約**: **コメント要約**と同内容。**3〜4 行**（表内は `<br>` で改行。2 行以下にしない）。要約だけ読んで、何が問題で、どこで、どう直すかが分かるようにする。詳細は下の RC 記録ブロックへ

**例**:


## RC 記録ブロック（必須13項目）

※ Outdated のコメントは評価対象外。件数のみを出力する（例: Outdated: 5件）。
※ レビュー非該当（手順 1 の除外リスト該当）は RC を付けず、レビュー記録ファイルに RC 記録ブロックを書かない。件数のみ（例: レビュー非該当スキップ: 2件）。
※ **評価**・**ステータス**は上記 **共通区分**（❌ は使わない）。
※ **RC 対象**の各指摘には手順 1 の並びに従い **`RC-1`, `RC-2`, …** を付与する。1コメントに複数指摘があるときは指摘ごとに振る。後続タスクで「`RC-3` に対応して」等と依頼できるようにする。
※ 差分なしの再掲は RC を付けず、**重複除外** に `GitHub id → 既存 RC-n、差分なし` と書く。レビュー非該当スキップには入れない。

**ドキュメント**（`documents/レビューコメント/review-<slug>.md` 等。パスは [review-doc-path.md](references/review-doc-path.md)）では、RC 対象ごとに **必ず** 以下の **13項目** を **この順** で記載する。**チャット**も原則同じ（`diff_hunk` のみチャットで末尾抜粋可。ドキュメントは下記ルール）。**サマリ表**（要約列含む）と各 RC ブロックの内容は一致させる。

**識別子**: `RC-1`（インラインで GitHub のコメント `id` が分かる場合は `RC-1（GitHub id: 123456789）` のように併記）

**レビュワー**: Copilot / Codex / kokufu 等を明記

**指摘箇所**: `` `path/to/file.ts:123` `` 形式（API の `path` と `line` / `original_line`）。**トップレベルコメント**（インライン行なし）の場合は `PR トップレベル` 等と明記

**該当コード（レビュー時点の diff）**:

- **インラインコメント**: GitHub API の **`diff_hunk` を改変せず**、````diff` フェンス内に貼る
- **長い `diff_hunk`**: ドキュメントでは先頭1行に `…（diff 先頭省略）` を入れ、**末尾を優先して最大約 80 行**まで掲載可
- **トップレベルコメント**: `（インライン指摘なし）` と1行明記
- **`diff_hunk` 未取得**: `(diff_hunk 未取得)` と1行明記（**指摘箇所**は省略しない）

**レビュワーのコメント（原文）**:

- **GitHub**: 分割しないときは `body` を一字一句そのまま。分割した指摘はその塊だけを削らず載せる（`>` 引用は除く）。要約は **コメント要約** のみ。``` フェンスは任意
- **エージェント**: shokujii-code-review の指摘文をそのまま（🚨 / 🟡 / 👌 付き）

**コメント要約**: **3〜4 行**。2 行以下にしない。各行は 1 文。**サマリ表の要約列**と文言を揃える（表では `<br>` で改行）。要約だけ読んで内容が分かるように、次の順で書く。

1. 何が起きるか（不具合・指摘の要点）
2. どこか（ファイル・関数、または仕様の箇所）
3. 影響（誰が困るか、データや決済がどうなるか）
4. 対応の方向（直すなら何をするか。修正不要なら、その理由）

3 行にするときは 2 と 3 を 1 行にまとめてよい。目次だけの overview も、何の目次か、実体はどの RC か、目次自体に修正要求が無いか、を 3 行程度で書く。

**評価**: 🚨 必須修正 / 🟡 修正提案 / 👌 修正不要（**評価時に確定・不変**）

**ステータス**: 未着手 / ✅ 対応済み / 📤 #NNNN 別Issue化 / `—`（👌 のとき）

**PRスコープ**: 📌 スコープ内 / 📤 スコープ外 / ❓ 要確認 / —

**ラベル**: 📑 仕様書 / 📏 規約 / 💾 データ / 💰 金銭 / 🔒 セキュリティ / 👤 UX / 🐛 実害（**複数可**: `💰 金銭, 🔒 セキュリティ`）。該当なし **`—`**（推測ラベルは使わない）

**変更種別**: 🔧 微修正 / 📐 リファクタ / 🆕 新機能 / 📋 仕様追加 / 📄 ドキュメントのみ / 👀 確認のみ / ➖ 該当なし

**想定工数**: S / M / L / —

**判断理由**: プロジェクト規約・妥当性に基づく理由を記述（**❓ 要確認**・**📤 スコープ外**・**ラベル `—`** の場合は理由を必ず含める）

---

（複数コメントがある場合は、**RC 一覧（サマリ）** 表（要約列含む）を載せ、続けて上記13項目をコメントごとに繰り返す。各 RC の末尾に `---`）

## 制約

- レビュワー（Copilot/Codex/kokufu 等）に依らず、指摘内容の妥当性のみで判断する
- プロジェクトのコーディング規約に基づいて客観的に評価する
- レビュー記録ファイルへの追記で **指摘箇所** または **レビュワーのコメント（原文）** を省略した RC ブロックは未完成とみなし、追記前に補完する
- インラインコメントでは **該当コード（diff_hunk）** も省略しない（未取得時は `(diff_hunk 未取得)` と明記）
- **auto モード**では `documents/レビューコメント/review-<slug>.md` への追記（手順 4）および手順 4a（自動修正対象 RC がある場合）が成功するまで完了とみなさない
- **auto モード**で wake consume（手順 5）は手順 4 成功後のみ。チャット要約のみでターンを終了しない
- 自動修正対象 RC があるのに手順 4a を省略して終了しない（ユーザーが「修正しない」「自動修正しない」と明示した場合を除く）
- 1 コメントに複数の指摘があるとき、全体を 1 RC にして 👌 修正不要にまとめない。指摘ごとに評価する
- 差分のない再掲をレビュー非該当スキップに入れない。**重複除外** に残す
- 会話コメントは `>` 引用の後ろまで読む。引用行だけを指摘本文とみなさない
- **コメント要約** とサマリ表の要約列は 3〜4 行。2 行以下で終えない
