## 1. 概要

### 1.1 このドキュメントの目的

「注文なしで参加」「主催者が自由にメニューを追加」「主催者がチケットを追加」の3機能は、いずれも**「参加者が選ぶものを増やす」**という同じ性質を持つ。それぞれを独立した機能として設計すると、カート・注文確定・参加者集計・キャンセル・請求のロジックが機能ごとに分岐し、破綻する。

本ドキュメントは3機能を単一のモデルで表現し、Phase 1 の実装が Phase 2・3 の下地になるようにデータ構造を定義する。

### 1.2 前提となる現行仕様

| 項目 | 現状 |
| :-- | :-- |
| 参加の正本 | `member_orders` に `status: 'ordered'` のドキュメントが存在すること。ここから `event.members` / `event_num_members` を再計算する（`functions/default/src/utils/recalcEventMembers.ts`） |
| 注文の粒度 | **メニュー1品 = 1ドキュメント**。数量 N は同一メニューのドキュメント N 件で表現する |
| メニューの出自 | `menus` サブコレクションは `PartnerMenu`（店舗マスタ）のスナップショット |
| メニューの表示制御 | `is_selected: true` のものだけ参加者に表示（`base/src/components/EventMenuList.vue`） |
| 金額 | `menu_price` は `EventMenu` / `PartnerMenu` / `EventMemberOrder` の全層で `z.number().int().positive()`（1円以上）。**税込** |
| 決済 | Stripe Connect 未使用。プラットフォームの単一アカウントで一括受領。店舗精算・主催者送金の自動化コードは存在しない |
| 税率 | メニュー（飲食）8% / 請求書手数料 10% を `common/src/utils/invoice.ts` でハードコード。参加者領収書は 8% 固定 |

## 2. 品目モデル（2軸）

品目は次の2軸で分類する。

**軸1: 役割** — イベントページのメニュー一覧に並び、参加者が「何を食べるか」として選ぶ**品目**か、メニューとは独立にカート画面で「いくら払うか」として加算される**付加項目**か。

**軸2: 供給者** — 店舗に発注し店舗が原資となる**店舗供給**か、店舗に発注せず主催者が原資・受領者となる**主催者供給**か。

|  | 品目（イベントページのメニュー一覧） | 付加項目（カート画面） |
| :-- | :-- | :-- |
| **店舗供給** | ① 店舗メニュー（既存） | 該当なし（将来の配送料等） |
| **主催者供給** | ② 主催者メニュー／**注文なし参加** | ③ チケット |

### 2.1 「注文なし参加」の位置づけ

**「注文なし参加」は ② 主催者メニューの「価格0円・システム提供」の特殊ケース**として扱う。チケット（③）には**しない**。

| 判断理由 | 内容 |
| :-- | :-- |
| 経済的な性質 | チケットはフード注文に**加算**される（参加費・場所代）。注文なし参加は徴収せず、フード注文の**代替**である |
| 参加者の体験 | イベントページのメニュー一覧に、店舗メニューと並んで表示される |
| 実装の連続性 | 主催者メニュー（Phase 2）と同一のデータ構造・UI で実現でき、Phase 1 が Phase 2 の下地になる |

### 2.2 各品目の性質

| | ① 店舗メニュー | ② 主催者メニュー | ③ チケット |
| :-- | :-- | :-- | :-- |
| マスタの出自 | `PartnerMenu` からスナップショット | 主催者が作成 | 主催者が作成 |
| 表示場所 | イベントページのメニュー一覧 | イベントページのメニュー一覧 | カート画面 |
| 店舗への発注 | **する** | しない | しない |
| 店舗への支払い | **する** | しない | しない |
| 主催者への入金 | なし | 有料時は**あり**（Phase 2） | 有料時は**あり**（Phase 3） |
| 消費税 | 8%（軽減税率） | 品目により 8% / 10% | 10%（標準税率） |
| 主催者請求書の対象 | **対象** | 対象外 | 対象外 |
| 数量 | 複数可 | 複数可（注文なし参加は1固定） | 原則1 |

## 3. コレクション設計

### 3.1 構成

```
communities/{communityId}/events/{eventId}/
├── menus/{menuId}                              品目マスタ（① + ②）
│                                               item_type: 'partner_menu' | 'organizer_menu'
├── tickets/{ticketId}                          付加項目マスタ（③）※ Phase 3 で追加
└── members/{userId}/member_orders/{orderId}    注文（① + ② + ③ を統合）
                                                item_type: 'partner_menu' | 'organizer_menu' | 'ticket'
```

**マスタは役割で分割し、注文は統合する。**

### 3.2 マスタを分割する理由

| 理由 | 内容 |
| :-- | :-- |
| 表示場所が違う | メニュー一覧に出すもの（① ②）と、カート画面に出すもの（③）。同居させるとメニュー一覧を表示する全箇所で「チケットを除外する」フィルタが必要になり、漏らすとイベントページに「セミナー参加費」が食事メニューとして並ぶ |
| フィールド構成が違う | チケットは `is_required`（必須なら自動加算・削除不可）等、メニューに存在しない属性を持つ。逆に `is_sold_out` はチケットに馴染まない。同居させると optional フィールドが増え、型の恩恵が失われる |
| ライフサイクルが違う | `menus` は下書き・申請中に `PartnerMenu` から**全再生成**される（`common/src/utils/eventMenuConverter.ts` の `convertPartnerMenusToEventMenus`）。チケットには再生成の概念がない |

### 3.3 主催者メニュー（②）を `menus` に同居させる理由

| 理由 | 内容 |
| :-- | :-- |
| 同じ一覧に混ざって表示される | 参加者から見れば選択肢の並びであり、`menu_sort_number` で通し番号として扱いたい。同居なら購読 1 本（`base/src/stores/event.ts` の `subscribeMenus`）とソート処理をそのまま使える |
| フィールド構成が同じ | `menu_name` / `menu_price` / `menu_description` / `menu_sort_number` / `is_sold_out` / `is_selected` で表現でき、追加は `item_type` のみ |
| 表示制御の既存パターンに乗る | 主催者の表示 / 非表示は既存の `is_selected` トグルで実現できる |

**同居のコスト**: `menus` の全再生成が `organizer_menu` を消してしまうため、**再生成対象を `item_type === 'partner_menu'` に限定する除外処理が必要**（1箇所）。

### 3.4 注文を統合する理由

`member_orders` はほぼ常に全品目をまとめて扱う。カート合計金額の算出、参加者としての集計、キャンセル、返金額の算出、請求書の生成のいずれも「その参加者の注文すべて」が対象である。

コレクションを分けると**これらすべてが「2回処理する」に変わり**、片方の記述漏れが「食事はキャンセルされたが参加費だけ残る」「返金額が不足する」といった金銭事故に直結する。参加の正本を二重化しないため、注文は統合する。

### 3.5 命名についての補足

`menus` コレクションに「注文なし参加」が入るのは名称としてやや不自然だが、参加者から見れば「メニュー一覧の選択肢のひとつ」であり実態とはずれていない。コレクション名の変更は既存データの移行を伴うため行わない。

`member_orders` の `menu_id` / `menu_name` / `menu_price` はチケットにも流用する（Phase 3）。フィールド名の汎用化（`item_id` 等へのリネーム）は既存データの移行コストが機能価値に見合わないため行わない。

## 4. item_type

### 4.1 定義

```typescript
// common/src/schemas/EventItemType.ts
export const EVENT_ITEM_TYPE_VALUES = ['partner_menu', 'organizer_menu', 'ticket'] as const
export type EventItemTypeType = (typeof EVENT_ITEM_TYPE_VALUES)[number]
```

| 値 | 意味 | 導入 Phase |
| :-- | :-- | :-- |
| `partner_menu` | 店舗メニュー。店舗に発注し、店舗へ支払う | Phase 1（既存データの既定値） |
| `organizer_menu` | 主催者メニュー。「注文なし参加」を含む | Phase 1 |
| `ticket` | チケット。カート画面で加算される付加項目 | Phase 3 |

**Phase 1 の時点で3値すべてを定義する。** 値の追加は容易だが、既存の値の意味を後から変えるのは困難なため。

### 4.2 供給者と役割の判定

`item_type` は1フィールドとし、供給者・役割の判定は `common` のヘルパー経由で行う。呼び出し側で `item_type === 'partner_menu'` と直接比較してはならない（値の追加時に判定漏れが発生するため）。

```typescript
// common/src/utils/eventItemType.ts
/** 店舗に発注し、店舗へ支払う品目か（発注情報・主催者請求書の対象判定） */
export function isPartnerSuppliedItem(itemType: EventItemTypeType): boolean
/** イベントページのメニュー一覧に表示する品目か */
export function isMenuItem(itemType: EventItemTypeType): boolean
/** カート画面で加算される付加項目か */
export function isTicketItem(itemType: EventItemTypeType): boolean
```

### 4.3 既存データとの互換

`item_type` は `.default('partner_menu')` を付けて定義する。`EventMenu` / `EventMemberOrder` の読み取りは AppSchema の `parse` を経由する（`functions/default/src/stores/memberOrder.ts` の `EventMemberOrderConverter` 等）ため、フィールドを持たない既存ドキュメントも既定値で解決される。**既存データのバックフィルは不要。**

ただし Firestore の `where('item_type', '==', ...)` はフィールドを持たないドキュメントに**マッチしない**ため、`item_type` による絞り込みは**必ず取得後のメモリ上で行う**（クエリ条件に使わない）。

## 5. 発注・請求・参加集計での扱い

### 5.1 集計方針

| 集計 | `partner_menu` | `organizer_menu` | `ticket` | 根拠 |
| :-- | :-- | :-- | :-- | :-- |
| 店舗への発注情報 | 含める | **除外** | **除外** | 店舗に発注しない |
| 名札 PDF（店舗が弁当に貼付） | 含める | **除外** | **除外** | 対応する品物がない |
| 店舗の最小注文数の目安 | 含める | **除外** | **除外** | 食事の数を数えるもの |
| 主催者請求書（`community_bill`） | 含める | **除外** | **除外** | 店舗への支払いを主催者に請求するもの |
| 参加者数 `event.members` / 定員 | 含める | **含める** | **含める** | 会場に来る人数 |
| 最小催行人数の判定 | 含める | **除外** | **除外** | 店舗の最小注文数を満たすための判定であり、食事注文者で数える（§5.3） |
| 参加者向けメールの宛先 | 含める | **含める** | **含める** | 参加者への連絡 |
| キャンセル・一括中止の対象 | 含める | **含める** | **含める** | 参加の取り消し |
| プロフィール `participated_event_count` | 含める | **含める** | **含める** | 参加した事実 |
| プロフィール `ordered_food_count` | 含める | **除外** | **除外** | 食事を注文していない |
| エンプラ福利厚生の補助対象・usage | 含める | **除外** | **除外** | 補助は食事代に対するもの |

### 5.2 フィルタの実装方針

`getOrders`（`functions/default/src/stores/memberOrder.ts`）の**既定の返却内容は変更しない**（全 `item_type` を返す）。

参加者集計・キャンセル・返金は「全品目を見ないと壊れる」処理であり、既定を絞り込むと**キャンセル漏れ**（参加者が取り消されずに残る）といった重い不整合を招く。したがって既定は全件のままとし、**店舗・請求書に向かう出口で明示的にフィルタする**。

対象の出口と、それぞれにフィルタ適用後の内容を検証するユニットテストを必ず用意する。

| 出口 | 対象ファイル |
| :-- | :-- |
| 店舗向け注文締切メールの共通データ | `functions/default/src/utils/order.ts`（`createOrdersForOrderDeadline`） |
| 店舗向けメール各種 | `orderDeadlineMail.ts` / `orderRemindMail.ts` / `eventStatusChangeMail.ts` / `rejectOrderMail.ts` |
| partner の注文一覧・詳細 | `partner/src/pages/order/index.vue` / `[eventId].vue`、集計は `base/src/utils/orders.ts` |
| 名札 PDF | `functions/default/src/namesPrint.ts` / `utils/namesPrintPdf.ts` |
| 主催者請求書 PDF・一覧 | `functions/default/src/eventBillInvoice.ts`、`common/src/utils/invoice.ts`、`base/src/components/manage/community/CommunityInvoice.vue` |
| エンプラダッシュボード集計 | `common/src/utils/dashboardAggregation.ts` |

### 5.3 最小催行人数の判定について

`minimum_participants` は「人が集まらなければ中止する」設定だが、実運用では**店舗の最小注文数を満たすため**に使われる。注文なし参加を人数に含めると、食事の注文が足りないまま催行が成立し店舗に迷惑がかかるため、**判定は食事注文者（`partner_menu`）のユニークユーザー数で行う**（`functions/default/src/minimumParticipantsJudgment.ts`）。

一方、`event_max_people`（定員）は会場のキャパシティであるため全品目を含める。

## 6. 消費税の扱い

現状の請求書・領収書は「メニュー合計 = 8%」を前提に実装されている。

| 箇所 | 現状 |
| :-- | :-- |
| `common/src/utils/invoice.ts` | 注文合計を 8% 税込、請求書手数料を 10% 税込として分解 |
| `functions/default/src/eventReceipt.ts` | `computeInclusive8ExTaxAndTax` で 8% 固定 |
| Stripe | `tax_behavior: 'inclusive'` のみ。`tax_rates` / `automatic_tax` は未使用 |

**Phase 2 以降は品目ごとに税率が変わる**（有料の主催者メニューは飲食物なら 8%・それ以外は 10%、チケットは 10%）。したがって Phase 2 の着手前に、品目ごとの税区分フィールドと、それを踏まえた税計算への作り替えが必要になる。

```typescript
// 導入予定（Phase 2 の前提）
export const TAX_CATEGORY_VALUES = ['reduced_8', 'standard_10'] as const
// EventMenu / EventTicket / EventMemberOrder に tax_category を追加（既定 'reduced_8'）
```

`.default('reduced_8')` を付ければ既存データのバックフィルは不要。Phase 1 の「注文なし参加」は 0 円で税額が発生しないため Phase 1 では導入しなくても成立するが、**Phase 2 の必須前提**として扱う。

## 7. お金の流れ

### 7.1 現状

参加者の支払いはプラットフォームの単一 Stripe アカウントで一括受領する。Stripe Connect（`transfer_data` / `on_behalf_of` / `application_fee_amount`）は未使用で、店舗精算・主催者送金の自動化コードは存在しない。`eventBillInvoice` は**主催者 → プラットフォーム**の請求書であり、逆方向の入金機構はない。

### 7.2 Phase による分岐

| | 参加者の支払い | 主催者への入金 | Stripe Connect |
| :-- | :-- | :-- | :-- |
| 注文なし参加（Phase 1） | 0 円（決済なし） | なし | **不要** |
| 主催者メニュー・0 円（Phase 2） | 0 円（決済なし） | なし | **不要** |
| 主催者メニュー・有料（Phase 2） | あり | **必要** | 必要（または手動振込運用） |
| チケット（Phase 3） | あり | **必要** | 必要（または手動振込運用） |

**0 円のものは Connect に依存せず実装できる。** これが Phase の切れ目である。

有料分について Connect を待たずに開始する選択肢として、プラットフォームが一旦受領し月次でまとめて主催者へ振込む**手動運用**がある（イシュー [#958](https://github.com/nijuniinc/bokudeli-event-new/issues/958) のコメント方針と一致）。運営コストと引き換えに早期リリースが可能。採用可否は Phase 2 着手時に判断する。

## 9. 主催者メニュー追加機能（Phase 2）の仕様概要

### 9.1 目的

店舗メニューにない品目を主催者が用意できるようにする。持ち込み参加枠、主催者が用意する軽食・ドリンク等。

### 9.2 データ構造

`menus/{menuId}` に `item_type: 'organizer_menu'` のドキュメントを作成する。ドキュメント ID は自動生成（「注文なし参加」のみ予約 ID。[18_注文なし参加.md](../03_参加者獲得/18_注文なし参加.md) §5.2.2 参照）。フィールドは既存の `EventMenu` と同一 + `item_type` + `tax_category`。

### 9.3 主催者の操作

Callable Function で CRUD を提供する（`updateEventMenus` は店舗メニューの選択状態更新に用途を限定し、混在させない）。

| 操作 | 制約 |
| :-- | :-- |
| 作成 | イベントが `in_draft` / `applying_reservation` / `accepting_order` のいずれか。コミュニティ管理者のみ |
| 更新 | **当該メニューの注文が 1 件でも存在する場合、`menu_name` / `menu_price` / `tax_category` は変更不可**（注文スナップショットとの乖離を防ぐ）。`is_selected` / `is_sold_out` / `menu_description` / `menu_sort_number` は変更可 |
| 削除 | 注文が存在する場合は不可。代わりに `is_selected: false` とする |

### 9.4 決定が必要な事項

- 有料の主催者メニューの入金手段（Stripe Connect / 手動振込運用）
- プラットフォーム手数料の料率と控除方法
- 主催者メニューの画像アップロードを許可するか（Storage のパス設計）
- 参加者側 UI で店舗メニューと主催者メニューを視覚的に区別するか

## 10. チケット機能（Phase 3）の仕様概要

### 10.1 目的

フード注文とは別に、セミナー参加費・場所代・懇親会費等を徴収する。

### 10.2 データ構造

```
communities/{communityId}/events/{eventId}/tickets/{ticketId}
```

| フィールド | 型 | 説明 |
| :-- | :-- | :-- |
| `ticket_name` | string | チケット名 |
| `ticket_description` | string | 説明 |
| `ticket_price` | number（int, ≥ 0） | 税込価格 |
| `tax_category` | enum | 既定 `standard_10` |
| `is_required` | boolean | true の場合、カートに自動加算され削除不可 |
| `is_selected` | boolean | 参加者への表示 / 非表示 |
| `ticket_sort_number` | number（int, ≥ 0） | 並び順 |
| `updated_at` | Timestamp / EpochMillis | 更新日時 |

将来的な拡張候補として販売上限数・販売期間・1 人あたり上限数がある。Phase 3 の初期スコープには含めない。

### 10.3 カート画面での挙動

| 種別 | 挙動 |
| :-- | :-- |
| 必須チケット（`is_required: true`） | カートに品目が入った時点で自動加算。参加者は削除できない |
| 任意チケット | カート画面で参加者が選択して追加 |

数量は原則 1。同伴者分の複数購入は将来課題とする。

注文時は `member_orders` に `item_type: 'ticket'` のドキュメントを作成し、決済・キャンセル・返金の経路を品目と共有する。

### 10.4 「注文なし参加」との併用

**併用可**とする。「参加費だけ払って食事は注文しない」は正当なユースケースであるため、排他制御は品目同士（`partner_menu` と `organizer_menu`）に限定する（[18_注文なし参加.md](../03_参加者獲得/18_注文なし参加.md) §5.4.3 の排他ルール参照）。

### 10.5 決定が必要な事項

- 主催者への売上払い出し方式（[04_有料チケットの払い出し.md](../01_マネタイズと決済/04_有料チケットの払い出し.md) の Stripe Connect 案の採否）
- プラットフォーム手数料の料率
- チケットのみ購入（食事なし）を許すか
- 領収書の記載（店舗名義の食事代とチケットを分けて発行するか）

## 12. 注意事項

### 12.1 既存システムへの影響

- **スキーマ**: `EventMenu` / `EventMemberOrder` に `item_type` を追加。`menu_price` を `positive()` から `nonnegative()` に緩和
- **メニュー再生成**: `eventMenuConverter` の再生成対象を `partner_menu` に限定
- **店舗・請求書**: §5.2 の各出口でフィルタを追加
- **Firestore Rules**: `menus` の read は既に `allow read: if true`、write は Callable 経由のみのため Phase 1 での変更は不要。`tickets` は Phase 3 で追加

### 12.2 セキュリティ考慮事項

- 主催者メニュー・チケットの作成・更新はコミュニティ管理者のみ（Callable 内で権限チェック）
- 参加者側からの品目の作成・改変は不可（`menus` / `tickets` の write はクライアントから禁止）
- 価格はサーバー側でマスタを参照して決定し、クライアントから受け取った金額を信頼しない

### 12.3 将来の拡張性

- 品目の種別追加は `EVENT_ITEM_TYPE_VALUES` への値追加と、`common/src/utils/eventItemType.ts` の判定関数の更新で対応する
- 「店舗供給の付加項目」（配送料等）が必要になった場合、`tickets` に `item_type` 相当の判別子を追加するか、`partner_fee` を `EVENT_ITEM_TYPE_VALUES` に追加して対応する
