# モデル運用・最新ブランチの取り込み・コード品質

2026-10-04の利用者の希望を、[導入計画](01_pstack導入計画.md)と[標準フロー](04_作業依頼からsandbox確認までの標準フロー.md)に追加する。実装・設定確認の状態は[チェックリスト](02_導入チェックリスト.md)の `M-* / R-* / Q-*` で管理する。この文書の作成はモデル設定や課金設定の変更、rebaseの実行を意味しない。

## 1. 使用量の出発点

添付されたSpending画面では、Ultraは月額$200、リセット日は10月25日、残り22日と表示されている。

| 枠 | 画像の使用量 | 運用で見ること |
| --- | --- | --- |
| Cursor Models | 35% | ComposerとCursorのGrokモデルで共有する月次枠 |
| Other Models | 4% | 仕様・設計・Planなどに振り分ける月次枠 |
| Grok Bot | 週次0% | 調査・資料整理の小さな依頼から試す週次枠 |
| On-Demand | $0 / 上限$50 | 画像時点では追加課金を許容する設定。D-19により無効化する方針が確定。実設定の変更は未実施 |

ダッシュボードURLはWeb取得ツールから参照できなかったため、アカウントの現在値や日別・モデル別の利用履歴は確認していない。数値の根拠は添付画像である。35%が特定モデルの消費によるとは断定しない。

画像の残り65%を22日で割ると、Cursor Modelsの目安は1日約2.95ポイントになる。これは残量を配分する目安で、金額や依頼件数への換算ではない。Other Modelsと週次枠は別に管理し、3つの割合を足さない。日別の増分・リセット日・残日数から使い切る見込みを更新する。

## 2. モデルの役割を決める

通常の実装はComposer 2.5を中心にし、仕様・設計・Planは上位モデルへ振り分ける。以下は初期の運用案であり、モデル間の品質差は対象作業で測って調整する。

| 作業 | 初期の割当 | 切替・終了の条件 |
| --- | --- | --- |
| 仕様が確定した実装、最小のバグ修正、テスト・ドキュメント、通常のRC修正 | Composer 2.5の通常版 | 同じ失敗を繰り返す、原因の根拠が得られない、設計判断が必要になったら調査・設計部分を上位モデルへ渡す |
| 仕様検討、設計検討、Plan、認証・権限・決済・データ整合性の難しい判断 | Other Modelsの上位候補（Opus / GPTの上位モデル等） | 制約・採用案・変更範囲・合否・未決事項を短く確定して、実装をComposerへ戻す。実際のモデル名・スラッグは導入時に確認する |
| 上記の判断が割れたときの別視点 | Grokモデル、または別系統のOther Models | 問いを1つに絞り、回答の根拠を主担当が照合する。回答一致だけで検証成功にしない。毎回全モデルへ同じ依頼は投げない |
| 単純な分類・要約など、Cursor Modelsの消費を分散できる作業 | Other Modelsの低単価候補 | 完了までの消費量と修正回数を比較して採用する。低単価だけで製品変更を任せるモデルを決めない |
| 公式資料の比較、調査結果の整理、読み取りだけのレビュー補助 | 人が明示的に依頼するGrok Bot | 対象・参照範囲・成果物・終了条件を限定する。まず小さな依頼1件の消費量と結果を確認する |

### 料金と枠の注意点

公式料金表の100万トークンあたりの入力・出力単価は次のとおり。キャッシュ等で実際の消費は変わる。

| モデル | 入力 | 出力 |
| --- | --- | --- |
| Composer 2.5 | $0.50 | $2.50 |
| Composer 2.5 Fast | $3.00 | $15.00 |
| Grok 4.7 通常版 | $2.00 | $6.00 |
| GPT-5.6 Luna | $0.20 | $1.20 |

ComposerはCursor Models内で低単価だが、全モデル中の最安ではない。Fastは通常版の入力・出力単価の6倍なので、初期の標準は通常版とする。Grokモデルへ切り替えてもComposerと同じ枠を消費する。Other Modelsの採用は枠の分散にもなる。[Cursor公式の料金と使用枠](https://cursor.com/docs/models-and-pricing)

Grok BotにはUltraに含まれる週次枠があり、上限後はOn-Demandが有効なら追加課金へ進む。[Grok Botの料金](https://cursor.com/help/grok-bot/plans)

### 設定と試行

- `/setup-pstack` で役割別の割当を設定し、新しい会話で実際に選ばれるモデルを確認する。主担当のモデルを変えただけで、委任先も安いモデルになるとは仮定しない。役割別設定で対象モデルを指定できなければ、手動で設計と実装の会話を分ける。
- 設計から実装へ渡す情報は、目的・制約・決定・対象ファイル・完了条件・検証手順・未決事項に絞る。決定済みの設計を毎回上位モデルで作り直さない。
- 代表的な実装・設計・調査を小さく試し、モデル、Fastの有無、作業種別、利用前後の各枠、再試行・修正回数、所要時間、検証結果を残す。並行する他の会話の消費が混じる場合はその制約を記録する。ローカルhookのトークン推定をCursorの請求額と同一視しない。
- 消費ペースが残日数の目安を超えたら、Fastの使用、長い会話、不要な重複調査・パネル、根拠のない修正の反復を見直す。未使用枠へ適した作業を移す。検証の省略で帳尻を合わせない。

Grok Botはクラウドで動き、PCを閉じても継続する。[公式概要](https://cursor.com/docs/grok-bot) 初期試行は人が依頼する調査・整理だけとし、Cursorをコード変更・コミット・PR・sandbox操作の主担当に保つ。Botによる定期起動や実装フローの自律起動はフェーズ5以降の別判断とする。読み取りの試行でも、既存の接続・権限を確認し、利用者が許可していない新しいアクセスを追加しない。

## 3. 最新のorigin/developmentを取り込む

作業ブランチは、開始・再開時に `origin/development` をfetchし、最新のコミットを取り込んでから進める。手元に古い追跡ブランチがあるだけでは最新確認にならない。

| 確認する時点 | 行うこと |
| --- | --- |
| 新規開始・中断からの再開 | fetch後のdevelopment SHAを記録する。新規ブランチはそのSHAから作り、既存ブランチは未取り込みならrebaseする |
| 他PRのマージを把握したとき・レビュー修正を再開するとき | fetchして更新を照合し、次の変更・検証の前に取り込む |
| 最終検証とpush・デプロイに進む前 | fetchし、未取り込みがあればrebaseしてから新HEADを検証する |
| 人への最終引き渡し直前 | fetchして取り込み済みか確認する。更新されていれば、取り込み・必要な再検証・PR更新・再デプロイを終えてから渡す |

最新developmentが既にHEADの祖先ならrebaseは不要。長い作業の途中にも上記の区切りを設ける。常時変化するリモートに対して「ずっと最新」とは保証せず、最終確認時刻・基点SHA・PR HEADを証拠として残す。

### 差分と履歴を守る手順

1. 現在の作業ブランチ・worktree・未コミット差分・実行中の処理を確認する。同じブランチを複数の実行者が同時に変更しない。tree/上では実装用の作業ブランチに切り替える。
2. 未コミット差分を失わない方法で退避し、復元できることを確認する。無差別な `reset --hard`、clean、秘密を含む一括コミットで解決しない。別作業者の変更を自分の変更としてまとめない。
3. fetchして基点SHAを取得し、作業ブランチをその `origin/development` へrebaseする。複数Issueの必要なコミットを保持する。競合は意図・呼び出し元・最新の仕様を読んで解消し、片側の機械的な採用で済ませない。仕様判断が必要なら止めて確認する。
4. 復元した差分と最終差分を確認し、新しいHEADを検証する。rebase後は元のHEADに対するCI・レビュー・sandbox検証を新HEADの証明として扱わない。
5. push済みの履歴を書き換える場合は、既存Git Skillの手順でリモートの変更と共有状況を確認して `--force-with-lease` を使う。未知のリモート変更やlease不一致を無条件forceで上書きしない。保護ブランチへはpushしない。

rebaseでHEADが変わったらD-09と同様にレビューの対象を更新し、必要なCI・画面検証・デプロイのSHAをそろえる。外部レビューが新HEADで利用不能ならD-08/D-10の不足表示を行う。旧runの終了とsandbox予約世代を確認してから再デプロイする。同じ作業のrebaseだけでは予約を解放せず、架空データも初期化しない。取り込みが繰り返され完了できない場合は、理由と最終確認SHAを報告し、古い基点のまま完了扱いにしない。

## 4. 少なく、質の高いコードを書く

指定された[第6章](https://zenn.dev/sc30gsw/books/080faba713547b/viewer/33f073)は、小さな実装、検証できる成果物を得てからの並列化、役割別のモデル運用を扱う。今回も1人の主担当で検証を成立させ、必要な変更の根拠を実行結果で示す方針とする。

既存計画には根本原因の修正と必要な検証があるが、slopを減らす差分確認の完了条件が不足していた。以下をコミット前のセルフレビューに加え、レビュー修正・rebase競合解消で新しい差分が増えた場合も確認する。

- 既存のcommon/base/storeの処理で満たせるか、新しい分岐・層・依存が本当に必要か確認する。同じ条件の重複実装、使われないコード、不要になった設定を残さない。
- 今回必要な具体的な処理を先に書く。未要求の将来機能、汎用フレームワーク、互換層、設定項目を追加しない。D-15の追加Issueも検証を妨げる原因の最小修正に限る。
- 根拠のない「念のため」のfallback、無条件の再試行、例外を握りつぶすcatch、型の問題を隠すキャストや抑制を入れない。必要な異常系は仕様と観測結果に対応させる。
- コメントはコードの言い換えを減らし、理由・制約・落とし穴を残す。コメント、テスト、バリデーション、認可を一括削除して行数を減らさない。
- 変更の合否を示すテストと実行証拠を保つ。実装をそのまま写したテストや、何も検出しないモックの大量追加を避ける。store/converter、Zod、Rules、Functions export等の既存ルールを維持する。
- 行数・PR件数を成果目標にしない。必要な振る舞い、修正理由、読みやすさ、変更範囲、実行証拠で評価する。必要なコードの増加を理由なく拒否しない。

`/deslop` はpstack自体には含まれず、cursor-team-kit側の依存として本で説明されている。初期は既存セルフレビューに上記観点を組み込み、同kitの初期導入を見送る方針を維持する。未導入の `/deslop` を実行済みと記録しない。追加導入は必要性・利用可否を確認した別判断とする。

## 5. 追加課金を無効化し、枠内で運用する

D-19により、On-Demandを無効化し、Ultraの含有枠を使い切ったら停止する方針が確定した。月$50の追加課金枠は使用せず、枠不足を理由に課金を有効化したり上限を引き上げたりしない。設定変更と無効状態の確認は `M-5` で実施する。今回の計画更新では実際の課金設定を変更していない。

1つの枠が不足しても、対象作業に適した別の含有枠が残っていれば、その範囲で切り替えてよい。モデルの利用可否と実際に消費する枠を確認し、有料の継続を選ばない。含有枠内で継続できなければ、Issue/PR・HEAD・未コミット差分・未完了工程・レビュー/CI/run・sandbox予約と再開手順を残して停止する。枠不足を理由に検証を省略して完了扱いにせず、sandboxも時間だけでは解放しない。リセット後や利用可能な含有枠での再開時はD-13に従い、最新状態を照合して続きから進める。
