## 1. 結論

通常の実装はComposer 2.5を中心にし、仕様・設計・PlanにOther Modelsを使う。開始・再開・最終検証・引き渡し時に最新のorigin/developmentを確認し、未取り込みならrebaseして検証し直す。コード量ではなく、必要最小限の変更と実行証拠を評価する。[具体的な運用](06_モデル運用と品質管理.md)と詳細TODOの `M-* / R-* / Q-*` に従う。

最初に作るのは、プラグイン全体の常時適用ではない。失敗しても困らない本物の画面を1つ選び、エージェントが起動し、操作し、成功の見え方を証拠として残す検証を1周させる。プラグインの追加はその作業と並行してよい。常時適用は、この1周の代わりにしない。

pstack を入れるときは、`/poteto-mode` をその会話だけで使う。全チャットの既定にはしない。戻せる実装は証拠つきで進め、コミット、マージ、本番デプロイ、`tree/` への push は今の `AGENTS.md` を優先する。

導入後に目指す標準フローは、人の作業依頼を起点に、AIがIssue作成、Issue番号の作業ブランチでの実装・コミット、PR作成、Copilot/Codexのレビュー対応、競合しないsandboxへのデプロイまで進めることである。完了は、人がデプロイ済みのものを確認できるURL・ログイン方法・検証結果を受け取れる状態。sandboxの確認、PR承認、`development`へのマージは人が行う。[標準フロー](04_作業依頼からsandbox確認までの標準フロー.md)と詳細TODOの `F-*` に、既存手順の整備と環境予約を追加する。

多数の PR を夜間に回す運用、Orchestrate は、検証が複数回通ってから別フェーズで判断する。自動マージはエージェント運用では解禁しない（第9章）。フェーズ5の前に [`03_branch_protection.md`](../01_Loop_Engineering/03_branch_protection.md) と [`02_導入チェックリスト.md`](../01_Loop_Engineering/02_導入チェックリスト.md) を読む。0-3-1 と 0-3-2 は #2119 で完了済み。未完了の 0-3-5 などが残っている間は、エージェントが PR を量産する運用には進まない。

## 2. この計画が「任せる」と呼ぶ状態

本の「はじめに」に合わせ、次の3つが依頼に書いてある状態を「任せている」と呼ぶ。

| # | 渡すもの | このリポジトリでの形 |
|:--|:---------|:---------------------|
| 1 | 何をすれば終わりか | 実行して合否が出る完了条件。画面なら「この操作のあと、この文言が見える」 |
| 2 | どう進めるか | 調べる、再現する、直す、確かめる、の順。後のフェーズで Playbook が担う |
| 3 | どう確かめるか | エージェント自身がアプリを動かし、出力、画面、保存された値のいずれかを残す |

3つ目が無いあいだは、lint や vitest が緑でも、画面の確認は人の仕事のままである。`user` / `partner` の vitest は、導入チェックリスト 0-2 の設計どおり、自動 import に依存しない純粋ロジックに限られる。Vue 画面の回帰は CI では検出されない。

## 3. 用語

| 言葉 | 意味 |
|:-----|:-----|
| Playbook | 仕事の種類ごとの手順書。バグ修正、機能追加など。利用者が直接呼ぶ Skill ではなく、`/poteto-mode` が1冊選ぶ |
| Skill | 手順の途中で使う能力。仕組みの説明、設計、検証スキルの作成など |
| Principle | 作業中の判断基準。最初は名前と適用条件の1行だけ読み、該当したときだけ全文を読む |
| `/poteto-mode` | 依頼を Playbook に振り分ける入口。一度呼ぶと、その会話ではやめると言うまで有効なまま残る |
| 検証スキル | そのアプリの起動、操作、証拠、片付けを書いたプロジェクト専用 Skill |
| Feature Map | 機能ごとに、ユーザーの到達手順、検証スキルでの操作、成功時に見えるものを書いた文書。検証スキルと一緒に作る |
| 証拠 | あとから人が見て合否を判断できるもの。コマンド出力、スクリーンショット、保存された値の読み戻し。今回の変更のあとで作ったものであることまで含める |

## 4. 本から採用する順番

本の第1部は、次の4フェーズを前のフェーズの前提にしている。この計画もこの順から外さない。

1. **成果物を信じる。** エージェントの「直しました」は判断の報告である。動いている画面、書き込まれた値、出力を、エージェントが実行し、人が見られる形で残す。ビルドやテストの成功は、動いた証拠の代わりにしない。
2. **確かめ方を再実行できる形にする。** 一度きりの目視より、同じ操作をもう一度実行できる手順をリポジトリに残す。同じ指摘が2回出たら、会話ではなく lint、CI、Skill、フックのいずれかに移す。
3. **記憶はコードベースに置く。** 会話は消える。Feature Map はアプリが変わっても CI が落ちないので、実物と照合して古さを検出する。壊れた挙動に合わせて Map を直すことはしない。
4. **自動化は最後。** 直接検証できる、手順がある、判断が残っている、推奨の実装が1本に絞られている、悪い実装を機械が止める。この5つがそろった仕事だけ、時刻やイベントで回す。

本のおわりにが提案する最初の1週間は、次の4ステップである。フェーズ1の TODO はこの4つに対応する。

1. 失敗しても困らない、本物の小さな仕事を1つ選ぶ。練習用の課題にはしない。
2. 完了条件を、実行して合否が出る文で書く。
3. テスト通過の報告ではなく、エージェントにアプリを起動させ、変えた機能を動かし、証拠を出させる。止まったら、起動方法、操作手段、テスト用ユーザーのどれが欠けていたかを記録する。
4. 同じ注意が2回出たら、文章ではなく仕組みに残す。

pstack は汎用の進め方である。Shokujii のドメイン規則は、すでに Skill と `AGENTS.md` にある。置き換えない。

| 本が求めるもの | 今あるもの | この計画での扱い |
|:---------------|:-----------|:-----------------|
| 機械的な検証 | `lint-and-format`、`pr-verify.yml`（lint / format / 型 / vitest） | そのまま隣に置く。画面の証明にはしない |
| レビューの記録 | `shokujii-code-review`、`review-comments-evaluate`、`documents/レビューコメント/` | コード変更の完了条件として残す |
| 危険操作の停止 | `protect-git-release`、機密ファイルの保護 | pstack の自律より優先する |
| 実装前の方針決定 | `grill-me` | 仕様が未確定の機能追加では、Playbook より先に使う |
| 並列の作業ディレクトリ | `wt/tree-*` | 継続して使う。`tree/` ブランチへのコミットは禁止のまま |

| 画面を操作する道具 | Playwright MCP | 検証スキルの操作手段の候補。[`documents/テスト方針・テスト項目書/playwright-mcp/`](../../テスト方針・テスト項目書/playwright-mcp/) の PhaseA/B 試行手順を棚卸しし、フェーズ1では対象機能向けに再利用・分割する。Feature Map は未作成 |

## 6. 既存ルールが優先される操作

pstack の Principle「戻せる作業は人に確認せず進める」と、`/poteto-mode` の Autonomy は、このリポジトリの規則と同時に効く。衝突したときは次の表の「採用」を使う。フェーズ2で書くプロジェクト側の指示にも、この表をそのまま入れる。

| 場面 | pstack 側の既定 | 採用 |
|:-----|:----------------|:-----|
| 製品の方針、文言の好み、仕様の未決 | 観察できることは実験し、好みは人に聞く | `grill-me` で人に聞く。決まったことだけを実装に渡す |
| コミット | 作業の区切りでコミットしうる | 標準フローの実装依頼に含む。個別に聞き直さず `AGENTS.md` と既存のコミット手順に従う。計画・調査だけの依頼では実行しない |
| PR の作成と push | Opening a PR が PR を開く | 標準フローの実装依頼に含む。`git-create-pull-request` / `git-reflect-after-commit` を使う。PRまで等の限定依頼を優先する |
| マージ | Babysit は自分ではマージしない。Shipping は頼まれたときだけ | エージェントはマージしない |
| 本番デプロイ、`firebase deploy`、`.env` / `.secret` | 戻せない操作の前で止まる | 既存のフックとスキルの禁止を優先する。sandboxは標準フローの依頼に含むが、事前に認めたプールから予約し、既存デプロイSkillで実行する。本番は含まない |
| `development` / `main` / `production` への直 push、`npm version` | force-push とデプロイの前で止まる | 既存の禁止を優先する。本流は `main` ではなく `development` |
| `tree/` ブランチ | worktree で作業する | 作業ブランチは `feat/` `fix/` など。`tree/` にはコミットも push もしない |
| コミットメッセージ | Conventional Commits の例がある | 日本語。変更ディレクトリのタグ。一致する Issue があるときだけ番号を付ける |
| Firestore | 境界で検証する、という一般原則 | DB 操作は store 経由。`xxxRef` は withConverter 付き。Zod は `common/src/schemas` と `common/src/apis` だけ |
| Functions の export | 一般の手順には無い | `functions/default/src/index.ts` の export を同じ変更に含める |
| 画面確認 | 検証スキルでエージェントが行う | 人がブラウザで見る確認が残っている間は、完了条件に「証拠が残ったか」を入れる。証拠が無い完了は認めない |

プラグイン同梱の Playbook ファイルは編集しない。更新で消える。差し替えはリポジトリ側に書き、書き方は入れる時点の pstack 0.15.9 の第37章「自分の流儀に合わせる」と README を正本にする。

## 7. フェーズ

```
フェーズ0  ルールの優先と、対象画面を1つ決める
フェーズ1  その画面の検証を1周させる（プラグインなしでよい）
フェーズ2  pstack を入れ、その会話だけで /poteto-mode を使う
フェーズ3  バグ修正用のプロジェクト手順を1枚足す
フェーズ4  差分の影響と、直す前の失敗テストを足す
フェーズ5  自動化を検討する（条件がそろうまで着手しない）
```

フェーズ2のプラグイン追加は、フェーズ1と並行して始めてよい。フェーズ2はフェーズ1の完了を置き換えない。検証の1周が無い状態で `/poteto-mode` を全チャットの既定にすると、アプリを操作する手段が無い Playbook は再現と確認を `skip` する。

### フェーズ0: 対象を固定する

人が決めるのは次の2つだけである。D-14で対象シナリオを決定し、以下の表に記録した。具体的なfixtureと操作対象は実装を調べて固定する。

- 最初の画面。推奨は、一般ユーザーアプリのイベントページでメニューを見てカートへ進む流れのうち、1画面。D-14ではイベントからカートまでを1機能の検証として選んだ。理由は、参加者の画面で、CI の vitest がコンポーネントを見ていないから。別の画面にする場合も、決済の確定、本番データ、アカウント削除は選ばない。
- その画面の完了条件を、操作と見える結果の文で1〜3個書く。

| 項目 | 決定 |
|:-----|:-----|
| 画面 | userのイベントページでメニューを選び、カートに反映されるまで（D-14）。カート確認を同じ1機能の範囲に含む |
| アプリ | user |
| 完了条件 | ①ローカル・sandboxの両方で新しいブラウザから人の補助なしにテストユーザーとしてログインできる。②架空の注文受付中イベントで指定メニューを選びカートへ追加できる。③カートのメニューと数量が選択した内容に一致する。決済確定は含めない。fixtureの具体値は実装調査で固定する |

### フェーズ1: 検証を1周させる

正本は `.agents/skills/` に置く。Cursor 用と Claude 用のスキルパスは、既存どおりシンボリックリンクで同じファイルを指す。

検証スキルに書く節は、次に限る。

| 節 | 内容 |
|:---|:-----|
| 起動 | 開発サーバーの起動コマンドと、起動できたことの判定 |
| 診断 | 接続先、テストデータ、認証、起動失敗の切り分けと停止条件 |
| 操作 | 対象画面への到達と、完了条件に書いた操作。セレクタか、画面上の見える文言で書く |
| 証拠 | 成功時に残すもの。スクリーンショットまたはアクセシビリティスナップショットを必須とし、接続先 URL・ビルド識別・操作手順とセットで残す。コンソール出力や保存値の読み戻しを併記してよい。チャット本文の文言だけでは完了にしない |
| 片付け | この手順が起動したものの止め方 |
| 詰まり | 起動、操作、テスト用ユーザーのどれで止まったかを残す欄 |
| 補助（必要な場合） | 繰り返す操作の補助スクリプト。不要ならその理由を残す |

Feature Map は、その1機能だけにする。全画面を一度に書かない。

Googleログインやメールログインでエージェントが止まり、人が代わりに操作する場合がある。認証状態の再利用、Auth Emulator、開発専用のログイン補助、専用アカウント、メールコード取得を [別紙](03_検証用ログインの検討.md)で比較し、詳細TODOの `1-6` で方式を選ぶ。ログイン後の画面確認と認証フロー自体の確認を区別する。認証補助やメール配送の変更は独立した実装単位として追跡する。検証に必要な変更を同じブランチ・PRに含めてよく、別PRの先行マージを前提にしない。

作ったあとに、書いた手順をエージェントが1回最後まで実行する。実行していない手順は下書きのまま完了にしない。検証スキルの保守で、製品の期待仕様を不具合に合わせて変更しない。検証を妨げる既存不具合の最小修正が必要な場合はD-15に従い追加Issueで追跡し、同じブランチ・PRで別のコミットとして修正する。別PRのマージ待ちは挟まない。

保守は、その機能を触る PR のときか、月1回のどちらかで、Map と実物を照合する。結果は次の3つのどれかで残す。

- 一致した。直す箇所は無い
- 手順書だけが古かった。検証スキルのディレクトリ内だけを直した
- アプリが手順と違う動きをした。手順書は不具合に合わせて直さず、原因を記録する。今回の検証を妨げる不具合はD-15に従い追加Issueと最小修正で対応する

### フェーズ2: プラグインを会話単位で使う

Cursor のチャットで pstack を追加し、`/setup-pstack` で役割ごとのモデルを決める。書き出される `~/.cursor/rules/pstack-models.mdc` は利用者のホームディレクトリにあり、リポジトリにはコミットしない。新しいチャットから効く。

このフェーズでやること:

- `/poteto-mode` は、検証したい作業のチャットの先頭だけで付ける。Custom Mode で全ターン固定にはしない。やめたいときは、その会話でやめると伝える。
- 使えるモデルのスラッグは、そのセッションでサブエージェントに渡せるものだけを書く。通常の実装はComposer 2.5の通常版を中心にし、仕様・設計・PlanはOther Modelsの上位モデルへ振り分ける。本の既定割当をそのまま採用せず、検出できたスラッグで設定する。主担当と委任先の反映を確認し、Grok Botは人が依頼する限定した調査から試す。[モデル運用](06_モデル運用と品質管理.md)に従う。
- 最初の依頼はフェーズ0で選んだ画面に限る。完了条件と、使う検証スキルのパスを依頼文に書く。
- 返答に、測定した、推論した、推測のどれかが各主張に付いているかを見る。証拠の無い「問題ありません」は完了にしない。

cursor-team-kit の `control-ui` / `control-cli` は、このフェーズでは入れない。対象画面の操作はフェーズ1の検証スキルが担う。性能計測でトレースが必要になってから検討する。

### フェーズ3: バグ修正の手順を1枚足す

プロジェクト側の手順は、バグ修正のときだけ次の順にする。

1. 再現する。検証スキルで届くところまで自分で操作する。人に再現を頼むのは、届かない理由を書いたあとだけ。
2. 安いテストが書けるなら、本番コードを直す前に、今の不具合で落ちるテストを実行し、落ちた出力を残す。モックだけのテストは足さない。
3. 根本原因を直す。効くかもしれない対策は入れない。
4. フェーズ1の検証スキルで、直す前と同じ操作が成功することを証拠で示す。単体テストの成功だけでは直ったことにしない。
5. [品質管理](06_モデル運用と品質管理.md)のslop確認を含めて `shokujii-code-review` を行う。push や PR を頼まれているときだけ `lint-and-format` を行う。
6. 第6章の採用条件に従い、許可されていない操作はしない。ユーザーが依頼したコミット、PR、push、sandbox デプロイは所定の Skill で実行してよい。

機能追加用の手順は、バグ修正が1件通ってから作る。仕様が未確定なら、その前に `grill-me` を使う。

### フェーズ4: 影響範囲とテスト

次の2つだけを、既存のレビューに足す。

- 小さい差分が Firestore ルール、Stripe、Functions を触るとき、呼び出し元の一覧ではなく、離れた画面や保存値で壊れうる根拠を、実行した結果で示す。実行できなければ未証明と書く。
- 不具合修正で手元のテストが書けるとき、修正前に失敗したログを PR または完了報告に残す。

複数モデルに同じ差分をレビューさせる使い方は、設計の意見が割れたときだけにする。毎回はしない。

### フェーズ5: 自動化は条件がそろうまで着手しない

次が全部そろうまで、`/loop` による夜間実行、Orchestrate、Autopilot、Grok Bot からの実装フローの自律起動はしない。自動マージは条件が揃ってもエージェント運用では行わない（第9章）。人が明示的に依頼する限定した調査・資料整理の試行は、モデル運用の範囲で先に行える。

- フェーズ1の検証が、対象画面で2回以上、別の変更に対して再現できている
- Feature Map の照合を1回行い、製品の不具合を手順書で隠していない
- Loop Engineering の 0-3-5 が完了し、CI が赤い PR を `development` にマージできない（0-3-1 と 0-3-2 は完了済み。正本は `03_branch_protection.md`）
- 終了条件が「N時間作業する」ではなく、テストが通る、対象画面の証拠が残る、のように合否で書ける
- 人に残す判断が、方針とマージと本番に限られている
- ループ起動前の目標契約（目的・禁止領域・停止条件・Owner・最大ラウンド数）と、試行回数・時間・トークンまたは費用の上限、kill switch が文書化されている（Loop 方針 第4章・第10章）

最初に自動化してよい候補は、Loop Engineering フェーズ1と同じく、CI が赤い PR を読んで報告するだけ（コードは変更しない）である。修正して PR を出すフェーズは、その報告の誤検知が許容範囲に入ってからにする。

## 9. この計画でやらないこと

- pstack をセッション開始時の全タスクの既定にする
- `AGENTS.md` の Skill 一覧を pstack の Playbook に置き換える
- 検証スキルを全画面分まとめて作る
- 練習用のサンプルアプリを別途作って、そこでだけ検証する
- cursor-team-kit を、対象画面の操作に必要になる前に入れる
- 計画書専用の Skill を新設する。観察できる未決は小さく動かして決める
- `/reflect` や `/automate-me` で、人の承認なしに既存 Skill を書き換える
- 自動マージ、本番デプロイ、顧客へのメッセージ送信
- PR 件数を導入の成功指標にする

最初の成功は、フェーズ1の対象画面について、エージェントが起動から証拠までを1周させ、人がその証拠で合否を判定できることである。その後の標準フローの成功は、実在する作業依頼1件をIssueからレビュー対応・sandboxデプロイまで通し、人が確認できる状態で引き渡すことである。無人の定期起動はフェーズ5の条件を別途満たすまで始めない。
