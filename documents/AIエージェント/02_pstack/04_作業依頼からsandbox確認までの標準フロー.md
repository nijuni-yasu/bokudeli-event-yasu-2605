# 作業依頼からsandbox確認までの標準フロー

人が作業を依頼したら、AIがIssue作成、実装、コミット、PR、AIレビュー対応、sandboxデプロイを進め、人がデプロイされたものを確認できる状態で引き渡す。人はsandboxを確認し、PRを承認して `development` にマージする。2026-10-04の利用者の希望を採用方針とする。

これは導入後の標準フローの設計であり、今回の計画の相談をIssue作成・コミット・デプロイの実行依頼として扱わない。実装TODOは [導入チェックリスト](02_導入チェックリスト.md)の `F-*` で管理する。

初回の主担当はCursorとする。まずCursorで全工程を通し、Claude Code・Codexへの対応拡大は後続にする。GitHub上のCopilot/CodexによるPRレビューは引き続き使う。[設計の決定事項 D-01](05_設計の決定事項.md)

初期対象はuser・partnerと関連するFunctions・Firestore・Storageとする。既存sandboxを現在の状態まで確認して活用し、enterprise・supportへの対応拡大は後続とする。[設計の決定事項 D-02](05_設計の決定事項.md)

検証データは専用の架空データを基本とする。テストユーザー・店舗・イベントと関連データを整合させ、同じ初期状態を再現できるようにする。初期プールに開発環境の既存データを丸ごとコピーすることは前提にしない。[設計の決定事項 D-06](05_設計の決定事項.md)

通常の自動検証では、メール・Slack・LINE等の外部送信をテスト用の受け口に記録する。AIが送信内容とメールログインコードを取得して確認し、実サービスへの送信は連携を確認するテストに限定する。[設計の決定事項 D-07](05_設計の決定事項.md)

## 1. 作業依頼に含める範囲

この標準フローに沿う実装依頼では、スコープ内のIssue作成、作業ブランチ作成、コミット、push、PR作成、Copilot/Codexへのレビュー依頼、コメント評価と対象修正、空いているsandboxの予約とデプロイまでを一括して依頼された範囲とする。工程ごとに同じ許可を聞き直さない。PRの`gh pr create` / `gh pr edit`も確認せず実行する。

調査・相談・計画作成だけの依頼、「PRまで」「デプロイ不要」等の限定は優先する。既存Issueが内容に一致する場合は再利用し、番号のためだけの重複Issueは作らない。仕様・方針の未決、D-15の必要最小修正を超えるスコープ変更、必要な権限・費用の追加は人の判断を残す。

マージ、本番デプロイ、保護ブランチへの直push、`npm version`、顧客への送信は含めない。`tree/` は作業場所であってコミット先ではない。

### 検証を妨げる既存不具合は同じブランチで直す

[決定事項 D-15](05_設計の決定事項.md)により、今回の検証に必要な最小修正は同じ作業に含める。今回の差分が原因でなくても、関連する既存不具合が検証を妨げる場合は、一致する既存Issueを再利用し、なければ追加Issueを作成する。同じ作業ブランチ・PRに修正を含め、追加Issueの別PRを先にマージしないと進めない状態にはしない。

ブランチ名は主たるIssueを表す名前のままでよい。修正はIssueごとに追跡できるコミットにし、各コミットには変更内容に一致するIssue番号を付ける。PR本文には含まれるIssue、検証を妨げる理由、最小修正の範囲と結果を記載する。無関係な改善は追加しない。仕様・権限・費用の変更が必要なら人に確認する。

追加Issueは同じPRで実装していても、マージ前に閉じない。PRがマージされなかった場合の再作業は許容し、Issueに未マージのPR・コミット・証拠を残す。後続作業は履歴や差分を再利用できるが、その再利用を進行の必須条件にはしない。RC由来の修正を同じPRで解消した場合、記録は「対応済み」とし、「別Issue化したので本PRでは実装しない」という扱いにしない。


### モデル・基点・差分品質

[モデル運用と品質管理](06_モデル運用と品質管理.md)に従い、通常実装はComposer 2.5、仕様・設計・Planは上位モデルを使う。開始・再開、最終検証とpush・デプロイ前、引き渡し直前にfetchし、未取り込みのorigin/developmentがあればrebaseする。コミット前には重複、過剰な抽象化、根拠のない防御コード等を確認する。rebase後は新HEADへの検証・レビュー・デプロイを対応付け、同じ作業のsandbox予約とデータは保持する。

## 2. 人とAIの分担

| 順 | 担当 | 工程 | 次に渡すもの |
| --- | --- | --- | --- |
| 1 | 人 | 作業を依頼する | 目的、対象、完了条件。未決の仕様は必要な範囲で確定 |
| 2 | AI | 既存Issueを検索し、なければ作成する | 日本語のIssue、Project・Status・milestone、Issue番号 |
| 3 | AI | Issue番号の作業ブランチで実装する | `feat/<番号>` / `fix/<番号>` 等、対象差分、検証証拠 |
| 4 | AI | 検証・セルフレビュー後にコミットする | 内容の一致するIssue番号付きの日本語コミット。無関係な変更は混ぜない |
| 5 | AI | PRを `development` 向けに作成する | PR URL、Issueとの対応、目的と検証結果 |
| 6 | GitHubのAI | CopilotとCodexがPRレビューする | 対象HEADに対するレビュー結果 |
| 7 | AI | PRコメントを評価・修正する | RC記録、必要な修正、再検証・PR更新、未解決事項 |
| 8 | AI | 空いているsandboxを予約してデプロイする | sandbox割当、最終HEAD、全対象workflowの成否 |
| 9 | AI | デプロイされた環境を確認して引き渡す | 確認URL、ログイン方法、確認手順、証拠、注意点 |
| 10 | 人 | sandboxを確認し、PRを承認・マージする | `development`へのマージ、sandboxの解放判断 |

`git-create-issue`、`git-commit-workflow`、`git-create-pull-request`、`wait-ai-pr-review`、`review-comments-evaluate`、`github-actions-deploy` を再利用する。入口は `git-reflect-after-commit`。PR作成とsandboxデプロイは同じターンで始め、レビュー待ちをデプロイの前条件にしない。修正でHEADが変わったら同じ予約で再デプロイし、PR HEADとデプロイSHAを揃えて引き渡す。

### 並行して進め、最後に最新版をそろえる

[決定事項 D-09](05_設計の決定事項.md)により、PRレビューとsandboxデプロイ・AIによる検証を並行する。上表の工程6〜9は厳密な直列ではなく、次のように進める。

1. ローカル検証・セルフレビュー後にPRを作成する。
2. Copilot/Codexへレビューを依頼し、同時に予約済みsandboxへデプロイする。空き環境がない場合でもレビューは進め、デプロイ側は待機する。
3. 受信したレビュー指摘とsandboxで観測した不具合を評価・修正する。初回デプロイは仮の確認対象として扱う。
4. HEADが変わったら必要なチェック・レビュー更新・再デプロイ・sandbox検証を行う。実行中の旧SHAのworkflowを整理し、古いrunが後から上書きしないよう制御する。
5. 最終PR HEAD、必要なコンポーネントのデプロイSHA、検証証拠をそろえて引き渡す。変更のないSHAは重複してデプロイしない。

人が途中からsandboxを確認することもできる。その場合は確認対象SHAを記録し、修正後の引き渡しで更新内容と再確認対象を伝える。旧SHAの確認を最新版の確認済みとは扱わない。片方のレビューが利用不能な場合はD-08、両方の場合はD-10に従う。

## 3. AIが完了として引き渡す条件

- Issue・PR・sandbox割当が同じ作業に対応する。
- 最終fetchで確認したorigin/developmentをHEADが取り込んでおり、基点SHA・確認時刻・PR HEADが記録されている。引き渡し前に更新があれば取り込みと再検証を行う。
- 最新HEADに必要なローカルチェック、セルフレビュー、CIが通っている。コード変更後は必要な検証を再実行する。
- Copilot/Codexへのレビュー依頼と結果、各指摘の判断・対応が記録されている。片方が利用上限・障害・無応答等で利用できない場合は、利用できたレビュー、セルフレビュー、CI・画面検証を通し、不足と理由を明記して人のsandbox確認へ進む（D-08）。partialを両者のレビュー完了とは扱わない。両方が利用不能な場合も、セルフレビュー・CI・画面検証を通し、「外部AIレビュー未実施」と理由を明記して人の確認へ進む（D-10）。
- 必須修正が残っていない。自動修正対象外の提案・仕様判断・スコープ外は理由を記録する。解消すべき必須修正が残る場合は完了にしない。
- sandboxのデプロイ対象SHAがPRの最新HEADと一致し、必要なworkflowすべてが成功している。監視の起動だけで完了にしない。
- デプロイ済みURLが開き、対象の操作を確認できる。AIが実行可能な検証はデプロイ先でも行う。ローカルだけの成功をsandboxの成功としない。
- ローカル・sandboxの両方で、AIが新しいブラウザから人のログイン補助なしにテストユーザーとして認証して対象画面を検証できる（D-05）。人には同じ対象を確認できるテストアカウント・ログイン方法、対象データ、確認手順を渡す。
- 人の確認中に別作業から上書きされないよう、sandboxの予約が維持されている。

最新HEADが変わればレビュー・検証・デプロイの対応を見直す。複数アプリ、Functions、Rulesが混在する場合は、対象コンポーネントごとのSHAと今回デプロイしないものの既存バージョンを記録する。必要な組合せを確認できない環境は引き渡さない。

## 4. sandboxを複数用意して競合を防ぐ

### 4.1 環境プール

初期プールは既存3環境（sandbox2606〜2608）で始める。1環境を1作業に割り当て、人の確認待ちも占有に数える。空きがなければ待機する。増設は待機の実績を見て別途判断する。[設計の決定事項 D-03](05_設計の決定事項.md)

2606〜2608の架空データが揃うまでは、標準フローとイベント→カート検証の正本は **sandbox2603** を1環境として使う。2606〜2608への seed・`FUNCTIONS_ENV` 変更・push は、データ構築の別PRまで行わない。selectable な候補は sandbox2603 だけとする。

予約の正本はメインクローンのローカル台帳である。worktree からは `git rev-parse --git-common-dir` の親を使い、各 tree の `.agents/state/` は読まない。

`/Users/yasukawanaohiro/Github/bokudeli-event-new/.agents/state/sandbox-reservations.json`

操作は [`.agents/scripts/sandbox_reservation.py`](../../../.agents/scripts/sandbox_reservation.py)。`fcntl` でロックしてから読む。`pick` は先に `reconcile` し、同じブランチの予約があればそれを使い、無ければ selectable かつ空きの環境を1つ取る。空きが無ければデプロイしない。人がマージまたはクローズした PR は次回 `reconcile` で空きに戻す。エージェントはマージしない。別ブランチへの新規割当の直後だけ `scripts/pstack/seed-pstack-fixture.mjs` を走らせ、同じブランチの再デプロイでは戻さない。

1環境につき、次を共有台帳で管理する。

| 区分 | 必要な情報 |
| --- | --- |
| 環境 | sandbox ID、GitHub repo/remote、Firebase project、Hosting URL、対応アプリ、Auth/DB/Storage/Functionsの接続先 |
| 利用状態 | 空き / 予約済み / デプロイ中 / 人の確認待ち / 障害・要確認 |
| 所有者 | Issue、PR、作業ブランチ、tree/worktree、チャットまたは実行者 |
| 予約 | 一意の予約ID・世代、取得日時、最終更新、解放条件、切替履歴（時間だけでは失効しない） |
| 実行 | デプロイ対象SHA、workflow run ID、各コンポーネントの成功SHA、fixture版・初期化の結果、確認証拠 |

別名のremoteでも同じFirebase projectやDBを指すなら別環境と数えない。共有Auth・DB・Functionsがある構成では、Hostingが別でも競合する。初期案は作業ごとの独立したFirebase sandbox。Hostingのpreviewだけで分離する案は、バックエンドの共有を許容できる作業に限って別途比較する。

### 4.2 予約と解放

1. 共有台帳、他の作業の予約、対象環境の実行中/待機中workflow、最後にデプロイされたSHAを確認する。
2. `sandbox_reservation.py pick` で空き環境を予約する。ロック中に読んで書く。同じブランチなら既存予約を継続する。別作業の占有は取らない。`switch` は人が別ブランチ指定をしたときだけ。
3. 新しい作業・別ブランチへの割当では、旧runの整理と予約取得後に、管理する専用の架空データを初期状態へ戻す。fixture版・対象範囲・復元結果を記録する。人の確認待ち中、同じ作業の修正、単なる再デプロイでは初期化しない。環境設定や無関係なデータは対象外（D-12）。予約所有者だけがpush・dispatchできるよう、デプロイ直前にも予約IDを確認する。`branch.<branch>.sandboxRemote` は割当先の記憶であり、予約の証明には使わない。
4. 予約を保ったまま、対象SHAをデプロイして結果を記録する。関連workflowが別の変更と混ざらないことを確認する。
5. 引き渡し後は「人の確認待ち」にして保持する。デプロイworkflowが終了しただけでは解放しない。
6. PRのマージ・クローズ、または人の明示的な返却で解放する。確認しただけでは解放しない。修正依頼が来た場合は同じ作業で予約を維持して再デプロイする。
7. 人が「別ブランチでこのsandboxを使って」と指示した場合は、割当変更と上書きの承認として扱う。対象環境・ブランチが特定できれば再確認しない。旧作業の待機中・実行中runを停止または終了まで待ち、取消要求だけで停止済みと扱わず、結果を確認して旧予約を無効化し、新しい予約世代へ切り替える。旧作業の引き渡し記録にも切替を記載する。
8. 時間経過、会話終了、PC停止だけでは解放しない。長期占有は返却候補として報告し、人の指示なく回収しない。古い予約の実行者が遅れてdispatchできないよう予約世代を検査する。[設計の決定事項 D-04](05_設計の決定事項.md)

空きがなければ待機または追加環境の準備を必要事項として報告する。他の人が確認中の環境を上書きしない。この Mac の worktree 間はメインクローンの JSON を正本にする。別マシンからの共有は未実装。tree 内だけのファイルを排他の正本にしない。`branch.<branch>.sandboxRemote` は割当先の記憶であり、予約の証明には使わない。

### 4.3 現行との差

2026-10-04に読んだローカルのworkflowでは、多くのHosting/Rulesデプロイがworkflow名で同時実行を制御し、Functionsはrefを含むgroupを使っている。`cancel-in-progress: true` もあり、後の作業が先の実行を取り消し得る。[user workflow](../../../.github/workflows/deploy_user.yml)、[Functions workflow](../../../.github/workflows/deploy_functions.yml)

この制御は「同じsandboxへの作業単位の予約」や「人の確認中の保持」ではない。異なるworkflow・ref・repoが同じ環境へ書く場合も考えて、予約とworkflowの同時実行制御を合わせて設計する。

## 5. 既存ルール・Skillで整備する点

| 現行 | 標準フローに必要な整備 |
| --- | --- |
| pstack計画がコミット・PR・sandboxを個別依頼時に限定 | この標準フローの実装依頼には一連の操作が含まれることを明記する。限定依頼は優先する |
| `git-create-issue` が作成前の確認を要求 | 標準フローの実装依頼かつ目的・完了条件が本文にあるときは確認を省略して起票する。先に一致するIssueを探す。未マージでは閉じない。「イシューを作って」だけの依頼は確認を残す |
| `git-create-pull-request` 手順10が確認を要求 | 標準フローからの委譲と「PRを作って」では `gh pr create` / `gh pr edit` の前に確認しない。本文案だけの依頼は止める |
| `git-reflect-after-commit` がコミット後に実行提案 | 標準フローの依頼では提案で止まらず委譲する（入口はこのスキル）。「コミットして」だけは提案のまま。A（PR）とB（予約してデプロイ）を同じターンで始め、修正後は同じ予約で再デプロイしてSHAを揃える |
| sandbox未割当時は人に選択を依頼 | 台帳の `pick` が selectable かつ空きの環境を選ぶ。現状の候補は sandbox2603。空きが無ければデプロイせず報告する |
| deploy Skillは失敗解析で止まり、修正・再実行をしない | 一時障害はD-11に従い、初回＋最大2回まで同じSHA・予約環境で失敗工程だけを再試行する。ビルド不良は単純再試行せず原因を調べる。D-15に従い、検証を妨げる既存不具合も追加Issueで追跡して同じブランチで最小修正する。仕様・権限・費用・破壊的変更が必要なら人に判断を求める |
| watcherはクライアントのwake機能を前提 | Cursor / Claude / Codexごとの監視・再開手段を確認する。同じShellオプションがあると仮定しない |
| PRコメント自動修正は条件と最大2周あり | 既存の評価規則を維持する。上限後の未解決事項、仕様判断、partialを隠さず返す。片方はD-08、両方はD-10に従い不足を明記して引き渡しへ進む。無限に直し続けない |

既存Skill・AGENTS・hooksの変更は入口 `git-reflect-after-commit` と台帳スクリプトで行う。計画だけを変更して既存の仕組みも対応済みと扱わない。利用者が示した一括フローの意図を反映し、工程ごとの重複した許可待ちを増やさない。

### デプロイの一時障害

[決定事項 D-11](05_設計の決定事項.md)に従い、原因を一時障害と確認できた場合だけ最大2回再試行する（初回を含め最大3回）。同じSHAと予約環境を維持し、成功済みの工程は繰り返さない。再実行前に旧runの終了・予約所有者を確認し、失敗原因とrun ID、回数を記録する。ビルドエラーや権限不足は対象外。上限に達した場合はデプロイ未完了として報告し、成功扱いや環境の自動解放はしない。

### 停止と再開

[決定事項 D-13](05_設計の決定事項.md)に従い、Cursor・PC停止中のAIの継続実行は初期範囲に含めない。開始済みのGitHubレビュー・workflowの結果は、同じ作業を再開したときに確認する。進捗・Issue/PR・HEADと未コミット差分・レビュー依頼/評価・run ID・sandbox予約を保存し、再開時に現状を照合する。未完了工程だけを続行し、同じIssue・PR・レビュー依頼・デプロイを重複作成しない。停止だけで予約は解放しない。通常の作業再開記録として整備し、フェーズ5の長時間自律作業用の台帳とは分ける。

## 6. 導入と試行

このフローは**人が依頼した1件を進める運用**である。フェーズ5の夜間起動・Bot・Autopilotの着手条件とは分ける。一括の作業依頼があっても、無人の定期起動や自動マージまで許可されたことにはならない。

検証用ログイン、PRレビュー対応、sandbox予約と監視の準備が整ったら、小さな実在の作業1件で試行する。Issueから人の確認待ちまでの所要時間、途中の人の介入、レビュー修正の回数、デプロイ失敗、環境競合を記録する。競合試験は模擬予約等で行い、人の確認環境を実際に上書きしない。

## 7. 引き渡しの書式

```markdown
- Issue / PR:
- 確認URL / sandbox ID / 予約ID:
- PR HEAD / デプロイSHA / 対象コンポーネント:
- CI・Copilot・Codex・RC対応の結果:
- デプロイrunと成否:
- AIがデプロイ先で確認した操作・証拠:
- 人のログイン方法・テストデータ・確認手順:
- 未解決事項・未証明の範囲:
- 予約の解放条件・切替履歴:
- 人に依頼すること: sandbox確認、PR承認、developmentへのマージ
```

ログイン方法は秘密の値をチャットへ載せることを意味しない。事前に決めた取得経路を示す。人から修正依頼が来たら、必要な修正・レビュー・デプロイを同じ作業として続け、新しいSHAの確認URLと証拠を渡す。
