# 検証用ログインの検討

[導入チェックリスト](02_導入チェックリスト.md)のフェーズ1で、Shokujiiをエージェントがどこまで自分で検証できるかを調べる。ログインで止まり、人が代わりに操作することがあるという利用者の報告を出発点とする。現時点では失敗を実機で再現していないため、原因と採用方式は未確定。

完了条件は [決定事項 D-05](05_設計の決定事項.md)で確定した。初期導入からローカル・sandboxの両方で、新しいブラウザから人の補助なしにテストユーザーとして認証し、対象画面まで到達する。人のログイン状態の再利用だけでは完了にしない。

## 1. 検証するものを分ける

| 検証目的 | 必要な確認 |
| --- | --- |
| ログイン後の画面・業務操作 | 必要な権限を持つテストユーザーとしてログイン済みにでき、通常の認可・store・画面操作が動くこと |
| 認証フロー | Googleからの復帰、メールコード入力、期限切れ、誤ったコード、登録済み/未登録、アカウント連携等が期待どおり動くこと |

ログイン後の画面確認では、毎回外部Google画面や受信箱を操作する必要はない。一方、認証状態を準備しただけの検証では、Googleログインやメール配送そのものを証明したことにはならない。

## 2. 他のプロジェクトでも使える代表的な方法

以下は公式資料にある手法と、そのShokujiiへの適用案。利用率の調査ではなく、再現性のあるE2E検証で選べる方法の比較である。

| 方法 | 仕組み | 適した用途 | 制約・Shokujiiでの判断 |
| --- | --- | --- | --- |
| 認証状態の再利用 | 一度ログインしてブラウザの状態を保存し、次の実行で読み込む | 調査時の比較や、AIが自分で準備した認証状態の再利用 | 失効時の再ログインが必要。FirebaseではIndexedDBの保存・復元も確認する。認証フローの証明にはならない |
| テスト専用アカウント＋自動ログイン | setup工程やAPIで認証し、ログイン済み状態から画面を操作する | 開発・ステージングの継続検証 | 1つのアカウントで並列にデータを変更すると干渉する。権限・workerごとに分ける。Shokujiiのメールログインは単純なメール/パスワード方式ではない |
| Auth Emulator＋テストユーザー | ローカルの模擬認証で、Googleの模擬画面やテスト用資格情報を使う | ローカルの画面・Rules・Functions連携検証 | 実際のGoogleサービスの挙動は証明しない。Auth以外のサービスも接続先をそろえる |
| 開発専用のログイン補助 | 限定したテストユーザーのFirebase資格情報を準備し、SDKでログインする | UIログインが不安定なときの画面検証 | 「開発モードなら誰でも任意ユーザーになれる」方式は採らない。ローカルはEmulator限定、sandboxは指定環境・指定テストユーザーだけに限定する候補を別設計にする。通常のRules・認可は維持し、本番では入口が動かない設計にする |
| テスト用メール受信・取得 | メールをテスト用の受け口へ送り、APIで対象のコードを取得して入力する | メール認証フローのE2E検証 | SendGrid送信を受け口に接続する仕組みが必要。Gmailをブラウザ操作する方式以外に、ローカルのメール捕捉や専用受信APIがある |
| 専用Google/Gmailアカウント | 組織で管理するテスト用アカウントで実際のGoogleログインやメール受信を行う | 外部連携を含む少数の実環境確認 | アカウントを与えたことと無人ログインできることは別。Google側の追加確認やブラウザ制約が解消するとは限らない。初期の主経路にはせず、外部連携確認用の候補とする |

Playwright公式は、認証状態の再利用、APIによる認証準備、権限別の状態、並列worker別のアカウントを説明している。共有データを変更する並列テストではアカウントの分離が必要になる。[Authentication](https://playwright.dev/docs/auth)

Firebase公式は、Auth EmulatorのGoogle等の模擬ログイン画面、REST経由のテストユーザー準備、カスタムトークン認証を提供している。[Auth Emulator](https://firebase.google.com/docs/emulator-suite/connect_auth)

Mailpitはメール取得等のAPIを提供するローカルのメールテスト用ツールの例。ただしShokujiiはSendGrid HTTP APIを使用しているため、Mailpitを起動するだけでは配送先は切り替わらない。[Mailpit API](https://mailpit.axllent.org/docs/api-v1/)

## 4. 推奨する検討順

外部送信の方針は [決定事項 D-07](05_設計の決定事項.md)で確定した。通常の検証ではメール・Slack・LINE等をテスト用の受け口に記録し、AIが内容やログインコードを取得する。実サービスへの送信は連携テストに限定する。以下の方式比較はこの方針を満たす実装の選定とし、通常検証でGmailの受信箱を操作することを前提にしない。

1. **停止箇所を観測する。** Google画面、popup/redirect、コード配送、コード取得、コード検証、セッション復元、ログイン後の権限のどこで止まるかを記録する。
2. **比較のため認証状態の再利用を試す。** テストユーザーで人が一度ログインしたあと、新しいブラウザ/会話でログイン済み状態から対象画面を検証できるか試す。人の補助が残るため、これだけで完全に無人になったとは扱わない。
3. **ローカルの本命としてAuth Emulatorを試す。** まず既存のプロバイダー認証をEmulatorの模擬画面で操作する。これで足りなければ、Emulator限定のログイン補助を別実装として設計する。
4. **sandboxの無人認証とメールログインの検証経路を設計する。** ローカルでSendGridへの送信内容を捕捉するadapter、または開発環境のテスト専用受信APIを比較する。sandboxではテスト用受信APIを使って通常のコード認証を通す案と、指定テストユーザーだけの認証補助を比較し、新しいブラウザから人の補助なしに到達する方式を採用する。宛先・実行IDで今回のコードを特定し、期限切れ・誤入力・再送も確認できるようにする。
5. **実Google/Gmailアカウントは必要な外部連携確認に限定して検討する。** 付与する場合も個人用アカウントではなく組織管理のテスト専用とし、通常の画面検証の主経路にはしない。

これは採用済みの仕様ではなく、コードの現状と公式機能からの提案である。開発者のログイン支援とAgentの検証には同じ基盤を使える可能性があるが、「任意のユーザーへのなりすまし」や「Rulesを通さない画面確認」を完了条件にしない。

## 5. 試行時の完了条件

- 新しいブラウザ/会話から、指定したテストユーザーのUID・役割・接続先を確認し、対象画面の操作まで到達できる。
- セッションを消した状態からもログイン状態を準備できる。人の補助を必要とする再利用方式だけでは未達とする。
- アカウントを切り替えた際に前のユーザーの状態が混ざらず、通常のRulesとアプリの認可が働く。
- ログイン失敗・状態の失効・接続先不一致は検出して止まり、黙って権限を強めない。
- 認証状態やトークンはGit・完了報告・画像に含めない。人の補助回数を記録し、補助ゼロを達成した範囲だけを無人検証可能とする。

PlaywrightではFirebaseの認証情報がIndexedDBにある場合、`storageState({ indexedDB: true })` が必要。MCPの保存ツールが同じ内容を保存するとは仮定せず、導入済みバージョンで確認する。[BrowserContext.storageState](https://playwright.dev/docs/api/class-browsercontext#browser-context-storage-state)、[MCPの認証状態管理](https://playwright.dev/mcp/tools/storage)
