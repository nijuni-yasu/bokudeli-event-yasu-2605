## 1. 台帳の使い方

- 子IDは元の台帳のIDを引き継ぐ。例: `1-2-1` は元の `1-2` の具体作業。別の名前空間にある Loop Engineering のIDは必ず `Loop 0-3-1` のように表記する。
- 状態は `Todo` / `Doing` / `✅ DONE`。依存が未完了でも状態は `Todo` とし、実行記録に停止理由を残す。Ownerは着手時に割り当てる。
- 表の「担当」は役割であり、割当済みの個人を意味しない。「人」は対象・仕様の選択、「Agent」は調査・作成・実行、「共同」は利用者のCursor設定と実行結果の確認。
- `✅ DONE` には成果物のパスまたは実行記録へのリンクが必要。未実行・`skip`・証拠不足を成功に数えない。親IDの完了は必須の子IDすべての完了で判定する。
- 条件付き項目は、適用条件が偽である根拠を記録すれば完了にできる。例えば純粋UIの変更ではStripeの検証を追加しない。適用するのに実行できない項目は未証明のまま残す。
- 導入後の標準フローでは、実装の作業依頼にIssue・コミット・push・PR・AIレビュー対応・予約済みsandboxへのデプロイを含む。工程ごとに同じ許可を聞き直さない。この台帳の作成・計画の相談だけでは外部操作を実行しない。限定依頼と [AGENTS.md](../../../AGENTS.md)、[導入計画§6](01_pstack導入計画.md#6-既存ルールが優先される操作)に従う。

## 10. 実行記録の書式

各フェーズの実行時に、まず検証スキルのディレクトリ内で記録方法を決める。画像・大きなログ・一時ファイルは公開コミットへ自動で追加せず、保存先と保持期間を明記する。実行記録から人が開けるパスまたはリンクを残す。

```markdown
### 実行 <ID> / <日時>

- 対応TODO:
- 実行者・クライアント・道具のバージョン:
- 対象: branch / HEAD SHA / 未コミット差分の識別子
- 環境: 起動URL、サービスの接続先、fixture識別子、初期状態
- 実行したコマンド・操作:
- 条件ごとの判定: 成功 / 失敗 / 未検証
- 証拠: 条件 → ログ・画像・読み戻し結果のパス
- 不具合修正時: 修正前の失敗 → 原因 → 修正後の同じ操作
- 影響範囲: 証明済み / 未証明と理由
- 主張の区別: 測定 / 推論 / 推測
- 片付け: 停止したプロセス・戻したデータ・残した証拠
- 人の補助回数、所要時間、取得可能な費用・使用量:
- 停止理由・次に必要な入力:
```

実行後に差分が変わった場合、以前の証拠を新しい差分の成功証拠として再利用しない。必要な範囲を再実行する。`.secret` は読まない。envの値、トークン、実ユーザーの個人情報をログ・画像・文書へ残さない。

- CI が成功した PR のマージと、release PR 経由で `development` を更新する実地は Loop の `0-3-5` であり、人が行う。手順の一覧は [branch protection の 0-3-5](../01_Loop_Engineering/03_branch_protection.md) にある。pstack の実験ではマージしない。`0-3-5` が Todo の間、`5-0-3` も Todo のままにする。

`5-0-4` は、終了条件が合否で書けることの確認である。検証スキルの C1〜C3 は、操作と見える結果で終わる文になっている。「N時間作業する」を終了条件に足さない。`5-0-1` の2回の証拠が揃ったあと、その証拠が C1〜C3 で判定できることを記録して完了にする。文章が足りていることだけでは完了にしない。

`5-0-5` は、人に残す判断と進行可否である。`5-0-1` から `5-0-4` が揃ったあと、次を1つの記録に書く。仕様・方針、マージ、本番は人に残っていること。起動、再現、対象画面の検証を、毎回人に依頼しなくてよい範囲。5条件が揃う前に「進行可」と書かない。

`R-1` から `R-4` の rebase 手順は [モデル運用の最新基点の節](06_モデル運用と品質管理.md) を使う。未証明なのは、その手順を捨ててよい履歴で一度通すことである。

`R-4` は次の順で行う。

1. 実在の `development` や、人が共有している作業ブランチは書き換えない。使い捨てるローカルの参照で、他 PR が先に進んだ状態を作る。
2. 未コミットの差分と、複数 Issue のコミットが残ることを確認する。退避は `git stash push -u` とし、`--all` と `.env` は含めない。
3. rebase のあと、新しい HEAD に対する検証、レビュー、デプロイの対応を記録する。古い HEAD の成功を流用しない。同じ作業の sandbox 予約と fixture は戻さない。
4. 未知のリモート変更や lease の不一致を、無条件の force で上書きしない。

`R-2` と `R-3` は、この1回の記録で手順どおりに保全と再検証ができていれば完了にできる。できていない段は未証明のまま残す。`hotfix/*` と `sync/*` では、この実験の自動 rebase を適用しない。

`Q-2` は、`Q-1` の観点を `F-4-1` の実差分か、それに先立つ実在の修正に適用する。足した処理ごとに、完了条件、原因、実行結果のどれで必要だったかを書く。レビュー修正や rebase の競合解消で増えた差分も同じである。行数や PR 件数は成功条件にしない。観点の文章がセルフレビューにあるだけでは完了にしない。
