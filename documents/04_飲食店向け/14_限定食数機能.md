# 限定食数機能（1イベントあたり / 1日あたり）

- **関連 Issue**: [#1775](https://github.com/nijuniinc/bokudeli-event-new/issues/1775)
- **マイルストーン**: v2.13
- **関連仕様書**: [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) / [07_リファクタリング/06_EventMemberOrderに伴うカート・注文・決済の実装.md](../07_リファクタリング/06_EventMemberOrderに伴うカート・注文・決済の実装.md) / [07_リファクタリング/09_EventMemberOrderに伴うキャンセル機能.md](../07_リファクタリング/09_EventMemberOrderに伴うキャンセル機能.md)

## 1. 概要

### 1.1 機能の目的

飲食店がメニューごとに提供可能な食数の上限を設定し、上限を超える注文を防止する。上限は「1 イベントあたり」と「1 日あたり（複数イベントにまたがる）」の 2 軸で指定できる。

### 1.2 主要な機能

- メニュー単位で「1 イベントあたりの上限食数」を設定できる
- メニュー単位で「1 日あたりの上限食数」を設定できる（同一 partner の複数イベントを横断して集計）
- 注文確定時に上限を超えないかをサーバー側で検証する
- 参加者向けイベントページに「残り XX 食」を表示する

### 1.3 対象ユーザー

- **飲食店（partner）**: 上限食数を設定する
- **参加者（user / enterprise）**: 残り食数を見て注文する

### 1.4 スコープ外

- 上限に達したメニューの自動売り切れ表示（[13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) の手動売り切れとは独立に扱う）
- 店舗全体（メニュー横断）の 1 日あたりキャパシティ上限
- 店舗単位（`shop_id`）での上限設定。現状 `PartnerMenu` は partner 配下で店舗に紐づかないため、partner 単位で集計する
- 上限到達時の飲食店・主催者への通知

## 2. ねらい

### 2.1 ビジネス目標

- 仕込み数に限りがあるメニュー（数量限定メニュー・高原価メニュー）を安全に提供できるようにし、飲食店の出店ハードルを下げる
- 提供能力を超える受注による当日のトラブルと返金対応を防ぐ

### 2.2 ユーザー価値

- 飲食店は仕込める数だけを販売でき、機会損失と過剰受注の両方を避けられる
- 参加者は「残り XX 食」を見て早めに注文する判断ができる

### 2.3 成功指標（KPI）

- 上限を超えた注文の発生件数: 0 件
- 限定食数を設定したメニューの利用店舗数

## 3. 前提条件

### 3.1 技術的前提条件

- 注文は [`EventMemberOrder`](../../common/src/schemas/EventMemberOrder.ts) の **1 ドキュメント = 1 食**で表現される。食数は `count` フィールドではなくドキュメント数で数える
- 注文のパスは `communities/{communityId}/events/{eventId}/members/{userId}/member_orders/{orderId}`。イベント横断の集計には `collectionGroup('member_orders')` を使う
- `status` は `in_cart` / `processing` / `ordered` / `canceled` の 4 値
- [`addToCart`](../../functions/default/src/memberOrders.ts) と [`confirmOrder`](../../functions/default/src/memberOrders.ts) は既に `db.runTransaction` 内で処理しており、`event_max_people` による定員チェックを同じ場所で行っている
- Firestore のトランザクション内では集計クエリ（`count()`）を利用できないため、上限判定はドキュメントを読んで数える

### 3.2 ビジネス的前提条件

- 上限は**メニュー単位**で設定する（店舗全体のキャパシティではない）
- カウント対象は**確定済み注文（`ordered`）のみ**。カート投入（`in_cart`）は在庫を確保しない
- 「1 日」は **`event_start_datetime` の Asia/Tokyo 暦日**で判定する

### 3.3 依存関係

- [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md): 参加者側の注文ブロック UI と `addToCart` / `confirmOrder` / `createStripeCheckoutSession` のサーバー検証を先に整備する
- 既存注文への非正規化フィールド追加に伴う backfill（[`bokudeli-event-batch`](https://github.com/nijuniinc/bokudeli-event-batch)）

## 4. 画面仕様

### 4.1 飲食店メニュー編集（partner）

対象: [`partner/src/components/MenuEditCard.vue`](../../partner/src/components/MenuEditCard.vue)

#### 4.1.1 入力フィールド

- **1イベントあたりの限定食数**
  - 任意項目
  - 型: 整数
  - バリデーション: 1 以上。未入力（空欄）は無制限として `null` を保存する
  - プレースホルダー: 「無制限」
  - ヘルプ: 「1 つのイベントで受け付ける上限の食数です」

- **1日あたりの限定食数**
  - 任意項目
  - 型: 整数
  - バリデーション: 1 以上。未入力（空欄）は無制限として `null` を保存する
  - プレースホルダー: 「無制限」
  - ヘルプ: 「同じ日に開催される複数のイベントを合計した上限の食数です」

両方が設定されている場合、`limit_per_event > limit_per_day` は設定ミスの可能性が高いため警告を表示する（保存はブロックしない）。

  - 上限未設定の場合: 何も表示しない

  - 状態: 残数が 0 のとき無効

  - 判定順序: [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) の `sold_out` 判定の後に評価する

## 5. 技術仕様・データ構造設計

### 5.1 Firestore スキーマ設計

#### 5.1.1 コレクション構造

新規コレクションの追加はない（表示用カウンタを採用する場合を除く。§5.5 参照）。既存 3 スキーマにフィールドを追加する。

```
/partners/{partnerId}
  /menus/{menuId}                    ... limit_per_event / limit_per_day を追加

/communities/{communityId}
  /events/{eventId}
    /menus/{menuId}                  ... limit_per_event / limit_per_day を追加（スナップショット）
    /members/{userId}
      /member_orders/{orderId}       ... partner_id / event_day を追加（集計用の非正規化）
```

#### 5.1.2 ドキュメントスキーマ

```typescript
// PartnerMenu / EventMenu に共通で追加
interface MenuLimitFields {
  limit_per_event: number | null // 1イベントあたりの上限食数（任意、1以上の整数、null は無制限）
  limit_per_day: number | null // 1日あたりの上限食数（任意、1以上の整数、null は無制限）
}

// EventMemberOrder に追加（日次集計を1クエリで行うための非正規化）
interface OrderAggregationFields {
  partner_id: string // イベントの partner_id（必須）
  event_day: string // event_start_datetime の Asia/Tokyo 暦日 'yyyy-MM-dd'（必須）
}
```

**非正規化の採用根拠**

`partner_id` と `event_day` は親の `Event` が持つ情報であり、コーディング規約の「親ドキュメントが既に持っている情報を子ドキュメントに重複させない」に反する。それでも複製するのは、日次集計が**イベント横断**であり、非正規化しない場合は「`events` を `partner_id` + 開催日で引く」→「各イベントの `member_orders` を引く」という 2 段のクエリをトランザクション内で実行する必要があり、対象イベント数に比例して読み取りが増えるため。非正規化により `collectionGroup('member_orders')` への 1 クエリで完結する。

整合性の担保は §5.4.2 の Trigger に依存する。`partner_id` は注文作成後に変わらない前提（イベントの店舗は承認後に変更されない）だが、この前提は §8.4 で確認する。

#### 5.1.3 Zod スキーマ定義

`common/src/schemas` 配下を更新する（[shokujii-common-schemas](../../.agents/skills/shokujii-common-schemas/SKILL.md) に従う）。

```typescript
// common/src/schemas/PartnerMenu.ts / EventMenu.ts
// DbSchema
limit_per_event: z.number().int().positive().nullable(),
limit_per_day: z.number().int().positive().nullable(),

// AppSchema（既存ドキュメントとの後方互換のため default(null)）
limit_per_event: z.number().int().positive().nullable().default(null),
limit_per_day: z.number().int().positive().nullable().default(null),
```

`nullable` を使うのは、`null` が「無制限」という**明示的な意味を持つ値**だからである。`optional`（フィールド不在）ではなく `null` を保存することで、上限を解除した状態を区別できる。同じ `PartnerMenu` の `menu_date_start` / `menu_date_end` が先例として `TimestampSchema.nullable()` を採用している。

```typescript
// common/src/schemas/EventMemberOrder.ts
// DbSchema
partner_id: z.string().nonempty(),
event_day: z.string().nonempty(),

// AppSchema
partner_id: z.string().nonempty(),
event_day: z.string().nonempty(),
```

`event_day` の生成には [`convertToDateString`](../../common/src/utils/datetime.ts)（`yyyy-MM-dd`、既定タイムゾーン Asia/Tokyo）を使う。

上記は backfill 完了後の**最終形**である。既存注文が値を持たない状態で必須にすると Zod パースに失敗するため、リリース時は一時的に `optional` として追加する（§6.3 参照）。

### 5.2 スナップショットへの反映

[`convertFromPartnerMenuToEventMenu`](../../common/src/utils/eventMenuConverter.ts) で `limit_per_event` / `limit_per_day` を `PartnerMenu` から `EventMenu` へコピーする。承認後（`accepting_order`）はスナップショットが固定されるため、**受付開始後の上限変更は反映されない**。上限を変更したい場合はイベントを差し戻す必要がある旨を飲食店向けに明示する。

### 5.3 上限判定ロジック

判定の正本はサーバー側のトランザクション内クエリとする。カウンタドキュメントを持たないため、キャンセル・返金時の減算処理が不要になる（`status` が `canceled` になれば自動的に集計対象から外れる）。

`common/src/utils/menuLimit.ts` に判定ロジックを切り出し、Vitest で単体テストする。

```typescript
// イベント単位の確定済み食数
collectionGroup('member_orders')
  .where('event_id', '==', eventId)
  .where('menu_id', '==', menuId)
  .where('status', '==', 'ordered')

// 日次（partner 横断）の確定済み食数
collectionGroup('member_orders')
  .where('partner_id', '==', partnerId)
  .where('event_day', '==', eventDay)
  .where('menu_id', '==', menuId)
  .where('status', '==', 'ordered')
```

読み取りドキュメント数は上限値（数十食程度を想定）に収まるため、トランザクション内の読み取りコストは許容範囲に収まる。クエリは [`functions/default/src/stores/memberOrder.ts`](../../functions/default/src/stores/memberOrder.ts) に store 関数として追加する。

**実装上の制約**: Firestore のトランザクションはすべての read を write より前に実行する必要がある。`confirmOrder` は既存処理で注文ドキュメントへの書き込みを行うため、上限判定のクエリは**必ず書き込みより前**に配置する。エンタープライズ補助（`finalizeEnterpriseSubsidyZeroPaymentOrder`）の経路も内部で書き込みを行うため、その呼び出し前に判定を済ませる。

### 5.4 Functions 設計

#### 5.4.1 Callable Functions（既存の変更）

| Function | ファイル | 変更内容 |
| :-- | :-- | :-- |
| `addToCart` | [`memberOrders.ts`](../../functions/default/src/memberOrders.ts) | 残数の目安チェックを追加。`partner_id` / `event_day` を注文作成時に設定 |
| `confirmOrder` | [`memberOrders.ts`](../../functions/default/src/memberOrders.ts) | トランザクション内で上限を検証。超過時は拒否 |
| `createStripeCheckoutSession` | [`stripe.ts`](../../functions/default/src/stripe.ts) | 決済開始前に上限を検証。超過時は拒否 |

`addToCart` でのチェックは `ordered` のみを数える方針上あくまで参考値であり、**権威的な判定は確定時**に行う。超過時は `HttpsError('failed-precondition', '限定食数の上限に達しました')` を返す。

#### 5.4.2 Trigger Functions（新規・条件付き）

イベントの `event_start_datetime` が変更されて暦日が変わると、既存注文の `event_day` が古くなり日次集計がずれる。注文受付中に開催日時を変更できる場合は、以下の Trigger を追加する。

```typescript
// functions/default/src/memberOrderEventDaySync.ts
export const onEventStartDatetimeChanged = onDocumentUpdated(
  { document: 'communities/{communityId}/events/{eventId}', region: 'asia-northeast1' },
  async (change) => {
    // event_start_datetime の暦日が変わった場合のみ、
    // 当該イベントの member_orders の event_day を一括更新する
  },
)
```

開催日時が `accepting_order` 以降は変更不可であることが確認できれば、この Trigger は不要（§8.3 参照）。

いずれの Function も [`functions/default/src/index.ts`](../../functions/default/src/index.ts) への export 追加が必要。

### 5.5 「残り XX 食」の表示方式

判定と表示は分離する。判定は §5.3 のサーバー側クエリが正本であり、表示は参考値でよい。

**案 A（第一候補）: クライアントからの集計クエリ**

`collectionGroup('member_orders')` に対する `count()` 集計クエリで残数を算出する。`firestore.rules` 上、PF イベント（`enterprise_id == null`）の `member_orders` は未認証でも read 可、エンプラ案件は同一 enterprise 内で read 可のため、参加者は自分が見ているイベントの注文数を読める。追加のデータ構造が不要で、常に正確な値になる。

ただし Firestore のセキュリティルールは `resource.data` を参照する条件を持つため、集計クエリが許可されるかは**実地検証が必要**。

**案 B（フォールバック）: 表示用カウンタ**

案 A が Rules 制約で成立しない場合、表示専用のカウンタを持つ。

```
/communities/{communityId}/events/{eventId}/menus/{menuId}
  ordered_count: number                              ... イベント単位の確定済み食数

/partners/{partnerId}/menu_daily_counts/{yyyy-MM-dd}_{menuId}   （※新規サブコレクション）
  partner_id: string
  menu_id: string
  event_day: string
  ordered_count: number
```

注文確定・キャンセル時に Function が更新し、クライアントは `onSnapshot` で購読してリアルタイム表示する。カウンタがずれても**表示のみの影響**にとどまり、上限判定には使わない。新規サブコレクションには `allow read: if true` / `allow write: if false` の Rules を追加する。

### 5.7 Firestore セキュリティルール

- `member_orders` の read 条件は変更しない
- `PartnerMenu` の write 条件（`request.auth.uid == partner_id`）は変更しない。上限フィールドは飲食店本人のみが更新できる
- 案 B を採用する場合のみ `partners/{partnerId}/menu_daily_counts/{docId}` のルールを追加する

### 5.8 処理フロー

#### 5.8.1 上限設定フロー

1. 飲食店が partner アプリのメニュー編集画面で上限食数を入力する
2. クライアント側でバリデーション（1 以上の整数、空欄は無制限）
3. [`base/src/stores/partner.ts`](../../base/src/stores/partner.ts) の `updateMenu` が `PartnerMenu` を更新する
4. 以後に作成・承認されるイベントのスナップショットで `EventMenu` にコピーされる

#### 5.8.2 注文確定時の上限判定フロー（エラーハンドリング含む）

1. 参加者がカート画面で注文を確定する
2. `confirmOrder` または `createStripeCheckoutSession` が呼ばれる
3. トランザクション内でイベントと確定対象注文を取得する
   - 既存の期限・定員・売り切れ検証を実施。失敗時はそれぞれのエラーを返す
4. 確定対象注文を `menu_id` ごとに集約し、各メニューについて以下を実施する
   - `EventMenu` から `limit_per_event` / `limit_per_day` を取得する
   - いずれも `null` の場合は判定をスキップする
   - `limit_per_event` が設定されていれば、イベント単位の確定済み食数を数える
   - `limit_per_day` が設定されていれば、日次の確定済み食数を数える
5. 「既存の確定済み食数 + 今回の確定食数」が上限を超える場合、`failed-precondition` で拒否する
   - どのメニューが超過したか、残り何食かをエラーメッセージに含める
6. 上限内であれば `status` を `ordered` に更新する
7. フロントエンドで結果を表示する
   - 成功: 注文完了画面へ遷移
   - 失敗: 超過メニューと残数を表示し、カートの調整を促す

#### 5.8.3 キャンセル・返金時

`cancelOrders` は `status` を `canceled` に更新するのみで、**追加実装は不要**。集計クエリが `status == 'ordered'` で絞るため、キャンセルされた注文は自動的に集計対象から外れ、その食数は次の注文者に開放される。

### 5.9 データ整合性の保証

- 上限判定はトランザクション内の読み取りで行うため、同時確定による超過が発生しない
- カウンタを持たないため、ずれの復旧運用が不要
- `event_day` は非正規化フィールドであり、開催日時変更時の再計算（§5.4.2）が整合性の唯一の依存点になる

## 6. データマイグレーション

### 6.1 マイグレーション対象

| 対象 | 内容 | 必要性 |
| :-- | :-- | :-- |
| `PartnerMenu` | `limit_per_event` / `limit_per_day` の追加 | AppSchema の `default(null)` で吸収できるため backfill 不要 |
| `EventMenu` | 同上 | 同上 |
| `EventMemberOrder` | `partner_id` / `event_day` の追加 | **backfill 必要**（必須フィールドのため既存ドキュメントに値がないと Zod パースに失敗する） |

### 6.2 実装方針

既存 Firestore データへの backfill は本リポジトリの `functions/default` ではなく [`bokudeli-event-batch`](https://github.com/nijuniinc/bokudeli-event-batch) で実装・実行する。本リポジトリ側では schema / converter / store / Rules / index / テストを整備する。

backfill の処理内容は、`collectionGroup('member_orders')` を走査し、各注文の `community_id` / `event_id` からイベントを引いて `partner_id` と `event_day`（`convertToDateString(event_start_datetime)`）を設定する。

### 6.3 段階的リリース

1. `partner_id` / `event_day` を **optional** として追加し、書き込み側（`addToCart`）で値を設定するようリリースする
2. `bokudeli-event-batch` で既存データを backfill する
3. 全件に値が入ったことを確認してから **必須** に変更する

この順序を守らないと、backfill 前の既存注文が Zod パースに失敗して読み取りエラーになる。

## 8. 注意事項

### 8.1 既存システムへの影響

#### 8.1.1 データ構造への影響

- **既存コレクションの変更**: `PartnerMenu` / `EventMenu` / `EventMemberOrder` の 3 スキーマにフィールドを追加する
- **backfill**: `EventMemberOrder` は既存全ドキュメントが対象。段階的リリース（§6.3）を必ず守る
- **インデックス追加**: `member_orders` の collectionGroup インデックス 2 件

#### 8.1.2 アプリケーションへの影響

- **フロントエンド**: `MenuEditCard.vue`（partner）、`EventMenuList.vue` / `cart.vue`（base、user / enterprise から利用）
- **バックエンド**: `addToCart` / `confirmOrder` / `createStripeCheckoutSession`
- **既存機能**: `cancelOrders` と Stripe 返金は変更不要

#### 8.1.3 運用への影響

- **読み取りコスト**: 注文確定 1 回につき、上限が設定されたメニューの数 × 最大 2 クエリの読み取りが発生する。読み取り件数は上限値に比例するため、極端に大きな上限値（数百食以上）を設定するとトランザクションが重くなる。partner 向けの入力上限値を設けるか検討する

### 8.2 セキュリティ考慮事項

- `member_orders` は PF イベントの場合、collectionGroup 経由で未認証でも read 可能（`firestore.rules` のコメント参照。公開範囲の見直しは #2282）。今回追加する `partner_id` と `event_day` はいずれも機微情報ではないため追加して問題ない。**今後 `member_orders` に機微情報を追加しないこと**
- 上限判定はクライアント表示に依存せず、必ずサーバー側のトランザクション内で行う

### 8.3 既知の制約

- **事前クレカ決済での超過**: `ordered` のみをカウントする方針のため、`user_advance`（事前クレカ決済）では Stripe の決済完了後に `stripeWebhook` が `ordered` へ遷移する時点で上限超過が判明しうる。決済済みの注文をどう扱うか（自動返金 / オーバーブッキング許容）は本仕様の範囲外とする。既存の `event_max_people` による定員チェックも同じ構造の課題を持つため、**定員側と合わせて別 Issue で対応する**
- **カート放置による先取りはできない**: `in_cart` はカウント対象外のため、カートに入れていても他の参加者に先に確定される可能性がある。これは既存の定員チェックと同じ挙動
- **`processing` はカウント対象外**: PayPay 等の遅延決済で `processing` 状態にある注文は `ordered` ではないためカウントされない。決済成立後に `ordered` へ遷移した時点で上限を超える可能性がある（上記の事前クレカ決済と同じ課題）
- **受付開始後の上限変更は反映されない**: `EventMenu` はスナップショットのため、`accepting_order` 以降に `PartnerMenu` の上限を変更しても既存イベントには反映されない

### 8.4 実装前の確認事項

- `accepting_order` 以降に主催者が `event_start_datetime` を変更できるか。変更できる場合は §5.4.2 の Trigger が必須
- `accepting_order` 以降に主催者が店舗（`partner_id` / `shop_id`）を変更できるか。変更できる場合、既存注文の `partner_id` も再計算が必要になる
- 残数表示（§5.5 案 A）の集計クエリが `firestore.rules` の条件下で許可されるか
- 空の [`10_最大注文個数.md`](./10_最大注文個数.md) が本機能と重複する構想でないか。重複する場合は統合するか、本仕様書へのリンクを追記する
