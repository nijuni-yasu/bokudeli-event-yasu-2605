# 限定食数機能（1 イベントあたり）

- **関連 Issue**: [#1775](https://github.com/nijuniinc/bokudeli-event-new/issues/1775)
- **マイルストーン**: v2.13
- **関連仕様書**: [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) / [07_リファクタリング/06_EventMemberOrderに伴うカート・注文・決済の実装.md](../07_リファクタリング/06_EventMemberOrderに伴うカート・注文・決済の実装.md) / [07_リファクタリング/09_EventMemberOrderに伴うキャンセル機能.md](../07_リファクタリング/09_EventMemberOrderに伴うキャンセル機能.md)

## 1. 概要

### 1.1 機能の目的

飲食店がメニューごとに提供可能な食数の上限を設定し、上限を超える注文を防止する。

**Phase 1** では「**1 イベントあたり**」の上限のみを実装する。大規模イベントや数量限定メニュー（仕込み数に限りがあるメニュー）向けの想定であり、同日に同一 partner が複数イベントを持つケースは Phase 1 の主対象外とする。

**Phase 2** で「1 日あたり（複数イベントにまたがる）」の上限を追加する（§7.2 参照）。

### 1.2 主要な機能（Phase 1）

- メニュー単位で「1 イベントあたりの上限食数」を設定できる
- 注文確定時に上限を超えないかをサーバー側で検証する
- 参加者向けイベントページのメニュー一覧と、カート追加モーダルの両方に「残り XX 食」を表示する

### 1.3 対象ユーザー

- **飲食店（partner）**: 上限食数を設定する
- **参加者（user / enterprise）**: 残り食数を見て注文する

### 1.4 スコープ外（Phase 1）

- **1 日あたりの上限食数**（複数イベント横断の集計）→ Phase 2
- 上限に達したメニューの自動売り切れ表示（[13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) の手動売り切れとは独立に扱う）
- 店舗全体（メニュー横断）の 1 日あたりキャパシティ上限
- 店舗単位（`shop_id`）での上限設定。現状 `PartnerMenu` は partner 配下で店舗に紐づかない
- 上限到達時の飲食店・主催者への通知

## 2. ねらい

### 2.1 ビジネス目標

- 仕込み数に限りがあるメニュー（数量限定メニュー・高原価メニュー）を安全に提供できるようにし、飲食店の出店ハードルを下げる
- 提供能力を超える受注による当日のトラブルと返金対応を防ぐ

### 2.2 ユーザー価値

- 飲食店は仕込める数だけを販売でき、機会損失と過剰受注の両方を避けられる
- 参加者は「残り XX 食」を見て早めに注文する判断ができる

### 2.3 成功指標（KPI）

- 上限を超えた注文の発生件数: 0 件
- 限定食数を設定したメニューの利用店舗数

### 2.4 Phase 1 で 1 イベントあたりのみとする理由

- 主な利用想定は**大規模イベント 1 件**における数量限定メニューの提供上限であり、同日複数イベントの横断集計は Phase 1 では不要
- `limit_per_event` のみであれば、既存の `EventMemberOrder` フィールド（`event_id` / `menu_id` / `status`）だけで集計でき、**スキーマ追加・非正規化・backfill が不要**
- Phase 2 で日次上限が必要になった場合も、`limit_per_event` フィールドはそのまま併用可能

## 3. 前提条件

### 3.1 技術的前提条件

- 注文は [`EventMemberOrder`](../../common/src/schemas/EventMemberOrder.ts) の **1 ドキュメント = 1 食**で表現される。食数は `count` フィールドではなくドキュメント数で数える
- 注文のパスは `communities/{communityId}/events/{eventId}/members/{userId}/member_orders/{orderId}`。Phase 1 の集計は `collectionGroup('member_orders')` で `event_id` をキーに行う
- `status` は `in_cart` / `processing` / `ordered` / `canceled` の 4 値
- [`addToCart`](../../functions/default/src/memberOrders.ts) と [`confirmOrder`](../../functions/default/src/memberOrders.ts) は既に `db.runTransaction` 内で処理しており、`event_max_people` による定員チェックを同じ場所で行っている
- Firestore のトランザクション内では集計クエリ（`count()`）を利用できないため、上限判定はドキュメントを読んで数える

### 3.2 ビジネス的前提条件

- 上限は**メニュー単位**で設定する（店舗全体のキャパシティではない）
- カウント対象は**確定済み注文（`ordered`）のみ**。カート投入（`in_cart`）は在庫を確保しない

### 3.3 依存関係

- [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md): 参加者側の注文ブロック UI と `addToCart` / `confirmOrder` / `createStripeCheckoutSession` のサーバー検証を先に整備する

## 4. 画面仕様

### 4.1 飲食店メニュー編集（partner）

対象: [`partner/src/components/MenuEditCard.vue`](../../partner/src/components/MenuEditCard.vue)

#### 4.1.1 入力フィールド（Phase 1）

- **1 イベントあたりの限定食数**
  - 任意項目
  - 型: 整数
  - バリデーション: 1 以上。未入力（空欄）は無制限として `null` を保存する
  - プレースホルダー: 「無制限」
  - ヘルプ: 「1 つのイベントで受け付ける上限の食数です」

### 4.2 残り食数の表示方針（共通）

「残り XX 食」は次の **2 画面** に表示する。いずれも参考値であり、権威的な判定はサーバー側（§5.3）が正本とする。

| 画面 | コンポーネント | 目的 |
| :-- | :-- | :-- |
| イベントページのメニュー一覧 | [`EventMenuList.vue`](../../base/src/components/EventMenuList.vue) | 早めの注文判断（§2.2）。`is_sold_out` と同様、一覧で状態を見せる |
| カート追加モーダル | [`EventCartDialog.vue`](../../base/src/components/EventCartDialog.vue) | 個数選択時の上限 clamp。ダイアログ open 時点の最新残数を表示 |

**残数の算出**

- `limit_per_event`（`EventMenu` スナップショット）− 当該イベントの `status == 'ordered'` 件数
- 集計は既存の `EventMemberOrder` フィールド（`event_id` / `menu_id` / `status`）のみで行う。**backfill 不要**
- `in_cart` / `processing` はカウント対象外（§3.2）

**表示の共通ルール**

- 表示文言: 「残り XX 食」
- 条件: `limit_per_event` が設定されているメニューのみ。未設定（`null`）の場合は何も表示しない
- 残数 0: 「完売」と表示する（`is_sold_out` の売り切れ表示とは独立。両方該当する場合は `sold_out` 判定を優先してボタンを無効化する）

**2 画面間の整合**

- 一覧はページ表示時、モーダルは open 時にそれぞれ集計する。表示タイミングが異なるため数値がずれることがある
- モーダル open 時の残数を**個数選択の上限**に使う（一覧より新しい値を優先）
- 一覧で残 0 と表示されていても、モーダル open 時に 1 以上になっていれば追加可能（キャンセル等）。逆に一覧で残ありでも、open 時に 0 なら追加不可

**集計クエリのタイミング**

| 画面 | 取得タイミング |
| :-- | :-- |
| `EventMenuList` | イベントページ表示時（`limit_per_event` 設定メニューのみ） |
| `EventCartDialog` | モーダル open 時（選択メニュー 1 件） |

## 5. 技術仕様・データ構造設計（Phase 1）

### 5.1 Firestore スキーマ設計

#### 5.1.1 コレクション構造

新規コレクションの追加はない（表示用カウンタを採用する場合を除く。§5.5 参照）。Phase 1 では `PartnerMenu` / `EventMenu` にフィールドを 1 つ追加するのみ。**`EventMemberOrder` の変更は不要**。

```
/partners/{partnerId}
  /menus/{menuId}                    ... limit_per_event を追加

/communities/{communityId}
  /events/{eventId}
    /menus/{menuId}                  ... limit_per_event を追加（スナップショット）
    /members/{userId}
      /member_orders/{orderId}       ... 変更なし（既存フィールドで集計）
```

#### 5.1.2 ドキュメントスキーマ

```typescript
// PartnerMenu / EventMenu に追加
interface MenuLimitFields {
  limit_per_event: number | null // 1イベントあたりの上限食数（任意、1以上の整数、null は無制限）
}
```

#### 5.1.3 Zod スキーマ定義

`common/src/schemas` 配下を更新する（[shokujii-common-schemas](../../.agents/skills/shokujii-common-schemas/SKILL.md) に従う）。

```typescript
// common/src/schemas/PartnerMenu.ts / EventMenu.ts
// DbSchema
limit_per_event: z.number().int().positive().nullable(),

// AppSchema（既存ドキュメントとの後方互換のため default(null)）
limit_per_event: z.number().int().positive().nullable().default(null),
```

`nullable` を使うのは、`null` が「無制限」という**明示的な意味を持つ値**だからである。`optional`（フィールド不在）ではなく `null` を保存することで、上限を解除した状態を区別できる。同じ `PartnerMenu` の `menu_date_start` / `menu_date_end` が先例として `TimestampSchema.nullable()` を採用している。

### 5.2 スナップショットへの反映

[`convertFromPartnerMenuToEventMenu`](../../common/src/utils/eventMenuConverter.ts) で `limit_per_event` を `PartnerMenu` から `EventMenu` へコピーする。承認後（`accepting_order`）はスナップショットが固定されるため、**受付開始後の上限変更は反映されない**。上限を変更したい場合はイベントを差し戻す必要がある旨を飲食店向けに明示する。

### 5.3 上限判定ロジック

判定の正本はサーバー側のトランザクション内クエリとする。カウンタドキュメントを持たないため、キャンセル・返金時の減算処理が不要になる（`status` が `canceled` になれば自動的に集計対象から外れる）。

`common/src/utils/menuLimit.ts` に判定ロジックを切り出し、Vitest で単体テストする。

```typescript
// イベント単位の確定済み食数（Phase 1 の唯一の集計クエリ）
collectionGroup('member_orders')
  .where('event_id', '==', eventId)
  .where('menu_id', '==', menuId)
  .where('status', '==', 'ordered')
```

読み取りドキュメント数は上限値（数十食程度を想定）に収まるため、トランザクション内の読み取りコストは許容範囲に収まる。クエリは [`functions/default/src/stores/memberOrder.ts`](../../functions/default/src/stores/memberOrder.ts) に store 関数として追加する。

**実装上の制約**: Firestore のトランザクションはすべての read を write より前に実行する必要がある。`confirmOrder` は既存処理で注文ドキュメントへの書き込みを行うため、上限判定のクエリは**必ず書き込みより前**に配置する。エンタープライズ補助（`finalizeEnterpriseSubsidyZeroPaymentOrder`）の経路も内部で書き込みを行うため、その呼び出し前に判定を済ませる。

### 5.4 Functions 設計

#### 5.4.1 Callable Functions（既存の変更）

| Function | ファイル | 変更内容 |
| :-- | :-- | :-- |
| `addToCart` | [`memberOrders.ts`](../../functions/default/src/memberOrders.ts) | 残数の目安チェックを追加 |
| `confirmOrder` | [`memberOrders.ts`](../../functions/default/src/memberOrders.ts) | トランザクション内で上限を検証。超過時は拒否 |
| `createStripeCheckoutSession` | [`stripe.ts`](../../functions/default/src/stripe.ts) | 決済開始前に上限を検証。超過時は拒否 |

`addToCart` でのチェックは `ordered` のみを数える方針上あくまで参考値であり、**権威的な判定は確定時**に行う。超過時は `HttpsError('failed-precondition', '限定食数の上限に達しました')` を返す。

Phase 1 では `EventMemberOrder` への書き込み変更（非正規化フィールドの追加）は**行わない**。

### 5.5 「残り XX 食」の表示方式

判定と表示は分離する。判定は §5.3 のサーバー側クエリが正本であり、表示は参考値でよい。表示箇所は §4.2（`EventMenuList` + `EventCartDialog` の 2 画面）。

**案 A（第一候補）: クライアントからの集計クエリ**

`collectionGroup('member_orders')` に対する `count()` 集計クエリで残数を算出する。Phase 1 はイベント単位の `event_id + menu_id + status` のみで完結する。`firestore.rules` 上、PF イベント（`enterprise_id == null`）の `member_orders` は未認証でも read 可、エンプラ案件は同一 enterprise 内で read 可のため、参加者は自分が見ているイベントの注文数を読める。追加のデータ構造が不要で、常に正確な値になる。

- `EventMenuList`: ページ表示時に `limit_per_event` 設定メニュー分の count クエリ
- `EventCartDialog`: モーダル open 時に選択メニュー 1 件の count クエリ

ただし Firestore のセキュリティルールは `resource.data` を参照する条件を持つため、集計クエリが許可されるかは**実地検証が必要**。

**案 B（フォールバック）: 表示用カウンタ**

案 A が Rules 制約で成立しない場合、表示専用のカウンタを持つ。

```
/communities/{communityId}/events/{eventId}/menus/{menuId}
  ordered_count: number                              ... イベント単位の確定済み食数
```

注文確定・キャンセル時に Function が更新し、クライアントは `onSnapshot` で購読してリアルタイム表示する。カウンタがずれても**表示のみの影響**にとどまり、上限判定には使わない。新規フィールドには `allow read: if true` / `allow write: if false` の Rules を追加する（`EventMenu` の write 条件は既存のまま。カウンタ更新は Function 経由）。

### 5.6 Firestore インデックス設計

`firestore.indexes.json` に以下を追加する（Phase 1 は 1 件）。

```json
{
  "collectionGroup": "member_orders",
  "queryScope": "COLLECTION_GROUP",
  "fields": [
    { "fieldPath": "event_id", "order": "ASCENDING" },
    { "fieldPath": "menu_id", "order": "ASCENDING" },
    { "fieldPath": "status", "order": "ASCENDING" }
  ]
}
```

### 5.7 Firestore セキュリティルール

- `member_orders` の read 条件は変更しない
- `PartnerMenu` の write 条件（`request.auth.uid == partner_id`）は変更しない。上限フィールドは飲食店本人のみが更新できる
- 案 B を採用する場合のみ `EventMenu.ordered_count` の read ルールを追加する

### 5.8 処理フロー

#### 5.8.1 上限設定フロー

1. 飲食店が partner アプリのメニュー編集画面で上限食数を入力する
2. クライアント側でバリデーション（1 以上の整数、空欄は無制限）
3. [`base/src/stores/partner.ts`](../../base/src/stores/partner.ts) の `updateMenu` が `PartnerMenu` を更新する
4. 以後に作成・承認されるイベントのスナップショットで `EventMenu` にコピーされる

#### 5.8.2 注文確定時の上限判定フロー（エラーハンドリング含む）

1. 参加者がカート画面で注文を確定する
2. `confirmOrder` または `createStripeCheckoutSession` が呼ばれる
3. トランザクション内でイベントと確定対象注文を取得する
   - 既存の期限・定員・売り切れ検証を実施。失敗時はそれぞれのエラーを返す
4. 確定対象注文を `menu_id` ごとに集約し、各メニューについて以下を実施する
   - `EventMenu` から `limit_per_event` を取得する
   - `null` の場合は判定をスキップする
   - 設定されていれば、イベント単位の確定済み食数を数える
5. 「既存の確定済み食数 + 今回の確定食数」が上限を超える場合、`failed-precondition` で拒否する
   - どのメニューが超過したか、残り何食かをエラーメッセージに含める
6. 上限内であれば `status` を `ordered` に更新する
7. フロントエンドで結果を表示する
   - 成功: 注文完了画面へ遷移
   - 失敗: 超過メニューと残数を表示し、カートの調整を促す

#### 5.8.3 キャンセル・返金時

`cancelOrders` は `status` を `canceled` に更新するのみで、**追加実装は不要**。集計クエリが `status == 'ordered'` で絞るため、キャンセルされた注文は自動的に集計対象から外れ、その食数は次の注文者に開放される。

### 5.9 データ整合性の保証

- 上限判定はトランザクション内の読み取りで行うため、同時確定による超過が発生しない
- カウンタを持たないため、ずれの復旧運用が不要
- Phase 1 は `EventMemberOrder` にフィールドを追加しないため、既存注文データへの backfill は不要

### 7.2 Phase 2（将来対応）

#### 7.2.1 1 日あたりの上限食数（複数イベント横断）

同一 partner の複数イベントを合算した日次上限。Phase 2 で `limit_per_day` を `PartnerMenu` / `EventMenu` に追加する。

**集計方針（backfill なし）**

`EventMemberOrder` への非正規化（`partner_id` / `event_day`）および既存データの backfill は**行わない**。代わりにトランザクション内で次の 2 段クエリを使う。

1. `collectionGroup('events')` で `partner_id` + `event_start_datetime` の JST 暦日レンジから、当該日のイベント一覧を取得する（`accepting_order` 限定ではなく、**その日に開催される全イベント**が対象。終了済みイベントの `ordered` も日次上限に含める）
2. 各イベントについて `collectionGroup('member_orders')` で `event_id` + `menu_id` + `status == 'ordered'` を数え、合算する（`event_id in [...]` は 30 件上限のため、同日イベント数が多い場合はバッチ分割）

`limit_per_event` と `limit_per_day` の両方が設定されている場合、残数表示・判定とも**残数の少ない方**を適用する。

**非正規化を採用しない理由（Phase 2）**

`partner_id` と `event_day` は親 `Event` が持つ情報であり、コーディング規約の「親ドキュメントが既に持っている情報を子ドキュメントに重複させない」に反する。backfill を避けるため Phase 2 でも非正規化は採用せず、読み取りコストは対象イベント数に比例する。同日イベント数が少ない前提（Phase 1 と同様）であれば許容範囲とする。パフォーマンス問題が顕在化した場合のみ、非正規化 + backfill を別 Issue で検討する。

## 8. 注意事項

### 8.1 既存システムへの影響

#### 8.1.1 データ構造への影響（Phase 1）

- **既存コレクションの変更**: `PartnerMenu` / `EventMenu` の 2 スキーマに `limit_per_event` を追加する。**`EventMemberOrder` は変更しない**
- **backfill**: 不要
- **インデックス追加**: `member_orders` の collectionGroup インデックス 1 件（`event_id` + `menu_id` + `status`）

#### 8.1.2 アプリケーションへの影響

- **フロントエンド**: `MenuEditCard.vue`（partner）、`EventMenuList.vue` / `EventCartDialog.vue` / `cart.vue`（base、user / enterprise から利用）
- **バックエンド**: `addToCart` / `confirmOrder` / `createStripeCheckoutSession`
- **既存機能**: `cancelOrders` と Stripe 返金は変更不要

#### 8.1.3 運用への影響

- **読み取りコスト（Phase 1）**: 注文確定 1 回につき、上限が設定されたメニューの数 × 1 クエリの読み取りが発生する。読み取り件数は上限値に比例するため、極端に大きな上限値（数百食以上）を設定するとトランザクションが重くなる。partner 向けの入力上限値を設けるか検討する

### 8.2 セキュリティ考慮事項

- `member_orders` は PF イベントの場合、collectionGroup 経由で未認証でも read 可能（`firestore.rules` のコメント参照。公開範囲の見直しは #2282）。Phase 1 では `EventMemberOrder` にフィールドを追加しない。**今後 `member_orders` に機微情報を追加しないこと**
- 上限判定はクライアント表示に依存せず、必ずサーバー側のトランザクション内で行う

### 8.3 既知の制約

- **事前クレカ決済での超過**: `ordered` のみをカウントする方針のため、`user_advance`（事前クレカ決済）では Stripe の決済完了後に `stripeWebhook` が `ordered` へ遷移する時点で上限超過が判明しうる。決済済みの注文をどう扱うか（自動返金 / オーバーブッキング許容）は本仕様の範囲外とする。既存の `event_max_people` による定員チェックも同じ構造の課題を持つため、**定員側と合わせて別 Issue で対応する**
- **カート放置による先取りはできない**: `in_cart` はカウント対象外のため、カートに入れていても他の参加者に先に確定される可能性がある。これは既存の定員チェックと同じ挙動
- **`processing` はカウント対象外**: PayPay 等の遅延決済で `processing` 状態にある注文は `ordered` ではないためカウントされない。決済成立後に `ordered` へ遷移した時点で上限を超える可能性がある（上記の事前クレカ決済と同じ課題）
- **受付開始後の上限変更は反映されない**: `EventMenu` はスナップショットのため、`accepting_order` 以降に `PartnerMenu` の上限を変更しても既存イベントには反映されない
- **Phase 1 は同日複数イベントの横断上限をカバーしない**: 同一 partner が同日に複数イベントを持ち、厨房の日次仕込み上限を守りたい場合は Phase 2 の `limit_per_day` が必要
