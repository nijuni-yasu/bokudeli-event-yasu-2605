# 売り切れ機能のリアルタイム化

- **関連 Issue**: [#1774](https://github.com/nijuniinc/bokudeli-event-new/issues/1774)
- **マイルストーン**: v2.13
- **関連仕様書**: [02_主催者獲得と継続/10_イベント作成時のメニュー選択機能.md](../02_主催者獲得と継続/10_イベント作成時のメニュー選択機能.md) / [02_主催者獲得と継続/15_予約申請時のバリデーション.md](../02_主催者獲得と継続/15_予約申請時のバリデーション.md) / [14_限定食数機能.md](./14_限定食数機能.md)

## 1. 概要

### 1.1 機能の目的

飲食店が売り切れに切り替えたメニューを、注文受付中（`accepting_order`）のイベントページへリアルタイムに反映し、売り切れメニューの注文を防止する。

### 1.2 主要な機能

- 飲食店が `PartnerMenu.is_sold_out` を切り替えると、注文受付中の全イベントの `EventMenu.is_sold_out` へ自動反映する
- 参加者向けイベントページで売り切れメニューを「売り切れ」表示にし、カート追加を無効化する
- カート追加・注文確定・Stripe Checkout セッション作成の各サーバー処理で売り切れを検証する
- 売り切れメニューも `EventMenu` としてスナップショットし、売り切れ解除（復活）も反映できるようにする

### 1.3 対象ユーザー

- **飲食店（partner）**: 売り切れ操作を行う
- **参加者（user / enterprise）**: 売り切れ状態を見て注文する
- **主催者（user）**: イベント作成時にメニューを選択する

### 1.4 スコープ外

- 在庫数による自動売り切れ（食数上限は [14_限定食数機能.md](./14_限定食数機能.md) で扱う）
- イベント単位で個別に売り切れを設定する機能（飲食店の操作は全イベント共通）
- 売り切れ発生時の参加者へのプッシュ通知・メール通知

## 2. ねらい

### 2.1 ビジネス目標

- 提供できないメニューの注文を未然に防ぎ、当日のキャンセル・返金対応と店舗クレームを削減する
- 飲食店が売り切れ操作を行えば確実に反映される状態を作り、店舗の運用負荷と不信感を減らす

### 2.2 ユーザー価値

- 参加者は注文できるメニューだけを見て選べる
- 飲食店は在庫切れ時に自店舗の操作だけで注文を止められる

### 2.3 成功指標（KPI）

- 売り切れメニューに対する注文発生件数: 0 件
- 飲食店の売り切れ操作から参加者画面への反映時間: 10 秒以内

## 3. 前提条件

### 3.1 技術的前提条件（現行実装の課題）

現状、売り切れが参加者に伝わらない原因は 3 つある。

1. **同期経路が存在しない**
   売り切れの正本は `partners/{partnerId}/menus/{menuId}` の `PartnerMenu.is_sold_out`。参加者が見るのは `communities/{communityId}/events/{eventId}/menus/{menuId}` の `EventMenu` で、これは店舗承認時（`applying_reservation → accepting_order`）に [`onShopReservationChanged`](../../functions/default/src/eventMenusSnapshot.ts) が作るスナップショット。承認後に `updateEventMenus` が更新するのは `is_selected` のみで（[`shouldUpdateExistingMenusOnly`](../../common/src/utils/eventMenuConverter.ts)）、売り切れ変更を `EventMenu` へ運ぶ経路がない。

2. **売り切れメニューは `EventMenu` が生成されない**
   [`convertFromPartnerMenuToEventMenu`](../../common/src/utils/eventMenuConverter.ts) は `partnerMenu.is_sold_out` が `true` のとき `null` を返し、`EventMenu` ドキュメント自体を作らない。そのため「承認時に売り切れ → 後で復活」を反映する対象ドキュメントが存在しない。

3. **参加者側が `is_sold_out` を参照していない**
   [`EventMenuList.vue`](../../base/src/components/EventMenuList.vue) は `is_selected === true` のみでフィルタし、売り切れ表示を持たない。[`addToCart`](../../functions/default/src/memberOrders.ts) も `is_selected` しか検証していない。文言 `menu_disabled_reason.sold_out` は [`ja.ts`](../../base/src/locales/messages/ja.ts) に定義済みだが未使用。

一方で、以下は既に整備済みであり本機能で利用できる。

- `EventMenu` は [`base/src/stores/event.ts`](../../base/src/stores/event.ts) の `subscribeMenus` が `onSnapshot` で購読しているため、Firestore 上で `EventMenu` が更新されれば画面は自動的に追従する
- `EventMenu` は `firestore.rules` で `allow read: if true` のみ定義されており、書き込みは Functions（Admin SDK）専用

### 3.2 依存関係

- 予約申請時バリデーション [`validateReservationRequest.ts`](../../common/src/utils/validateReservationRequest.ts) の `NO_ORDERABLE_MENU_SELECTED` 判定（`is_selected && !is_sold_out`）
- メニュー画像の Storage コピー処理（[`savePartnerMenusToEventMenus`](../../functions/default/src/eventMenusSnapshot.ts)）

## 4. 画面仕様

### 4.1 参加者向けイベントページ（user / enterprise）

対象: [`base/src/components/EventMenuList.vue`](../../base/src/components/EventMenuList.vue)、[`user/src/pages/c/[communityAccount]/e/[eventId]/index.vue`](<../../user/src/pages/c/[communityAccount]/e/[eventId]/index.vue>)

#### 4.1.1 表示要素

- **売り切れバッジ**
  - 表示内容: 「売り切れ」
  - 条件: `EventMenu.is_sold_out === true`
  - スタイル: 既存の [`MenuCard.vue`](../../base/src/components/MenuCard.vue) の `.sold-out` に準拠

#### 4.1.2 ボタン・アクション

- **カートに追加ボタン**
  - 状態: `is_sold_out === true` のとき無効
  - 無効理由の表示: `MenuDisabledReason` に `sold_out` を追加し、`menu_disabled_reason.sold_out`（「売り切れました。カートに追加できません」）を表示する
  - 優先順位: 既存の `event_canceled` / `finished` / `order_closed` / `not_accepting_order` / `limit_people` の判定後に `sold_out` を評価する（イベント全体の状態を優先）

#### 4.1.3 表示・非表示の方針

売り切れメニューは**一覧から消さず、売り切れ表示付きで表示する**。売り切れ解除時に何も操作せず復活し、参加者にも「一時的に売り切れている」ことが伝わるため。

### 4.2 カート画面

対象: [`base/src/components/pages/cart.vue`](../../base/src/components/pages/cart.vue)

- 売り切れになったメニューがカートに残っている場合、**自動削除はしない**
- 該当行に「売り切れ」表示を出し、注文確定ボタンを無効化する
- 注文確定時にサーバー側で弾かれた場合はエラーメッセージを表示する

### 4.3 飲食店メニュー管理（partner）

対象: [`partner/src/components/MenuEditCard.vue`](../../partner/src/components/MenuEditCard.vue)

- 既存の売り切れスイッチの UI 変更はなし
- スイッチ操作が注文受付中の全イベントに反映される旨の注意書きを添える

### 4.4 主催者のメニュー選択（EventEdit）

対象: [`base/src/components/EventEdit.vue`](../../base/src/components/EventEdit.vue)、[`base/src/components/eventcreate/EventMenu.vue`](../../base/src/components/eventcreate/EventMenu.vue)

- 売り切れ除外の廃止により、売り切れメニューも選択候補として表示されるようになる
- 「売り切れ中」表示を添えるが、**選択自体は許可する**（イベント当日までに復活しうるため）

## 5. 技術仕様・データ構造設計

### 5.1 Firestore スキーマ設計

**スキーマ変更なし。** `is_sold_out` は [`PartnerMenu`](../../common/src/schemas/PartnerMenu.ts) と [`EventMenu`](../../common/src/schemas/EventMenu.ts) の双方に必須フィールドとして定義済み。本機能で変わるのは値の入り方のみ。

```
/partners/{partnerId}
  /menus/{menuId}              ... PartnerMenu.is_sold_out（売り切れの正本）

/communities/{communityId}
  /events/{eventId}
    /menus/{menuId}            ... EventMenu.is_sold_out（参加者が参照する複製）
```

### 5.2 スナップショット変換ロジックの変更

[`common/src/utils/eventMenuConverter.ts`](../../common/src/utils/eventMenuConverter.ts) の `convertFromPartnerMenuToEventMenu` から**売り切れによる除外を廃止**する。論理削除（`is_deleted`）と提供期間（`menu_date_start` / `menu_date_end`）による除外は現行どおり維持する。

```typescript
// 変更前: 売り切れメニューは EventMenu を生成しない
if (partnerMenu.is_sold_out) {
  return null
}

// 変更後: 上記ブロックを削除し、is_sold_out の値をそのままコピーする
return new EventMenu(eventId, partnerMenu.menu_id, {
  // ...
  is_sold_out: partnerMenu.is_sold_out, // true もそのまま反映される
  // ...
})
```

JSDoc の「売り切れの場合は null」という記述、および `convertPartnerMenusToEventMenus` の「売り切れのメニューは除外」という記述も併せて修正する。

### 5.3 Functions 設計

#### 5.3.1 Trigger Functions（新規）

`functions/default/src/eventMenusSoldOutSync.ts` を新規追加する。

```typescript
// functions/default/src/eventMenusSoldOutSync.ts
export const onPartnerMenuSoldOutChanged = onDocumentUpdated(
  {
    document: 'partners/{partnerId}/menus/{menuId}',
    region: 'asia-northeast1',
  },
  async (change) => {
    // 1. is_sold_out の変化がなければ何もしない
    // 2. partner_id 一致 / event_status.value === 'accepting_order' /
    //    event_deadline_datetime > now のイベントを store 経由で取得
    // 3. 各イベントの EventMenu（menu_id 一致）の is_sold_out を更新
  },
)
```

**設計上の要点**

- **差分検知**: `before.get('is_sold_out')` と `after.get('is_sold_out')` を比較し、変化した場合のみ処理する。価格・説明の変更では発火させない（承認後のスナップショット固定という現行方針を維持するため）
- **対象イベントの限定**: `accepting_order` かつ注文期限内のイベントのみ。`in_draft` / `applying_reservation` は承認時のスナップショットで最新化されるため対象外。終了済み・キャンセル済みイベントも対象外
- **対象 `EventMenu` が存在しない場合**: スキップしてログのみ記録する（主催者が承認前に店舗を変更した等）
- **invocation log**: [`onShopReservationChanged`](../../functions/default/src/eventMenusSnapshot.ts) と同様、v2 トリガーの取りこぼし検知のため冒頭で invocation ログを出力する（[07_リファクタリング/17_onDocumentWritten不具合.md](../07_リファクタリング/17_onDocumentWritten不具合.md)）
- **export**: [`functions/default/src/index.ts`](../../functions/default/src/index.ts) に import と export を追加する（漏れると development / production で未デプロイになる）

#### 5.3.2 Callable Functions（既存の変更）

| Function | ファイル | 追加する検証 |
| :-- | :-- | :-- |
| `addToCart` | [`functions/default/src/memberOrders.ts`](../../functions/default/src/memberOrders.ts) | 既存の `is_selected` 検証に `!is_sold_out` を追加 |
| `confirmOrder` | [`functions/default/src/memberOrders.ts`](../../functions/default/src/memberOrders.ts) | 確定対象注文の `menu_id` に対応する `EventMenu` が売り切れなら拒否 |
| `createStripeCheckoutSession` | [`functions/default/src/stripe.ts`](../../functions/default/src/stripe.ts) | 同上（決済開始前に拒否） |

いずれも `HttpsError('failed-precondition', '売り切れのメニューが含まれています')` を返す。

  // 取得した ShokujiiEvent の getMenus / saveMenu で EventMenu を更新する

`firestore.indexes.json` に以下の複合インデックスを追加する。

```json
{

  "queryScope": "COLLECTION_GROUP",
  "fields": [

    { "fieldPath": "event_status.value", "order": "ASCENDING" },
    { "fieldPath": "event_deadline_datetime", "order": "ASCENDING" }
  ]

```

### 5.5 Firestore セキュリティルール

**変更なし。**

- `EventMenu`（`communities/{community}/events/{event}/menus/{menuId}`）は `allow read: if true` のみで write ルール未定義のため、クライアントからの書き込みは不可。同期は Admin SDK 経由の Trigger で行うため現行ルールのままでよい
- `PartnerMenu`（`partners/{partner_id}/menus/{menu}`）の書き込みは `request.auth.uid == partner_id` に限定済み

### 5.6 処理フロー

#### 5.6.1 売り切れ切り替えの反映フロー

1. 飲食店が partner アプリのメニュー編集画面で売り切れスイッチを操作する
2. [`base/src/stores/partner.ts`](../../base/src/stores/partner.ts) の `updateMenu` が `PartnerMenu` を更新する
3. Trigger `onPartnerMenuSoldOutChanged` が発火する
4. `is_sold_out` に変化がなければ終了
5. 対象イベント（`partner_id` 一致 / `accepting_order` / 注文期限内）を store 経由で取得する
   - 0 件の場合はログを記録して終了
6. 各イベントの対象 `EventMenu` の `is_sold_out` を更新する
   - 個別イベントの更新に失敗しても他イベントの処理は継続する（`Promise.allSettled`）
   - 1 件でも失敗した場合は、失敗したイベント ID をログに記録したうえで**最後に例外を再 throw** し、Cloud Functions の自動リトライに乗せる
7. 参加者の画面では `subscribeMenus` の `onSnapshot` により自動で表示が更新される

#### 5.6.2 売り切れメニューの注文防止フロー

1. 参加者がイベントページで売り切れメニューを見る
   - カート追加ボタンは無効化され、理由が表示される
2. 画面表示前に売り切れになった等でカート追加が実行された場合、`addToCart` がトランザクション内で `EventMenu.is_sold_out` を検証し `failed-precondition` を返す
3. カートに残っている売り切れメニューを確定しようとした場合、`confirmOrder` または `createStripeCheckoutSession` が同様に拒否する
4. フロントエンドはエラーメッセージを表示し、カートから該当メニューを外すよう促す

### 5.7 データ整合性の保証

- `EventMenu` の更新は Trigger 内で行い、イベント単位でまとめて書き込む
- 売り切れ判定の最終的な正本はサーバー側の `EventMenu`。クライアント表示はあくまで購読結果であり、注文可否は必ずサーバーで再検証する
- Trigger が失敗した場合、`PartnerMenu` と `EventMenu` に一時的な乖離が生じる。この間はサーバー側検証も古い `EventMenu` を見るため注文を防げない。そのため失敗時は例外を再 throw して Cloud Functions の自動リトライに乗せる（§5.6.1 手順 6）
- 更新処理は `is_sold_out` の値をそのまま代入するだけであり冪等なため、リトライによる重複実行は安全

## 7. 注意事項

### 7.1 既存システムへの影響

#### 7.1.1 データ構造への影響

- スキーマ変更・マイグレーションは不要
- 売り切れ除外の廃止により、これまで生成されなかった売り切れメニューの `EventMenu` ドキュメントが新規に作られる。イベントあたりのドキュメント数がメニュー数ぶん増える可能性がある

#### 7.1.2 アプリケーションへの影響

- **予約申請バリデーション**: [`validateReservationRequest.ts`](../../common/src/utils/validateReservationRequest.ts) は `is_selected && !is_sold_out` で注文可能メニューを数えているため、除外廃止後も `NO_ORDERABLE_MENU_SELECTED` の判定は正しく機能する。ただし判定に使われる母集団が変わるため、[15_予約申請時のバリデーション_テスト項目.md](../02_主催者獲得と継続/15_予約申請時のバリデーション_テスト項目.md) の該当ケースを再確認する
- **メニュー画像のコピー**: `savePartnerMenusToEventMenus` は変換結果の `EventMenu` に対して画像をコピーするため、売り切れメニューの画像もコピー対象に加わる。コピー対象の増加と、[07_リファクタリング/16_EventMenu画像不具合.md](../07_リファクタリング/16_EventMenu画像不具合.md) で指摘されている除外条件の不整合への影響を確認する
- **主催者のメニュー選択**: 選択候補に売り切れメニューが並ぶため、既存イベントの `is_selected` の扱いに変化がないか確認する

#### 7.1.3 運用への影響

- **書き込み量**: 飲食店が売り切れを 1 回切り替えるたびに「対象イベント数」ぶんの書き込みが発生する。同一店舗が同時期に多数のイベントを受け付けている場合はまとめて更新されるが、通常運用の規模では問題にならない想定
- **反映遅延**: Firestore Trigger 経由のため数秒程度の遅延がある。即時反映ではない旨を飲食店向けの説明に含める

### 7.2 セキュリティ考慮事項

- `EventMenu` の書き込みは引き続き Admin SDK 経由のみ。`firestore.rules` の write ルールは追加しない
- 売り切れ検証をクライアント側だけに置かず、`addToCart` / `confirmOrder` / `createStripeCheckoutSession` の各サーバー処理で必ず検証する

### 7.3 実装前の確認事項

- `accepting_order` 中に主催者が店舗を変更できるか。変更できる場合、旧店舗の `PartnerMenu` 更新が誤って反映されないよう `partner_id` の一致判定で担保できているか
- 既存 Trigger（`onShopReservationChanged` 等）のリトライ設定に合わせるか。本 Trigger は冪等なため `retry: true` を有効にする方針とする
