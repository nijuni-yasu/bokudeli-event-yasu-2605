# 複数店舗・メニューリスト・業態

- **ステータス**: 仕様（未実装）
- **関連仕様書**: [02_オプションメニュー.md](./02_オプションメニュー.md) / [04_イートイン.md](./04_イートイン.md) / [05_テイクアウト.md](./05_テイクアウト.md) / [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) / [14_限定食数機能.md](./14_限定食数機能.md) / [00_仕様概要/01_仕様概要.md](../00_仕様概要/01_仕様概要.md)

飲食店DB検討資料の前半（メニュー → メニューリスト → 業態 → 店舗が業態を持つ）を、現行の `partners / shops / menus` に載せる。検討資料後半の `Stores`・独立 `Orders`・`MenuHistory`・店舗ごとのメニュー上書きは採用しない。

## 1. 概要

### 1.1 機能の目的

1 つのパートナーが複数店舗を持ち、メニューカタログはパートナーで共有する。店舗ごとに、デリバリー / テイクアウト / イートインを時間帯別の業態として設定する。

### 1.2 主要な機能

- メニューは `partners/{partnerId}/menus` のまま（店舗には紐づけない）
- メニューリストはメニュー ID の束。スケジュールは持たない
- 業態は店舗配下。曜日・時間帯・メニューリスト・注文条件を持つ
- 同一店舗で、同じ業態種別の時間帯が重なる設定は保存できない
- イベント承認時と注文確定時の 2 段で、メニューとオプションを固定する

### 1.3 対象ユーザー

- **飲食店（partner）**: メニュー、リスト、店舗、業態を設定する
- **主催者**: イベントに店舗と業態を選ぶ
- **参加者**: その業態のメニューを注文する

### 1.4 スコープ外

- 店舗ごとのメニュー価格上書き、共通メニューの `overrides`
- メニュー変更履歴（`MenuHistory`）
- 店舗直結の注文コレクション。注文は現行の `EventMemberOrder`
- 手数料 10% を店舗フィールドに固定する。課金は別仕様
- 請求書ダウンロード、店舗公開ページ、店舗アカウント作成、店舗主催イベント
- イートイン部屋の予約台帳と最低保証料金（[04_イートイン.md](./04_イートイン.md)）
- オーナー / 店長 / スタッフ権限（Phase 4）

## 2. ねらい

### 2.1 ビジネス目標

- チェーン店が店舗ごとに営業時間と提供メニューを分けられるようにする
- ランチとディナーで別メニューを出し、注文期限と最低注文金額を業態ごとに変えられるようにする

### 2.2 ユーザー価値

- 飲食店は「平日ランチのデリバリー」「土日ディナーのテイクアウト」を別設定にできる
- 主催者と参加者は、選んだ業態のメニューと条件だけを見る

### 2.3 成功指標（KPI）

- 業態の時間帯重複で保存できた件数: 0 件
- 承認後にマスタを変えても、確定済み注文のメニュー名・単価が変わらない

## 3. 前提条件

### 3.1 技術的前提条件

- 現行パスは `partners/{partnerId}/shops/{shopId}` と `partners/{partnerId}/menus/{menuId}`
- 認証は Auth UID = `partnerId`。Rules は partner 本人のみが shops / menus / options を書ける
- `partners` と `shops` と `menus` は現状 `allow read: if true`
- メニュー上限は [14_限定食数機能.md](./14_限定食数機能.md) の `limit_per_event`。`menu_max_count` は作らない
- 承認時スナップショットは `EventMenu`（`onShopReservationChanged`）。承認後の価格・説明はイベントに追従しない。売り切れだけ [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) の例外
- 注文時は `EventMemberOrder.menu_name` と `menu_price` をコピーする。`menu_price` は請求単価

### 3.2 ビジネス的前提条件

- メニューカタログはパートナー単位。店舗別価格が必要になるまで上書きは持たない
- 業態未設定の既存店舗は、現行の `shop_deadline_datetime` / `shop_range_min_orders` / `shop_time` でデリバリーを続ける
- 最小注文は金額（円）。個数下限は置かない
- 最大個数は 1 注文あたり。時間帯の総キャパシティは扱わない

### 3.3 依存関係

- [02_オプションメニュー.md](./02_オプションメニュー.md): Phase 1。リストと業態より先
- イベントは `partner_id` と `shop_id` を既に持つ。業態導入後は `service_format_id` を足す

## 4. 画面仕様

### 4.1 画面遷移

```
partner
  メニュー編集（02）
  メニューリスト一覧
    └─ リスト編集（名前、メニューの並び）
  店舗一覧
    └─ 店舗編集（現行の店舗項目）
         └─ 業態一覧
              └─ 業態編集（種別、曜日、時間、リスト、注文条件）
主催者
  イベント作成
    └─ 店舗を選ぶ
         └─ その店舗に業態があれば業態を選ぶ
              └─ 業態のメニューリストだけを候補にする
```

### 4.2 UI要素

#### 4.2.1 メニューリスト

- **リスト名**: 必須。1〜80 文字
- **メニュー**: 同一パートナーのメニューを 1〜100 件。表示順を保持する
- 空のリストは保存できない

#### 4.2.2 業態

- **名前**: 必須。1〜80 文字。例: 平日ランチ デリバリー
- **種別**: `delivery` / `takeout` / `eatin` のいずれか
- **曜日**: 1 つ以上。`0` 日曜 … `6` 土曜（現行 `day_of_week` と同じ）
- **時間**: 開始・終了の 1 枠。`HH:mm`。`24:00` は不可。終了は開始より後
- **メニューリスト**: 同一パートナーのリストを 1 つ
- **注文期限**:
  - デリバリー: 開催日の何日前の何時（現行 `shop_deadline_datetime` と同型）
  - テイクアウト / イートイン: 提供開始の何分前（1〜10080）
- **最小注文金額**: 任意。1 以上の整数円。未設定は下限なし
- **1 注文あたり最大個数**: 任意。1〜100。未設定は無制限
- デリバリーのみ:
  - **距離帯**: `{ range_km, min_order_amount }` を 0〜3 件。現行の個数帯は金額帯に読み替える（自動変換はしない。業態を手で作る）
  - **配達主体**: `shop`（店舗配達）。外部配達は将来の enum 追加まで置かない

#### 4.2.3 保存時の重複

同一店舗・同一 `type` で、曜日の積が空でなく、時間帯が重なる業態が既にあるときは保存しない。エラーは「同じ業態の時間帯が重なっています」。

#### 4.2.4 ボタン

- **保存**: バリデーション通過時のみ有効
- **削除**: その業態を参照する未終了イベントがあるときは削除できない

## 5. 技術仕様・データ構造設計

### 5.1 Firestoreスキーマ設計

#### 5.1.1 コレクション構造

現行ツリーに次を足す。`options` は Rules 上既存。スキーマは [02](./02_オプションメニュー.md)。

```
/partners/{partnerId}
  /menus/{menuId}                         現行。Phase 1 でフィールド追加（02）
  /options/{optionId}                     Phase 1（02）
  /menu_lists/{menuListId}                Phase 2。自動 ID
  /shops/{shopId}                         現行。Phase 2 で shop_emails
    /service_formats/{serviceFormatId}    Phase 2。自動 ID
    /rooms/{roomId}                       未採用。04 の将来項目

/communities/{communityId}/events/{eventId}
  service_format_id                       Phase 2 で追加（業態がある店舗のイベントのみ）
  /menus/{menuId}                         現行 EventMenu。承認時にオプション定義をコピー（02）
```

メニューリストとオプションはパートナー配下。業態は店舗配下。業態をパートナー配下に置くと、別店舗が同じ配達条件を共有してしまう。

振込先・オーナー住所・営業許可証は、公開読み取りの partner 文書に置かない。Phase 4 の非公開サブドキュメントで扱う（§6）。

#### 5.1.2 ドキュメントスキーマ

新規サブコレクションの時刻は `created_at` / `updated_at`（Timestamp）。既存の `PartnerMenu.updatedAt` と `PartnerShop.createdAt` / `updatedAt` は改名しない。

```typescript
interface PartnerMenuList {
  menu_list_id: string
  partner_id: string
  menu_list_name: string          // 必須、1〜80
  menu_ids: string[]              // 必須、1〜100。同一 partner の menu。順を保持
  created_at: Timestamp
  updated_at: Timestamp
}

interface PartnerServiceFormat {
  service_format_id: string
  partner_id: string
  shop_id: string
  name: string                    // 必須、1〜80
  service_format: 'delivery' | 'takeout' | 'eatin'
  weekdays: number[]              // 必須、1〜7。0〜6 の重複なし
  time_start: string              // 必須、HH:mm
  time_end: string                // 必須、HH:mm。time_start より後
  menu_list_id: string            // 必須。同一 partner
  order_deadline:
    | { kind: 'days_before'; days_before: number; time: string }  // delivery。days_before は 0〜14。time は HH:mm
    | { kind: 'minutes_before'; minutes_before: number }           // takeout | eatin。1〜10080
  min_order_amount?: number       // 任意、1 以上の整数
  max_quantity_per_order?: number // 任意、1〜100
  range_bands?: { range_km: number; min_order_amount: number }[]  // delivery のみ、0〜3
  delivery_provider?: 'shop'      // delivery のみ
  created_at: Timestamp
  updated_at: Timestamp
}
```

`PartnerShop` への追加（Phase 2）:

| フィールド | 型 | 制約 |
| :-- | :-- | :-- |
| `shop_emails` | `string[]` | 任意。1〜5。メール形式。重複なし。現行の `shop_email` と `shop_email_sub1`〜`sub3` を読み取り時にこの配列へ畳む。書き込みは配列のみ |

`Event` への追加（Phase 2）:

| フィールド | 型 | 制約 |
| :-- | :-- | :-- |
| `service_format_id` | `string` | その店舗に業態が 1 件以上あるとき必須。なければフィールドなし。現行イベントは空のまま |

`partners/{partnerId}` 直下への追加は Phase 4 まで行わない。インボイス番号は現行の `shop_invoice_number` を維持する。

#### 5.1.3 既存フィールドとの対応

| 現行 | 業態導入後 |
| :-- | :-- |
| `shop_time`（7 曜日 × 2 枠） | 業態の `weekdays` + 1 枠。2 枠目は自動では業態に分けない |
| `shop_deadline_datetime` | デリバリー業態の `order_deadline.kind = days_before` |
| `shop_range_min_orders`（距離 → 最小個数） | デリバリー業態の `range_bands`（距離 → 最小金額）。個数からの金額換算はしない |
| `min_orders_on_spot` | 使わない。イートインの最低保証は 04 の将来項目 |
| `limit_per_event` | 維持。業態の `max_quantity_per_order` とは別（イベント総数と、1 注文の個数） |

### 5.2 処理フロー

1. パートナーがメニューを作る（02 のオプション・アレルギー・バッジを含む）
2. メニューリストを作り、メニュー ID を順に保存する
3. 店舗を開き、業態を保存する。サーバー側（Callable）で同一店舗の既存業態と時間帯重複を調べ、重なれば `failed-precondition` で拒否する
4. 主催者がイベントに `shop_id` を選ぶ。業態があれば `service_format_id` も必須
5. 店舗承認で `accepting_order` になったとき、そのリストのメニューだけを `EventMenu` にコピーする。オプション定義もコピーする（02）
6. 注文確定時、`EventMemberOrder.menu_price` にオプション加減後の単価を書く（02）

業態が無い店舗のイベントは、手順 5 を現行どおり全パートナーメニュー（選択済み）のコピーにする。

### 5.3 Firestoreセキュリティルール

- `menu_lists` と `shops/{shopId}/service_formats` は、現行 shops と同様に誰でも読める
- 書き込みは `request.auth.uid == partnerId` または `isSupport()`（shops と同じ）
- 業態の重複禁止は Rules では完結しない。保存は Callable のみとし、クライアントからの直接 create/update は Phase 2 で閉じる
- 振込先・オーナー個人住所は公開文書に追加しない

### 5.4 インデックス

業態の重複検査は、店舗の `service_formats` を全件読んでメモリで判定する。1 店舗の業態数は上限 30。複合インデックスは不要。

メニューリストの `menu_ids` は `array-contains` で引かない。イベントは `service_format_id` からリストを 1 件読む。

### 5.5 Functions設計

| 名前 | 種別 | 役割 |
| :-- | :-- | :-- |
| `upsertServiceFormat` | Callable | 業態の作成・更新。重複検査、リストと店舗の所属検査、期限種別と `service_format` の組み合わせ検査 |
| `deleteServiceFormat` | Callable | 未終了イベントからの参照が無いときだけ削除 |
| 既存の承認トリガー | Trigger | `service_format_id` があるイベントは、そのリストのメニューだけをスナップショットする |

メニューリストの保存は、件数が小さく参照検査が partner 内で閉じるため、partner クライアントから直接書いてよい。存在しない `menu_id` は保存時にクライアントが弾き、承認トリガーは欠落 ID をスキップして `reportClientError` する。

### 5.6 データ整合性

- リストの `menu_ids`、業態の `menu_list_id` は同一 `partner_id`
- デリバリー以外に `range_bands` と `delivery_provider` を付けない
- テイクアウトとイートインの `order_deadline.kind` は `minutes_before` のみ
- 時間の重なりは半開区間 `[time_start, time_end)`。端が同じ時刻だけ接する場合は重なりとみなさない

## 6. 実装優先度

### Phase 1

[02_オプションメニュー.md](./02_オプションメニュー.md)。注文の表示・メール・集計は同書 §4.3。リストと業態はまだ使わない。

### Phase 2

メニューリスト、業態、`shop_emails`、イベントの `service_format_id`、承認時にリストでメニューを絞る。既存店舗の営業時間・締切・距離帯は残し、業態を作った店舗の新規イベントから業態必須にする。

### Phase 3

複数店舗の画面（店舗の追加・切り替え）。パス `shops` は現行のまま。1 パートナー 1 店舗の運用は崩さない。

### Phase 4

`partners/{partnerId}/members/{uid}` に `role: owner | manager | staff`。

| ロール | できること |
| :-- | :-- |
| owner | メンバー、店舗の作成と削除、非公開の請求情報 |
| manager | メニュー、リスト、業態、営業設定。振込先は不可 |
| staff | 売り切れと当日の注文確認。マスタ変更は不可 |

請求情報は `partners/{partnerId}/private/billing`（単一ドキュメント）。読めるのは owner と `isSupport()` のみ。フィールドは振込先（銀行名・支店・種別・口座番号・名義）と営業許可証の Storage パス。オーナー自宅住所は置かない。

現行の「UID = partnerId」は owner が 1 人のときの互換として残す。members が空なら今どおり本人だけが書く。

### Phase 5

イートインの部屋。予約台帳と最低保証の請求先が決まってから（04）。

## 7. 注意事項

- 検討資料後半（共通メニューの上書き、`Users.associatedStores`、汎用 `Orders`、`MenuHistory`）は、イベント注文と現行の参加者 `/users` と衝突するため採用しない
- `shop_emails` 導入時、メール送信は配列を優先し、空なら現行 4 フィールドにフォールバックする
- 業態の 2 枠営業（`time_start2`）は採用しない。分割シフトは業態を 2 件作る
- 削除済みメニューがリストに残っていても、承認スナップショットは `is_deleted` を除外する
- 手数料、請求書 PDF、店舗ページ、店舗主催は本書のフィールドにしない
