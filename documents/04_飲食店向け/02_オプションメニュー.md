- **ステータス**: Phase 1 実装済み。メニューリストと業態は Phase 2

コレクションの置き場所と実装順の正本は [03](./03_複数店舗・複数メニューリスト.md)。本書はオプションと注文時の金額固定を定義する。

## 1. 概要

### 1.1 機能の目的

メニューに選択肢（サイズ、トッピング）を付け、選んだ結果の単価を注文に固定する。

### 1.2 主要な機能

- オプションはパートナー配下のマスタ。メニューは ID の並びで参照する
- 選択は「単一 / 複数」と「必須 / 任意」
- 各項目は金額差分（`price_delta`）。メニュー本体価格との合計が 1 円未満になる組み合わせは保存も注文もできない
- 承認時にオプション定義を `EventMenu` へコピーし、注文時に選択結果と確定単価を `EventMemberOrder` へ書く

### 1.3 対象ユーザー

- **飲食店**: オプションを編集し、注文一覧とお名前シートで選択内容を見る
- **参加者**: カートで選択肢を選び、注文履歴・キャンセル・イベントページで選択内容を見る
- **主催者**: 参加者の注文一覧と CSV で選択内容を見る
- **運営**: 注文一覧で選択内容を見る

### 1.4 スコープ外

- オプション同士の依存（「大盛のときだけチーズ」）
- オプション項目ごとの在庫・売り切れ
- アレルギー、ヴィーガン、ハラル、表示バッジ
- メニュー変更履歴

## 2. ねらい

### 2.1 ビジネス目標

- サイズやトッピングを別メニューに分裂させずに販売できる
- マスタ変更後も、確定済み注文の単価と選択内容が残る

### 2.2 ユーザー価値

- 飲食店は「大盛 +100 円」を複数メニューで使い回せる
- 参加者は必須の取りこぼしを確認できる

### 2.3 成功指標（KPI）

- 確定注文の `menu_price` が、当時の本体価格 + 選択 `price_delta` と一致する
- オプション付き食事の確定単価は1円以上。「注文なしで参加」の本体0円・合計0円は例外とする

## 3. 前提条件

### 3.1 技術的前提条件

- オプションは `partners/{partnerId}/options/{optionId}` に保存し、共通 Zod スキーマで検証する
- `PartnerMenu.option_ids` で同一店舗のオプションを参照する
- `EventMemberOrder` は1ドキュメント1食。`menu_price` は請求単価（食事は正の整数、注文なし参加は0）
- 承認後、価格と説明は `EventMenu` に固定される（[13](./13_売り切れ機能のリアルタイム化.md)）

### 3.2 ビジネス的前提条件

- オプションの `price_delta` は、そのオプションを参照する全メニューで共通。メニューごとに差額を変える要件は、オプションを分ける

### 3.3 依存関係

- メニューリストと業態（[03](./03_複数店舗・複数メニューリスト.md)）が無くても、Phase 1 は全メニューを現行どおりイベントへコピーできる
- 限定食数（[14](./14_限定食数機能.md)）はメニュー単位のまま。オプションでは食数を分けない

## 4. 画面仕様

### 4.1 画面遷移

```
partner
  オプション設定
    └─ オプション編集
  メニュー設定
    └─ 設定するオプション（並び）
参加者 カート
  メニューごとにオプションを選んで追加
```

### 4.2 UI要素

#### 4.2.1 オプション編集

- **名前**: 必須。1〜40 文字。例: サイズ
- **説明**: 任意。0〜200 文字
- **選択**: `single` または `multiple`
- **必須**: boolean。単一必須は `single` + 必須。単一任意は `single` + 任意。複数任意は `multiple` + 任意。複数必須（1 つ以上）は `multiple` + 必須
- **項目**: 1〜20。名前 1〜40 文字。`price_delta` は整数、-10000〜10000。0 可。マイナスは値引き
- 項目名の重複は不可
- 一覧の上に、オプションメニューの選択肢を作り、メニュー編集の「設定するオプション」で各メニューに付ける旨を示す
- 編集画面では、選択方法（単一は 1 つ、複数は同時にいくつか）と必須（オンは未選択だと注文できない）を補足する

#### 4.2.2 メニュー編集

- **オプション**: 0〜10 件。同一パートナーの ID。表示順を保持
- 保存時、選べる組み合わせの最小合計が 1 円未満のメニューは保存できない。最小合計は `menu_price` に次を足した値
  - `single` かつ必須: 項目の `price_delta` の最小
  - `single` かつ任意: 0 と、項目の `price_delta` の最小のうち小さい方
  - `multiple`: 負の `price_delta` の合計（正の項目は選ばなくてよい。負の項目は全部選べる）

#### 4.2.3 カート追加モーダル

- 必須オプションが未選択のときはカートに入れない
- `single` は 0 または 1（必須なら 1）。`multiple` は項目の部分集合（必須なら 1 つ以上）
- 任意の `single` は未選択で開始し、「選ばない」の選択肢は出さない。項目を選択中のときだけ見出し右側に「選択を解除」を表示する。解除はそのオプションのみを未選択に戻し、小計にも反映する。必須や `multiple` には解除ボタンを出さない
- 既存テーマと Vuetify 標準のラジオボタン・チェックボックスを使う。各オプションに必須／任意を表示し、選択方法の案内文は表示しない。項目名は左、差額は右に揃える。差額は `+¥100`、`¥0`、`-¥100` の形式で表示する
- 写真とメニュー名は従来どおり大きく表示し、メニュー名は太字にする。メニュー名の直下に本体価格（イベントメニューの `menu_price`）を `¥1,200` の形式で表示する。写真・タイトル・価格・説明・オプションの左端を揃える。選択後の金額内訳は表示しない
- オプションの見出しは太字にし、各見出しの上を罫線で区切る
- 下部に個数、小計の金額、閉じる／カートに追加ボタンをまとめ、選択欄がスクロールしても操作できるようにする。小計は（本体 + 選択中の差額合計）× 個数で、「食事小計」の文言は付けない。必須未選択などで選択が無効な間は金額を「—」とする

### 4.3 選択内容の表示

注文 1 件の表示名は、メニュー名のあとに選択した項目名を付ける。項目が無い注文はメニュー名だけにする。

```
チーズバーガー（大盛、チーズ）
```

- 項目は `selected_options` の並び順。`price_delta` が 0 でも項目名は出す
- 保存順は、イベントにコピーされたオプション定義の順。同一オプション内は項目定義の順で、選んだものだけを並べる。まとめキーのソートはキー計算だけに使い、保存配列は並べ替えない
- カート、注文履歴、キャンセルでは、選択があるとき括弧つきの表示名は出さず、名前と金額の行だけを出す。名前は左、金額は右に揃える。行を足すとメニュー金額になる。カートの行は本文サイズ。注文履歴の行は、同じカードの【注文内容】などと同じ大きさ
- 注文履歴とキャンセルの内訳は 1 食あたりで、自己負担額・返金額とは別
  - 1 行目はメニュー名と本体価格。これら 3 画面の本体価格は `menu_price` から `selected_options` の `price_delta` 合計を引いた額
  - 続く行は項目名と、その項目の `price_delta`。差額 0 も ¥0 と出す。並びは `selected_options` の順
  - カートでは、選択が無いとき内訳を出さない
  - 注文履歴では、選択が無い行もメニュー名と `menu_price` を 1 行で出す。`selected_options` が無い過去注文も同じ
  - 個数が 2 以上のまとめ行は「1食あたり」と付ける。キャンセルは 1 注文 1 行なので付けない
- カート追加モーダルの選択 UI と金額表示は §4.2.3 に従う
- 上記 3 画面とカート追加モーダル以外の金額は、オプション込みの `menu_price` のまま。項目ごとの差額は再表示しない
- `selected_options` が無い過去注文は、注文履歴以外ではメニュー名だけの現行表示のまま

同じメニューでも選択が違う注文は別行である。`menu_id` だけで 1 行にまとめる処理は、まとめキーを「`menu_id` + 選択した `option_id` と `item_id` の組 + `menu_price`」に変える。単価が違う行を先勝ちの単価で件数だけ増やすのは不可。

## 5. 技術仕様・データ構造設計

### 5.1 Firestoreスキーマ設計

```typescript
interface PartnerOptionItem {
  item_id: string                 // オプション内で一意。自動 ID
  name: string                    // 1〜40
  price_delta: number             // 整数、-10000〜10000。マイナスは値引き
}

interface PartnerOption {
  option_id: string               // ドキュメント ID と同じ。フィールドは持たない
  partner_id: string
  option_name: string
  option_description?: string     // 0〜200
  selection: 'single' | 'multiple'
  required: boolean
  option_items: PartnerOptionItem[]  // 1〜20
  created_at: Timestamp
  updated_at: Timestamp
}
```

`PartnerMenu` への追加。既存フィールドは維持する。`limit_per_event` は [14](./14_限定食数機能.md) のまま。

| フィールド | 型 | 制約 |
| :-- | :-- | :-- |
| `option_ids` | `string[]` | 任意、0〜10。順を保持。同一 partner |

`EventMenu` への追加（承認時コピー）:

| フィールド | 型 | 説明 |
| :-- | :-- | :-- |
| `options` | オプション定義の配列 | 当時の名前、selection、required、items。ID も残す |

`EventMemberOrder` への追加:

| フィールド | 型 | 説明 |
| :-- | :-- | :-- |
| `selected_options` | `{ option_id, option_name, item_id, item_name, price_delta }[]` | 未選択なら空配列またはフィールドなし |
| `menu_price` | number | 現行どおり請求単価。オプション込みの確定額。過去注文（フィールドなし）は本体価格のまま。主催者負担と企業補助の基準もこの額。本体価格用の別フィールドは置かない |

### 5.2 処理フロー

1. 飲食店がオプションを保存する
2. メニューに `option_ids` を付けて保存する。合計が 1 円未満になる組み合わせがあれば拒否する
3. 承認トリガーが `EventMenu.options` に定義をコピーする。§4.2.2 の最小合計が 1 円未満のメニューはコピーしない（期間外メニューと同じ）。`reportClientError` に残す。ステータスはすでに `accepting_order` なので、ここで承認は取り消さない
4. 参加者がカートで選択する。Callable `addToCart` が、イベントにコピーされた定義に対して必須・単複・項目 ID を検証する
5. `menu_price` に本体 + 差分合計を書き、`selected_options` を定義順で書く。主催者負担・企業補助はこの `menu_price` を基準に、現行の式のまま計算する（全額負担はその額、割引と定額補助は額と `menu_price` の小さい方、割合補助は `menu_price` に対する割合）
6. 承認後にマスタのオプションを変えても、そのイベントの `EventMenu.options` と確定注文は変えない

### 5.3 Firestoreセキュリティルール

- `partners/{partnerId}/options` と `menus` の read は公開のまま。クライアントの create / update / delete は、店舗本人も含めて禁止する。
- 保存・削除・並び替えは以下の Callable に集約する。認証 UID を保存先 partner とし、入力から店舗 ID を受け取らない。
- `common/src/apis/partnerMenu.ts` で項目の型・件数・文字数・差額範囲・ID/名前の重複を検証する。メニュー保存時は同一店舗配下の参照先実在と最小合計金額をサーバーで検証する。

### 5.4 Functions設計

店舗操作用 Callable は `savePartnerMenu` / `savePartnerOption` / `deletePartnerOption` / `deletePartnerMenu` / `sortPartnerMenus`。入力不正は `invalid-argument`、参照先欠落は `failed-precondition` で拒否する。全操作は converter 付き store を経由する。

- メニュー保存・オプション編集・削除はトランザクションで検証と更新を一体化する。オプション編集では実際の参照メニューを再検証し、古い編集画面から削除済みオプションを再作成できないよう新規作成と編集を区別する。
- オプション削除は、Firestore から参照メニューを検索し、各メニューの最新 `option_ids` から対象を除去して本体削除と同時に確定する。途中失敗やトランザクション上限超過時は全体を失敗させる。メニュー保存も参照先を同一トランザクションで読むため、削除との競合時に無効な参照を残さない。
- 削除後の最小合計が1円未満になる場合は削除を拒否し、メニュー価格・残りのオプションを先に変更するよう案内する。承認済み `EventMenu` と注文スナップショットは変更しない。
- メニュー削除は従来の論理削除。並び替えは最新ドキュメントに並び順を反映する。

既存の承認トリガーと `addToCart` / 注文確定処理も検証する。`addToCart` は次を満たさない入力を `invalid-argument` で拒否する。

- 必須オプションが欠けている、または `single` で2件以上
- `item_id` が `EventMenu.options` に無い
- 確定 `menu_price` が1未満、またはクライアント提示額とサーバー計算が不一致。ただし「注文なしで参加」の本体0円・合計0円は許可する

`user_advance` は支払合計が正なら Stripe Checkout、0円なら `confirmOrder` に進む。サーバーで注文を読み直して支払合計0円を確認し、有料注文の混在を拒否する。通常の締切・定員・売り切れ・限定数・注文状態の検査と確定後処理は維持し、Stripe 決済記録は作らない。0円注文のキャンセルは既存の返金不要判定を使う。

### 5.5 データ整合性

- `option_id` はドキュメント ID のみ。中に重複フィールドを持たない
- 負の `price_delta` は許す。オプション付き食事の確定単価が1未満は許さない

### 5.6 表示と集計の共通関数

選択の表示名と、まとめキーは `common` に 1 つずつ置く。画面・メール・PDF・Stripe・請求書はそれを使う。各画面で文字列を組み立てない。

まとめキーは次を連結する。

1. `menu_id`
2. `selected_options` を `option_id` それから `item_id` でソートした組
3. `menu_price`

`selected_options` が無い注文と、空配列の注文は同じキー（`menu_id` と `menu_price`）にする。単価が違う行は分けたままにする。

Stripe に送る商品名だけは Unicode コードポイントで250文字以内にする。超える場合は先頭249文字 + `…` とし、注文の完全な名前・選択内容・集約キーは保持する。

Stripe の明細キーは、このキーに自己負担単価を足す（§4.3.3）。自己負担単価を落とすと、同じメニュー・同じオプションでも補助残額が違う注文が 1 行にまとまる。
