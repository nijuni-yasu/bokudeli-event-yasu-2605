# オプションメニュー

- **ステータス**: 仕様（未実装）。飲食店データモデルの Phase 1
- **関連仕様書**: [03_複数店舗・複数メニューリスト.md](./03_複数店舗・複数メニューリスト.md) / [13_売り切れ機能のリアルタイム化.md](./13_売り切れ機能のリアルタイム化.md) / [14_限定食数機能.md](./14_限定食数機能.md)

コレクションの置き場所と実装順の正本は [03](./03_複数店舗・複数メニューリスト.md)。本書はオプション、アレルギー、表示バッジ、注文時の金額固定を定義する。

## 1. 概要

### 1.1 機能の目的

メニューに選択肢（サイズ、トッピング）を付け、選んだ結果の単価を注文に固定する。アレルギーと食事区分は表示専用で、注文の可否には使わない。

### 1.2 主要な機能

- オプションはパートナー配下のマスタ。メニューは ID の並びで参照する
- 選択は「単一 / 複数」と「必須 / 任意」
- 各項目は金額差分（`price_delta`）。メニュー本体価格との合計が 1 円未満になる組み合わせは保存も注文もできない
- 特定原材料 8 品目、ヴィーガン、ハラル、バッジ（おすすめ / 新メニュー / 期間限定）をメニューに持てる
- 承認時にオプション定義を `EventMenu` へコピーし、注文時に選択結果と確定単価を `EventMemberOrder` へ書く

### 1.3 対象ユーザー

- **飲食店**: オプションとメニュー属性を編集する
- **参加者**: カートで選択肢を選び、アレルギー表示を読む

### 1.4 スコープ外

- オプション同士の依存（「大盛のときだけチーズ」）
- オプション項目ごとの在庫・売り切れ
- アレルギーによる注文ブロック、ハラル認証の審査
- メニュー変更履歴
- 推奨 20 品目（特定原材料に準ずるもの）。Phase 1 は 8 品目のみ

## 2. ねらい

### 2.1 ビジネス目標

- サイズやトッピングを別メニューに分裂させずに販売できる
- マスタ変更後も、確定済み注文の単価と選択内容が残る

### 2.2 ユーザー価値

- 飲食店は「大盛 +100 円」を複数メニューで使い回せる
- 参加者は必須の取りこぼしと、表示上のアレルギーを確認できる

### 2.3 成功指標（KPI）

- 確定注文の `menu_price` が、当時の本体価格 + 選択 `price_delta` と一致する
- 合計 0 円以下の注文が 0 件

## 3. 前提条件

### 3.1 技術的前提条件

- パス `partners/{partnerId}/options/{optionId}` は Rules にある。Zod スキーマは未実装
- `PartnerMenu` にオプション参照は無い
- `EventMemberOrder` は 1 ドキュメント 1 食。`menu_price` は請求単価（正の整数）
- 承認後、価格と説明は `EventMenu` に固定される（[13](./13_売り切れ機能のリアルタイム化.md)）

### 3.2 ビジネス的前提条件

- オプションの `price_delta` は、そのオプションを参照する全メニューで共通。メニューごとに差額を変える要件は、オプションを分ける
- アレルギーとバッジは表示のみ

### 3.3 依存関係

- メニューリストと業態（[03](./03_複数店舗・複数メニューリスト.md)）が無くても、Phase 1 は全メニューを現行どおりイベントへコピーできる
- 限定食数（[14](./14_限定食数機能.md)）はメニュー単位のまま。オプションでは食数を分けない

## 4. 画面仕様

### 4.1 画面遷移

```
partner メニュー管理
  オプション一覧
    └─ オプション編集
  メニュー編集
    └─ 付けるオプション（並び）
    └─ アレルギー、ヴィーガン、ハラル、バッジ
参加者 カート
  メニューごとにオプションを選んで追加
イベントページ
  アレルギー・バッジをメニューカードに表示
```

### 4.2 UI要素

#### 4.2.1 オプション編集

- **名前**: 必須。1〜40 文字。例: サイズ
- **説明**: 任意。0〜200 文字
- **選択**: `single` または `multiple`
- **必須**: boolean。単一必須は `single` + 必須。単一任意は `single` + 任意。複数任意は `multiple` + 任意。複数必須（1 つ以上）は `multiple` + 必須
- **項目**: 1〜20。名前 1〜40 文字。`price_delta` は整数、-100000〜100000。0 可
- 項目名の重複は不可

#### 4.2.2 メニュー編集

- **オプション**: 0〜10 件。同一パートナーの ID。表示順を保持
- **アレルギー**: 次のゼロ個以上。`ebi` `kani` `kurumi` `komugi` `soba` `tamago` `milk` `peanuts`（えび、かに、くるみ、小麦、そば、卵、乳、落花生）
- **ヴィーガン / ハラル**: 各 boolean。未設定は false
- **バッジ**: `recommended`（おすすめ）/ `new`（新メニュー）/ `limited`（期間限定）のゼロ個以上
- 保存時、付いているオプションのどの項目を選んでも `menu_price + 選んだ price_delta の合計 >= 1` になること。崩れる組み合わせがあるメニューは保存できない

#### 4.2.3 カート

- 必須オプションが未選択のときはカートに入れない
- `single` は 0 または 1（必須なら 1）。`multiple` は項目の部分集合（必須なら 1 つ以上）
- 表示単価は本体 + 選択中の差分合計

## 5. 技術仕様・データ構造設計

### 5.1 Firestoreスキーマ設計

```typescript
interface PartnerOptionItem {
  item_id: string                 // オプション内で一意。自動 ID
  name: string                    // 1〜40
  price_delta: number             // 整数、-100000〜100000
}

interface PartnerOption {
  option_id: string               // ドキュメント ID と同じ。フィールドは持たない
  partner_id: string
  option_name: string
  option_description?: string     // 0〜200
  selection: 'single' | 'multiple'
  required: boolean
  option_items: PartnerOptionItem[]  // 1〜20
  created_at: Timestamp
  updated_at: Timestamp
}
```

`PartnerMenu` への追加。既存フィールドは維持する。`limit_per_event` は [14](./14_限定食数機能.md) のまま。

| フィールド | 型 | 制約 |
| :-- | :-- | :-- |
| `option_ids` | `string[]` | 任意、0〜10。順を保持。同一 partner |
| `allergens` | enum[] | 任意。上記 8 値。重複なし |
| `is_vegan` | boolean | 任意。無ければ false |
| `is_halal` | boolean | 任意。無ければ false |
| `badges` | enum[] | 任意。`recommended` / `new` / `limited` |

`EventMenu` への追加（承認時コピー）:

| フィールド | 型 | 説明 |
| :-- | :-- | :-- |
| `options` | オプション定義の配列 | 当時の名前、selection、required、items。ID も残す |
| `allergens` / `is_vegan` / `is_halal` / `badges` | メニューと同じ | 承認時点の表示用 |

`EventMemberOrder` への追加:

| フィールド | 型 | 説明 |
| :-- | :-- | :-- |
| `selected_options` | `{ option_id, option_name, item_id, item_name, price_delta }[]` | 未選択なら空配列またはフィールドなし |
| `menu_price` | number | 現行どおり請求単価。オプション込みの確定額。過去注文（フィールドなし）は本体価格のまま |

### 5.2 処理フロー

1. 飲食店がオプションを保存する
2. メニューに `option_ids` を付けて保存する。合計が 1 円未満になる組み合わせがあれば拒否する
3. 承認トリガーが `EventMenu.options` に定義をコピーする
4. 参加者がカートで選択する。Callable `addToCart` が、イベントにコピーされた定義に対して必須・単複・項目 ID を検証する
5. `menu_price` に本体 + 差分合計を書き、`selected_options` に内訳を書く
6. 承認後にマスタのオプションを変えても、そのイベントの `EventMenu.options` と確定注文は変えない

### 5.3 Firestoreセキュリティルール

- `options` の read は現行どおり公開。write は `request.auth.uid == partnerId`
- メニューの新フィールドも、menus の現行 write 条件のまま。配列長と enum は Rules で上限を見る
- 金額の組み合わせ検査はクライアントの Zod と、`addToCart` のサーバー検証の両方で行う。Rules だけでは全組み合わせを見ない

### 5.4 Functions設計

新規 Callable は作らない。オプションとメニューの保存はクライアント直書き（現行メニューと同じ）。

変更するのは既存の承認トリガーと `addToCart` / 注文確定処理。`addToCart` は次を満たさない入力を `invalid-argument` で拒否する。

- 必須オプションが欠けている、または `single` で 2 件以上
- `item_id` が `EventMenu.options` に無い
- 確定 `menu_price` が 1 未満、またはクライアント提示額とサーバー計算が不一致

### 5.5 データ整合性

- `option_id` はドキュメント ID のみ。中に重複フィールドを持たない
- 負の `price_delta` は許す。確定単価が 1 未満は許さない
- アレルギーの自由文字列は許さない
