# 友人一覧機能（たべとも一覧）

> **関連仕様**: イベントへの招待（注文完了モーダル・メール送信）は [02_友人招待機能.md](./02_友人招待機能.md) を参照する。  
> **テンプレート**: 本仕様の構成は [02_仕様書追加ルールとテンプレート.md](../00_仕様概要/02_仕様書追加ルールとテンプレート.md) に準拠する。

## 1. 概要

### 1.1 機能の目的

食事会（イベント）に**同席した履歴**に基づき「たべとも」を把握し、**マイページ**で振り返りやすくする。

### 1.2 主要な機能

- マイページに「**たべとも**」タブを設け、**友人（同席者）**を一覧表示する
- 同席回数・初回・最終の会合日（イベント基準日時）を表示する
- 同席者関係のデータを Firestore 上に持ち、**リリース時バッチ**と**注文（参加）確定時の双方向更新**で整備する（**総浚いは行わない**）

### 1.3 対象ユーザー

- 本サービスにログインし、**イベントに参加（注文）**する一般ユーザー

### 1.4 用語・名称

- **友人（たべとも）**: 同一イベントに**参加が確定した**相手。一度同席で関係が成立。画面・コピーでは推奨名称「**たべとも**」を用いる（食事＋友だちの含意）

## 2. ねらい

### 2.1 ビジネス目標

- **リピート参加・紹介**につながる「関係の可視化」で、プロダクトの体験価値を高める
- 参加者同士の**つながり**を土台に、関連機能（例: 友人招待）の利用機会を生む

### 2.2 ユーザー価値

- 「**いつ・どの食事会で一緒だったか**」を思い出しやすくする
- 同席回数を通じた**関係の深まり**を感じられ、再参加の動機付けに寄与する

### 2.3 成功指標（KPI）

- マイページ「たべとも」タブの**閲覧数・閲覧率**
- **たべとも**として登録された**関係の件数**の推移
- 同一ユーザーあたりの**平均同席者数**（指標化する場合は計測定義を合わせる）

## 3. 前提条件

### 3.1 技術的前提条件

- **クライアント**: `user` アプリ（Vue 3 + Vite + Vuetify 3、パス `/user/`）
- **バックエンド**: Firebase Functions `functions/default`（TypeScript）
- **データストア**: Cloud Firestore。友人データは `users` の**サブコレクション**として保持
- イベント・注文（参加確定）のデータが既存どおり存在し、**参加確定**の判定ができること
- Firestore フィールド命名は**プロジェクト規約**に従う（`common` では **snake_case** ・ `created_at` / `updated_at` 等。詳細は [3.4 フィールド命名と Db/App の扱い](#34-フィールド命名と-dbapp-の扱い)）

### 3.2 ビジネス的前提条件

- 「一緒にいた」の根拠は、**当該イベントへの参加（注文）が確定した**こと（`order.status === 'ordered'`）に基づく
- 友人成立タイミングは**注文確定時**（イベント終了を待たない）。`event_at` には **`events/{event_id}.event_start_datetime`（イベント開始日時）**を格納する
- **総浚い**（注文のたびに二人の**過去全イベント**を再探索する）**は採用しない**
- **デノーマライズ（コピー）方針は採らない**: 相手の `user_name` / `user_image_url` などの**プロフィール情報を `friends` ドキュメントへコピー保持しない**。表示に必要な相手情報は**表示時に `users` を解決**して返す。  
  - 理由: 今後 `users` 側に**タグ**・**SNS リンク**・自己紹介など**追加プロフィール項目**を表示する可能性があり、その都度 `friends` 側のスキーマ追加と**伝播トリガー**を増やすコストを避ける。**`users` を真とする一元化**で、新項目追加時はクライアント取得側のみの対応で済む構造を維持する

### 3.3 依存関係

- [02_友人招待機能.md](./02_友人招待機能.md): 招待候補の取得等は、本仕様の友人データ・`GET` 方針に従う。**Callable は本仕様の `getUserFriends` を流用**することを基本とし、招待モーダルでの絞り込み（検索 q、人数の上限を緩める等）が必要になった段階で**派生 Callable**を追加検討する（R-8）
- 注文・イベントのドキュメント・ステータス（例: `ordered`）: 同席者一覧の解決元

### 3.4 フィールド命名と Db/App の扱い

- 本仕様の **DB（Firestore）上のフィールド名**は **snake_case** で記載する（[02_仕様書追加ルールとテンプレート.md](../00_仕様概要/02_仕様書追加ルールとテンプレート.md) 3.2 に準拠）
- 実装時は `common/src/schemas` の **DbSchema / AppSchema** および `TimestampSchema` / `EpochMillisSchema` のパターンに合わせる（既存: `EventMemberOrder` 等）

## 4. 画面仕様

### 4.1 画面遷移

- ログインユーザーが **マイページ**を開く
- タブ（または同等 UI）で **「たべとも」**を選択
- 一覧でカードをタップした場合の遷移（例: 相手の公開プロフィール）がある場合は **Phase 2 以降**で定義可

### 4.2 UI 要素

#### 4.2.1 表示要素（「たべとも」タブ内）

- **友人 1 人あたり**  
  - プロフィール写真、表示名  
  - **一緒に参加した回数**（`meet_count`）  
  - **最後に会った日**（`last_met_at` の表示用。フォーマットは既存の日付表記に合わせる）  
  - **初めて会った日**（`first_met_at`）
- **一覧**: カード型レイアウト
- **無限スクロール**（追加読み込み）。初回 N 件＋ `hasMore` 相当の継ぎ足し

#### 4.2.2 ソート・件数

- デフォルト: **同席回数**の多い順
- 切替: **最後に会った日**の**新しい**順
- 1 回あたり **10 件**（仕様上の目安。実装は `limit` パラメータと揃えてもよい）

#### 4.2.3 状態表示

- 初回・追加読み込み時の**ローディング**
- **空状態**（たべとも 0 人）のメッセージ（R-7）:
  - リリース直後 / 過去にイベント参加経験のないユーザー向けに「**まだ"たべとも"がいません。食事会に参加して仲間を見つけましょう**」相当の文言（最終文言は i18n / コピーチームと調整）
  - **CTA**: 「イベントを探す」ボタン → 既存のイベント一覧ページへ遷移
- 取得失敗時の**エラー表示**と、可能な範囲の**再試行**

## 5. 技術仕様・データ構造設計

### 5.1 Firestore スキーマ設計

#### 5.1.1 コレクション構造

**新規サブコレクション**: `users/{user_id}/friends/{friend_user_id}`


| 項目         | 内容                                                                         |
| ---------- | -------------------------------------------------------------------------- |
| 親          | `users` コレクションの `user_id`（Firebase Auth UID）                               |
| 子ドキュメント ID | 友人側の `friend_user_id`（相手の UID）                                             |
| 説明         | ログインユーザー `user_id` 視点の「**たべとも** 1 人分」の関係。双方向（A-B と B-A）の **2 ドキュメント**を維持する |


既存のツリーに対する追記例:

```
users/{user_id}
  /friends/{friend_user_id}  （本仕様で新設）
```

#### 5.1.2 ドキュメントスキーマ（論理名・型）


| フィールド           | 型               | 必須  | 説明                                                            |
| --------------- | --------------- | --- | ------------------------------------------------------------- |
| `first_met_at`  | Timestamp       | 必須  | 一覧用。**派生**。`event_history[].event_at` の最小。同一 `event_id` は 1 件 |
| `last_met_at`   | Timestamp       | 必須  | 一覧用・ソート用。**派生**。**最大**                                        |
| `meet_count`    | number (int)    | 必須  | 同席した**イベント**数。`event_history` のユニーク `event_id` 件数と一致          |
| `event_history` | array of object | 必須  | `{ event_id, community_id, event_at }`。**event_id 単位で重複なし**    |
| `created_at`    | Timestamp       | 必須  | 初回作成                                                          |
| `updated_at`    | Timestamp       | 必須  | 最終更新                                                          |

> **配列上限への備え**: `event_history` を配列で持つため、**Firestore の 1 ドキュメント 1MB 制限**に長期で抵触する懸念がある。Phase 1 では配列のままとし、件数が多くなる兆候が見えた段階で **`users/{user_id}/friends/{friend_user_id}/meetings/{event_id}` サブコレクションへの分離**を Phase 3 で検討する（直近 N 件のみ配列で保持する案を含む）。

> **デノーマライズしない方針**: 上記スキーマには **`user_name` / `user_image_url` などの相手プロフィールフィールドを含めない**。理由は 3.2 に記載のとおり、将来 `users` 側に**タグ・SNS リンク・自己紹介**などの追加項目を表示する可能性があり、`users` を**真**として表示時に解決する方が、追加項目発生時の改修コストとデータ整合リスク（伝播トリガー失敗による不整合）を抑えられるため。表示に必要な相手情報は **5.5.1 の Callable 内で `users` を都度解決**する。


`event_history[]` 各要素:


| フィールド          | 型         | 必須  | 説明                                                                                       |
| -------------- | --------- | --- | ---------------------------------------------------------------------------------------- |
| `event_id`     | string    | 必須  | 対象イベント ID                                                                                |
| `community_id` | string    | 必須  | 当該イベントが属するコミュニティ ID（B-2 / 将来のコミュニティ別フィルタや分析のために保持）                                      |
| `event_at`     | Timestamp | 必須  | **会合の基準日時**。`events/{event_id}.event_start_datetime` を**注文確定時点でスナップショット**として格納（後述 S-8）。 |


**整合**: `first_met_at` / `last_met_at` / `meet_count` は `event_history` と矛盾しないよう、更新トランザクションまたは単一箇所の更新ロジックで保つ。

> **`event_at` の不変性**: `events.event_start_datetime` は管理者が後から変更しうるが、`event_history[].event_at` は**注文確定時点の値で固定**する（後追いで書き換えない）。理由は、過去の同席実績の `first_met_at` / `last_met_at` がイベントの予定変更で動くと UX 上違和感があり、双方向ドキュメントの整合維持コストも増えるため。

#### 5.1.3 Zod スキーマ定義（配置イメージ）

`common` に `UserFriend`（仮名）用の Db / App スキーマを追加する。**DbSchema は `TimestampSchema`、AppSchema は `EpochMillisSchema`** で揃える（既存 `EventMemberOrder` 等と同じ慣習）。例（実装時にファイル名・export 名を確定）:

```typescript
// common/src/schemas/userFriend.ts（仮の配置）
import { z } from 'zod'
import { TimestampSchema, EpochMillisSchema } from './firebase/index.js'

const EventHistoryEntryDbSchema = z.object({
  event_id: z.string().nonempty(),
  community_id: z.string().nonempty(),
  event_at: TimestampSchema,
})

const EventHistoryEntryAppSchema = z.object({
  event_id: z.string().nonempty(),
  community_id: z.string().nonempty(),
  event_at: EpochMillisSchema,
})

export const UserFriendDbSchema = z.object({
  first_met_at: TimestampSchema,
  last_met_at: TimestampSchema,
  meet_count: z.number().int().nonnegative(),
  event_history: z.array(EventHistoryEntryDbSchema),
  created_at: TimestampSchema,
  updated_at: TimestampSchema,
})

export const UserFriendAppSchema = z.object({
  first_met_at: EpochMillisSchema,
  last_met_at: EpochMillisSchema,
  meet_count: z.number().int().nonnegative(),
  event_history: z.array(EventHistoryEntryAppSchema),
  created_at: EpochMillisSchema,
  updated_at: EpochMillisSchema,
})
```

### 5.2 フロントエンド（`user`）

- **主要ページ**: マイページ（「たべとも」タブ）
- **コンポーネント**（仮名）: `FriendsList.vue`、`FriendCard.vue`
- **データ取得**: **Callable 一本化**（5.5 と整合）。クライアントから `users/{uid}/friends` を直接読まない。理由は、相手プロフィール（`users` 解決）と退会判定・将来の `users` 追加項目展開を**サーバー側で一元実装**するため
- **状態管理**: 招待モーダル等でも友人リストの再利用が想定されるため、Pinia の **`useFriendsStore`**（仮）に集約し、ページごとの再取得を抑制する（R-6）

### 5.3 Firestore インデックス

サブコレクション `users/{user_id}/friends` で **ソート + カーソル**を行うため、`firestore.indexes.json` に以下の複合インデックスを追加する（S-9：tie-breaker は `friend_user_id` 昇順で安定化）。

| インデックス                                                    | 用途                                  |
| ---------------------------------------------------------- | ----------------------------------- |
| `users/{user_id}/friends`: `meet_count desc, friend_user_id asc` | 既定ソート（同席回数順）                        |
| `users/{user_id}/friends`: `last_met_at desc, friend_user_id asc` | ソート切替（最後に会った日順）                     |

> **インデックス削除の作法**（R-3）: Phase 3 で `event_history` を `meetings` サブコレクションへ分離する場合、上記インデックスのうち**不要になるもの**は `firestore.indexes.json` から削除し、デプロイ時に Firestore コンソールでも削除されたことを確認する（自動削除されないため、放置するとコストが残る）。

### 5.4 Firestore セキュリティルール（方針）

クライアントは `friends` を**直接読まず**、認証必須の Callable（5.5.1）経由で取得する。よってルールは**読み書きとも禁止**を基本とし、Functions の Admin SDK からのみアクセスする（M-5 と整合）。

```javascript
// 例（抜粋。実装時に match パスと申請用ルールで確定）
// match /users/{userId}/friends/{friendId} {
//   allow read, write: if false; // クライアント直接アクセスは全面禁止。Callable 経由のみ
// }
```

> **補足**: 「自分のサブコレクションは自分が読める」を許す設計も論理的には成り立つが、`users` 解決・退会フィルタ・追加プロフィール項目の展開を**サーバー一箇所**で実装する方針を優先する。将来直 read を許可する必要が出たら、当節で明示的に方針転換する。

### 5.5 Functions 設計

| 種別           | 役割           | 内容 |
| ------------ | ------------ | ---- |
| **Trigger**  | 注文（参加）**確定／取消** | `member_orders` の `onDocumentWritten`。当該イベントの**他参加者**と**双方向**で `event_history` を冪等更新／削除（`event_id` 単位で重複不可、5.6.1 詳細） |
| **バッチ Callable** | **リリース時**    | 管理者専用 Callable（`backfillUserFriends`）。既存 `member_orders` から一括で友人ドキュメントを構築・補正。`dry_run` / 範囲指定 / `resume_token` を受ける（5.6.2 詳細） |
| **Callable** | 友人一覧         | 認証必須（`getUserFriends`）。**カーソル方式**で `limit` / `sort_by` / `cursor` を受け、`sort_by` は `meet_count` または `last_met_at`。**相手の `user_name` / `user_image_url` 等は `users` を都度解決して返却**（friends にはコピーを持たない） |

注: [02_仕様書追加ルールとテンプレート.md](../00_仕様概要/02_仕様書追加ルールとテンプレート.md) の原則どおり、**可能な限り**読取は Firestore 直でもよいが、**他ユーザープロフィールの解決**が伴い、かつ将来の表示項目追加（タグ・SNS リンク等）にも備えるため、**本仕様では Callable 一本に寄せる**ことを推奨する。

#### 5.5.0 実装上の規約（プロジェクト共通）
- **Logger**: `console.log` / `console.error` および `firebase-functions` の `logger` を直接使わず、`createModuleLogger` を使用する
- **Store 経由**: Firestore へのアクセスは必ず **store 関数**を経由し、reference には **`withConverter`** を付与する（zod バリデーションを通す）
- **`set` 前の `get`**: `withConverter` + `set` で既存ドキュメントを更新する場合、必ず**先に `get` して既存データを引き継いでから**更新する。注文 Trigger では、対象友人ドキュメント（A→B / B→A）について、トランザクション内で `get → 既存 `event_history` に append（`event_id` 重複なし）→ 派生フィールド再計算 → `set`** とする
- **Callable**: 引数にクラスインスタンス等のオブジェクトを渡さず、ID とプリミティブで受け渡す
- **users の解決**: 友人一覧 Callable では、`friends` を読み取った後に**ユニークな `friend_user_id` 集合**を作り、`users` を **`Promise.all` による並列取得**で解決する。同一ページ内の重複は自然になくなるが、ループ内の逐次 `await` は避ける（N+1 回避）
- **退会／削除ユーザーの扱い**（S-1）: A-7 のとおり、`users/{friend_user_id}` が **存在しない** または **`is_deleted === true`**（`common/src/schemas/User.ts` の既存フィールド）の場合は、当該友人を**レスポンスから除外**する。ページサイズに満たない場合の追加取得は Phase 1 では行わず、`limit` のベストエフォートで返却する
- **同伴者の扱い**（S-2 / A-5）: 友人関係の集合 `Others` は **`member_orders` の `user_id` 集合**から算出する。同伴者数を表す `EventMember.member_count` は**参照しない**（同伴者は `user_id` を持たないため、そもそも集合に入らない）。これにより「アカウントを持たない同伴者を友人化しない」を実装で担保する

#### 5.5.1 友人一覧（API イメージ）

**Callable 名**: `getUserFriends`（C-3）

**リクエスト（例）**

```json
{
  "limit": 10,
  "sort_by": "meet_count",
  "cursor": null
}
```

| フィールド     | 型                                  | 必須 | 説明                                                                                                |
| --------- | ---------------------------------- | -- | ------------------------------------------------------------------------------------------------- |
| `limit`   | number                             | 任意 | 1〜50。既定 10                                                                                        |
| `sort_by` | `'meet_count'` \| `'last_met_at'`  | 任意 | 既定 `meet_count`                                                                                   |
| `cursor`  | string \| null                     | 任意 | 直前ページ末尾の不透明トークン。サーバー側で base64 エンコードしたソートキー（後述）を扱う                                                |

**レスポンス（例）** ※ `user_name` / `user_image_url` は **`users/{friend_user_id}` から都度解決**して詰める（`friends` ドキュメントには保持しない）。`user_name` は必須、`user_image_url` は未設定ユーザーは**空文字 `''`**（`User.AppSchema` の `null → ''` 変換と整合）。`total` は**返さない**（カーソル方式のため）。

```json
{
  "friends": [
    {
      "user_id": "string",
      "user_name": "string",
      "user_image_url": "",
      "meet_count": 0,
      "first_met_at": 0,
      "last_met_at": 0
    }
  ],
  "next_cursor": null,
  "has_more": false
}
```

`first_met_at` / `last_met_at` は **`EpochMillisSchema` 相当の数値（ms）** で返す（AppSchema と整合）。

**DB ↔ API のフィールド命名マッピング**（C-1 / C-2）

| API レスポンス        | DB の真名（`users` コレクション）       | 備考                                                           |
| ---------------- | ----------------------------- | ------------------------------------------------------------ |
| `user_name`      | `users.user_name`             | DB と同名で揃える（既存 `User` スキーマに準拠）                                |
| `user_image_url` | `users.user_image_url`        | DB と同名で揃える。**未設定時は空文字 `''`**（`UserAppSchema` の `null → ''` 変換と整合） |
| `user_id`        | `users.user_id` / ドキュメント ID   | —                                                            |

> **方針**: API レスポンスのフィールド名は **DB の真名と完全一致**させる（C-1 / C-2 の確定事項）。これにより API 層での命名変換が不要となり、フロントから `User` AppSchema を直接利用できる。

**カーソルの中身（サーバー内部）**

- `sort_by=meet_count` の時: `(meet_count, friend_user_id)` の組（tie-breaker は `friend_user_id` 昇順、S-9）
- `sort_by=last_met_at` の時: `(last_met_at, friend_user_id)` の組
- 上記タプルを base64(JSON) で不透明文字列化してフロントへ返却

**Callable 内の処理順（概略）**:
1. リクエストを zod でバリデーション（`limit` の範囲・`sort_by` の enum・`cursor` の形式）。NG は `HttpsError('invalid-argument')`
2. 認証済み `uid` の `users/{uid}/friends` を `orderBy(<sort_by>, 'desc'), orderBy('friend_user_id', 'asc')` ＋ `startAfter(cursor)` ＋ `limit(limit + 1)` でクエリ（`+1` は `has_more` 判定用）
3. 取得した友人の `friend_user_id` 集合に対し、`users` を **並列取得**（5.5.0 参照）
4. `users` が**未取得 / `is_deleted === true`** の `friend_user_id` を**除外**し、`user_name` / `user_image_url` を埋めて整形（`UserAppSchema` をそのまま使えば `user_image_url` の `null → ''` 変換も自動で行われる、S-1）
5. `event_history` の `Timestamp` は AppSchema の `EpochMillisSchema` 形式（ms）に変換
6. 末尾の `+1 件目` の有無で `has_more` を判定し、最終要素から `next_cursor` を生成
7. 将来 `users` のタグ・SNS リンク等を一覧に出す際は、**本ステップで返却フィールドを足すだけ**で済む（`friends` のスキーマ・Trigger を一切触らない）

**内部**の関係更新（注文 Trigger / バッチ）は、HTTP の `POST /api/friends/update` を公開せず **共有モジュール**（`friendsService`、後述 5.5.2）＋ Trigger 経由に寄せる。双方向（A→B / B→A）で**同一ロジック**を必須とする（5.6・5.7 参照）。

### 5.6 処理フロー

#### 5.6.1 注文（参加）確定 Trigger の処理フロー

**対象パス**（既存スキーマと整合・M-1）

```
communities/{communityId}/events/{eventId}/members/{memberId}/member_orders/{orderId}
```

`onDocumentWritten` で `EventMemberOrder` の作成・更新・削除をハンドリングする。

**ステータス遷移と処理の対応**（S-3）

| 遷移                                | 動作              | 備考                                  |
| --------------------------------- | --------------- | ----------------------------------- |
| `(none) → ordered` または `* → ordered`（before が `ordered` でない） | **追加**（ADD）     | A-1 / A-4 と整合                       |
| `ordered → canceled`              | **取消**（REMOVE）  | A-2: `event_history` から該当 `event_id` を外し派生フィールドを再計算 |
| `ordered → ordered`（メニュー変更等）      | **no-op**       |                                     |
| `(その他)` ／ `before === after.status === 'ordered'` | **no-op**       |                                     |
| ドキュメント削除                          | **取消**（REMOVE）  | 物理削除運用がある場合の保険                      |

> **判定の純粋関数化**（R-1）: 上記の遷移判定は `utils/orderStatusTransition.ts`（5.5.2 ④）に **`'ADD' | 'REMOVE' | 'NOOP'`** を返す純粋関数として切り出し、Trigger 本体はそれを呼び出すだけにする。

**処理ステップ**

1. Trigger に届いた `before / after` から `'ADD' | 'REMOVE' | 'NOOP'` を判定。`NOOP` なら早期 return
2. `after`（または削除時は `before`）から `community_id` / `event_id` / `user_id`（=`A`）を取り出す
3. 同イベントの確定済み注文者を取得し、`Others = { 当該 event の status==='ordered' な user_id 集合 } - { A }`（自己参照は除外、A-8）。同伴者は対象外（S-2 / A-5: 同伴者は `member_count` のみで `user_id` を持たないため自然に集合に含まれない）
4. `events/{eventId}` から `event_start_datetime` を取得し `event_at` とする（**注文確定時点で固定**して以後書き換えない、S-8）
5. `Others` の各 `B` について、**`runTransaction`** で次を実行（A-B 双方向を**同一トランザクション内**で処理）
   1. **read を先に**: `users/{A}/friends/{B}` と `users/{B}/friends/{A}` を `transaction.get`
   2. ADD の場合: `event_history` に `{event_id, community_id, event_at}` を**`event_id` 単位で重複なし**にマージ
   3. REMOVE の場合: `event_history` から `event_id` 一致要素を**全削除**。同一 `event_id` の注文は B-3 / A-1 の通り 1 つに正規化されているため、削除後の再計算で問題なし
   4. `meet_count` = `event_history` のユニーク件数、`first_met_at` = `event_at` の最小、`last_met_at` = 最大、`updated_at` を再計算（REMOVE で `event_history` が空になったら**ドキュメント自体を `transaction.delete`**）
   5. **write を後に**: `transaction.set`（`withConverter` 経由）または `transaction.delete`
6. **競合への備え**（S-4）: Firestore の自動リトライに任せつつ、Phase 1 では発生頻度をモニタ。多発するイベントが見つかった場合 Phase 2 で**イベント単位デバウンス**（Pub/Sub or Cloud Tasks で集約）を検討。リリース時バッチ（5.6.2）が**整合のセーフティネット**として再実行可能であることが前提
7. 失敗時は `createModuleLogger` でログし、**8.4 の運用方針**に従って再処理（再 Trigger / 補正バッチ）

**実行環境（S-5）**

- リージョン: 既存 `functions/default` と同一（`asia-northeast1` を踏襲。実装時に `index.ts` の他 Functions を確認）
- `timeoutSeconds`: 60（200 人クラスのイベントでも収まる目安。Phase 2 で計測値に応じて調整）
- `memory`: 256MiB（`runTransaction` のみで重い計算なし）
- `maxInstances`: 既存方針に揃える（暴走時のコスト上限）

#### 5.6.2 リリース時バッチの処理フロー

**起動方式（S-6）**

- **管理者専用 Callable**（`backfillUserFriends`）を Phase 1 で実装
- 認可: `firestore.rules` の `isSupport()` 相当のチェックを Functions 側でも明示（`auth.token` を確認）。判定ロジックは既存の admin Functions の作法に揃える
- 引数（プリミティブのみ、5.5.0 規約準拠）:
  - `dry_run: boolean`（既定 `true`。書き込みせず統計だけ返す）
  - `community_id?: string`（範囲を絞る）
  - `event_id_from?: string` / `event_id_to?: string`（イベントレンジ）
  - `resume_token?: string`（前回の中断地点から再開）
- リリース直後の初回投入は `dry_run` で件数とコストの見立て → 本実行 → 異常時は `resume_token` で部分再実行という運用を想定

**処理ステップ**

1. 上記 Callable を **support / 管理者**のみが叩く形で開始
2. 対象期間の `events` を走査し、各 `eventId` について **`status === 'ordered'`** の `member_orders.user_id` 集合 `P` を作る（同伴者は対象外、S-2）
3. `P` 内の任意の 2 人 `(A, B)`（`A !== B`、A-8）に対し、5.6.1 手順 5 と**同等のロジック**（`friendsService` を共有、R-2）を実行
4. 大量データに備え、**500 件単位**で `BulkWriter` または `WriteBatch` を分割し、`event_id` 単位で**チェックポイント** `resume_token` を返す（途中失敗からの再開を可能にする）
5. 進捗・失敗を `createModuleLogger` で記録し、再実行可能（冪等）であることを保証
6. `dry_run` 時は実際の write を行わず、追加見込みの `friends` ドキュメント数 / `event_history` 追加件数 / 想定コスト概算を返却

**ユーザー削除との関係（S-7）**

- ユーザー A の退会時に**自動削除はしない**（A-7 のとおり「表示で非表示」する）。`friends` ドキュメントは残置
- 個人情報の物理削除要請があった場合は、上記 Callable の派生として `purgeUserFriends(user_id)` を**別途用意**（Phase 2）。A 視点 / 他者視点（`users/{B}/friends/{A}`）の双方を `collectionGroup('friends')` で削除する
- Phase 1 では物理削除フローは未実装であることを 8.2 に明記

### 5.7 データ整合性の保証

- **冪等性**: 同一 `event_id` の `event_history` への二重追加を行わない（`get → ユニーク化 → set`）
- **双方向の整合**: `users/{A}/friends/{B}` と `users/{B}/friends/{A}` の更新は**同一 `runTransaction` 内**で行い、片側だけ書かれる状態を作らない
- **派生フィールド**: `first_met_at` / `last_met_at` / `meet_count` は **`event_history` を真とする**再計算（書き込み箇所を 1 つに集約）
- **プロフィール情報の真は `users`**: `user_name` / `user_image_url` 等は `friends` に**コピーを持たない**ため、`users` 更新時の**伝播トリガー（onUpdated）は不要**。`users` の値が常に最新として表示される
- **障害時の補正**: 双方向の不整合や Trigger 失敗が起きた場合、**リリース時バッチと同等のロジック**を一部のユーザー / イベント範囲で再実行できるようにしておく

### 5.8 エラーハンドリング（技術）

- **Callable**: 認証失敗、バリデーション、`HttpsError` の扱い（既存 Functions 方針に合わせる）
- **Trigger**: 失敗はログ・**再送可能**なデッドレター方針を検討
- **プロフィール解決の部分失敗**: `users` 取得時に**個別にエラー**となる相手が出ても、**ページ全体は成功**として返す方針（その相手のみ除外し、`createModuleLogger` で warn を残す）
- 一覧: 空・タイムアウト・部分失敗の扱い（クライアント側はカード単位での縮退表示は行わず、Callable 側で「返せる分のみ返す」設計とする）

- **Functions**: 新規 Trigger / バッチ / Callable
- 既存の注文フローに、**遅延・失敗**が与える影響（Trigger の**非同期**化と再試行）

#### 8.1.3 運用

- バッチ初回の**所要時間**・**再実行**手順
- ストレージ・**読取/書取**料金の見積り

### 8.2 セキュリティ考慮事項

- **read**: 本人の `friends` のみ。他者の**秘密の関係**が漏れないこと（クライアント直 read を禁止し、Callable で本人 `auth.uid` を絞り込み条件にする）
- **相手の表示名・写真**: 公開プロフィール方針に**準拠**
- 招待・外部連携は [02_友人招待機能.md](./02_友人招待機能.md) と**整合**
- **退会／物理削除運用**（S-7）: Phase 1 では退会ユーザーの `friends` ドキュメントは**物理削除しない**（表示時にフィルタ）。個人情報削除要請に応える物理削除フロー（`purgeUserFriends` 等）は Phase 2 で別途定義する

### 8.3 パフォーマンス考慮事項

- 一覧の**ページング**、**不要なユーザーフィールド**の省く取得
- 相手人数が多いイベントでの **Trigger 内書き込み**（**バッチ 500 件**制限、チャンク分割）
- **`users` の N+1 回避**: 友人一覧 Callable では、ページ分の `friend_user_id` を**一括収集 → `Promise.all` で並列取得**する（5.5.0 参照）。1 ページ `limit=10` であれば追加読み取りは最大 10 件で、全体読み取りは `friends` 10 件 ＋ `users` 10 件 = **20 件 / ページ**程度に収まる
- **頻繁な再表示への備え**: クライアント側の**短時間のキャッシュ**（同セッション内でのスクロール戻り等）を Phase 2 以降で検討

### 8.4 エラーハンドリング（プロダクト）

- ネットワークエラー時の**再試行**、一覧失敗の**メッセージ**（4.2.3 と整合）
- **Trigger 競合への運用方針**（S-4）:
  - Phase 1 は Firestore の**自動リトライ**に委ねる。同イベント内の同時注文確定で `runTransaction` 競合が発生しても、最終的に整合する設計
  - Trigger 失敗が **N 回連続**（仮: 3 回）の場合は `createModuleLogger` で error を出し、運用アラート（メトリクス R-4）でキャッチ
  - 復旧手段: **リリース時バッチ Callable**（5.6.2）を該当 `event_id` だけ範囲指定して実行する。これがセーフティネット
  - Phase 2 で発火頻度が高いイベントが見つかれば、**Pub/Sub or Cloud Tasks による集約**を検討

### 8.5 運用・監視（R-4）

**メトリクス**

- Trigger（`onMemberOrderWritten`）: 成功率 / 平均実行時間 / リトライ回数 / `event_id` ごとの最大 transaction 競合回数
- Callable `getUserFriends`: レスポンス時間 p50 / p95、エラー率（`HttpsError` の code 別）
- リリース時バッチ Callable: 完了時間、処理 event 数、追加された `friends` ドキュメント数、`dry_run` と本実行の差分
- KPI（2.3 と接続）: 「たべとも」タブ閲覧 PV / UU、`friends` 件数推移、1 ユーザー平均同席者数

**ログ**

- Trigger / バッチの失敗理由（`createModuleLogger` での error）
- **冪等性監査**: 同一 `event_id` の二重 append が起きた件数（0 が正常）
- 退会ユーザー除外でレスポンスから外した件数（過度に多ければ要注意）

### 8.6 ロールアウト戦略（R-5）

リリースは段階公開とし、各段で**ロールバック手順**を準備する。

| 段 | 内容 | ロールバック |
|---|---|---|
| 1. dark launch | Trigger と Callable をデプロイ。クライアントは UI から呼ばない（フィーチャーフラグで無効） | フラグを倒すだけ |
| 2. 内部検証 | 社内アカウントだけフラグを ON にし、マイページ「たべとも」タブの動作確認 | 同上 |
| 3. パイロットコミュニティ | リリース時バッチ Callable を `dry_run=true` でコスト見積もり → 本実行 → 1 コミュニティだけ UI 公開 | フラグ OFF。`friends` ドキュメントは残置でも問題なし |
| 4. 全体公開 | 全期間・全コミュニティをバッチで構築。UI フラグを全 ON | フラグ OFF。問題なら `purgeUserFriends` 群で部分整理 |

**フィーチャーフラグの場所**: `user/src/environment.constant.ts` または既存の Remote Config 運用に揃える（実装直前に確認）。
