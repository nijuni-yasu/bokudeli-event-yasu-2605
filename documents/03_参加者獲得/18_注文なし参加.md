## 1. 概要

### 1.1 機能の目的

食事を注文せずにイベントへ参加できる選択肢を提供し、主催者の参加者獲得を促進する。

### 1.2 主要な機能

- 主催者がイベント設定のメニュー選択画面（Step 3）で「注文なしで参加」の表示 / 非表示を切り替える
- 表示 ON の場合、イベントページのメニュー一覧に「注文なしで参加」が並ぶ
- 参加者はこれをカートに追加し、決済なしで注文を確定して参加できる
- 注文なし参加は店舗への発注情報・主催者請求書には含めない

### 1.3 対象ユーザー

- **主催者**: イベント設定で注文なし参加の可否を決める
- **参加者**: 食事を注文せずにイベントへ参加する

### 1.4 スコープ外（Phase 2 以降）

- 主催者が任意のメニューを追加する機能（品目モデル §9）
- チケット機能（品目モデル §10）
- 主催者が「注文なしで参加」の名称・説明文を編集する機能
- 注文なし参加から有料注文への切り替え導線（§9.2）
- 同伴者分の複数枚取得

## 2. ねらい

### 2.1 ビジネス目標

- 注文のハードルを下げることによるイベント参加者数の増加
- 主催者のイベント開催ハードルの低下

### 2.2 ユーザー価値

- **主催者**: 食事を注文しない参加者も受け入れられ、参加者を増やせる
- **参加者**: 食事の注文なしでイベントに参加できる

### 2.3 成功指標（KPI）

- 注文なし参加を ON にしたイベントの比率
- 注文なし参加者数 / 全参加者数
- 注文なし参加者の次回有料参加への転換率

## 3. 前提条件

### 3.1 技術的前提条件

- 参加の正本は `member_orders` の `status: 'ordered'`（`recalcEventMembers`）
- メニューの表示制御は `EventMenu.is_selected`
- 0 円の注文確定経路は Callable `confirmOrder`（Stripe を経由しない）

### 3.2 ビジネス的前提条件

- 注文なし参加者もイベントの参加者としてカウントする（定員・参加者一覧の対象）
- 注文なし参加者は店舗への発注対象外であり、主催者への請求も発生しない

### 3.3 依存関係

- 品目モデル（`item_type` の導入）
- イベント設定 Step 3（メニュー選択）
- カート・注文確定（`addToCart` / `confirmOrder`）

## 4. 画面仕様

### 4.1 画面遷移

```
[主催者] イベント設定 Step 3「メニュー」
  └── 「注文なしで参加」カードを選択 / 選択解除 → 保存（updateEventMenus）

[参加者] イベントページ
  └── メニュー一覧（末尾に「注文なしで参加」）
        └── 選択 → カート追加ダイアログ → カート画面
              └── 「参加を確定する」→ confirmOrder → 注文完了画面
```

### 4.2 主催者側 UI（`base/src/components/eventcreate/EventMenu.vue`）

- 店舗メニューのカード一覧（`v-for="props.menus"`）の**外側・末尾**に「注文なしで参加」専用カードを常に表示する
- **`props.menus` 配列に予約ドキュメントを混ぜない。** `selectedCount`（61-63行）・`isLastSelected`（56-58行）の対象外とし、店舗メニューの「最低 1 件は選択必須」制約に影響させない
- 選択状態は専用 prop `noOrderParticipationSelected` と emit `update:noOrderParticipationSelected` で管理する（店舗メニューの `update:selectedMenuIds` とは分離）
- 既定は**未選択**（`EventEdit.vue` が Firestore の予約ドキュメント `is_selected` から初期化する）
- 価格表示は「¥0」ではなく「注文なし」等の文言とする（金額として誤認させない）
- 画像は `EventMenuImage` を使わずアイコン表示とする
- 店舗メニューの選択が 0 件のまま「注文なしで参加」のみを ON にした状態は許可しない（既存の「最低 1 件」制約は店舗メニューに対して維持する）

### 4.3 参加者側 UI（`base/src/components/EventMenuList.vue`）

- `is_selected: true` のメニューのみ表示する既存ロジックをそのまま使う
- 表示位置は**メニュー一覧の末尾**（`menu_sort_number` による。§5.2.2）
- 画像は持たないため、`EventMenuImage` のフォールバックではなくアイコン表示（`mdiAccountCheck` 等）とする
- 価格欄は「¥0」ではなく「注文なし」と表示する
- **レイアウト分岐への影響**: 横長レイアウトは「2件以下かつ PC」のときのみ（`HORIZONTAL_LAYOUT_MAX_COUNT = 2`）。予約メニューが追加されると件数に含まれるため、店舗メニュー2件のイベントはグリッド表示になる。**許容する**（実装簡素化のトレードオフ）

### 4.4 カート画面（`base/src/components/pages/cart.vue`）

- 数量変更（+ / −）は表示しない（数量 1 固定）
- 合計金額は ¥0 と表示し、決済手段の選択・Stripe への遷移は行わない
- ボタン文言は「注文を確定する」ではなく「参加を確定する」とする

## 5. 技術仕様・データ構造設計

### 5.1 コレクション構造

新規コレクションは追加しない。既存の `menus` と `member_orders` にフィールドを追加する。

```
/communities/{communityId}
  /events/{eventId}
    /menus/{menuId}                              ← item_type を追加
      （menuId = 'no_order_participation' が予約ドキュメント）
    /members/{userId}
      /member_orders/{orderId}                   ← item_type を追加
```

### 5.2 スキーマ変更

#### 5.2.1 item_type の定義（新規）

```typescript
// common/src/schemas/EventItemType.ts
import { z } from 'zod'

export const EVENT_ITEM_TYPE_VALUES = ['partner_menu', 'organizer_menu', 'ticket'] as const
export type EventItemTypeType = (typeof EVENT_ITEM_TYPE_VALUES)[number]

export const EventItemTypeSchema = z.enum(EVENT_ITEM_TYPE_VALUES).default('partner_menu')
```

`ticket` は Phase 3 で使用する。Phase 1 では値のみ定義し、生成しない。

#### 5.2.2 EventMenu（`common/src/schemas/EventMenu.ts`）

| 変更 | 内容 |
| :-- | :-- |
| 追加 | `item_type: EventItemTypeSchema`（DbSchema / AppSchema 双方。既定 `'partner_menu'`） |
| 緩和 | `menu_price` を `z.number().int().positive()` → `z.number().int().nonnegative()`（DbSchema / AppSchema 双方。AppSchema の `.default(100)` は維持） |

**予約ドキュメントの内容**

| フィールド | 値 |
| :-- | :-- |
| ドキュメント ID | `no_order_participation`（定数 `NO_ORDER_PARTICIPATION_MENU_ID`） |
| `item_type` | `'organizer_menu'` |
| `menu_name` | `注文なしで参加` |
| `menu_description` | `食事の注文なしでイベントに参加します。`（`EventMenuDbSchema.menu_description` は `nonempty()` のため空文字は不可） |
| `menu_price` | `0` |
| `is_sold_out` | `false` |
| `is_selected` | 主催者の設定値（新規作成時は `false`） |
| `menu_sort_number` | `NO_ORDER_PARTICIPATION_SORT_NUMBER = 999999`（一覧の末尾に固定） |

ドキュメント ID は固定文字列とする。Firestore の自動 ID は 20 文字のランダム文字列であり、`PartnerMenu` の `menu_id` と衝突しない。

`EventMenuAppSchema.is_selected` の既定値は `true` であるため、**予約ドキュメントの新規作成時は `is_selected: false` を明示的に渡す**（既定値に任せると注文なし参加が初期状態で ON になる）。

#### 5.2.3 EventMemberOrder（`common/src/schemas/EventMemberOrder.ts`）

| 変更 | 内容 |
| :-- | :-- |
| 追加 | `item_type: EventItemTypeSchema`（DbSchema / AppSchema 双方。既定 `'partner_menu'`） |
| 緩和 | `menu_price` を `positive()` → `nonnegative()`（DbSchema / AppSchema 双方） |

#### 5.2.4 既存データとの互換

`item_type` は `.default('partner_menu')` を持つため、フィールドを持たない既存ドキュメントも AppSchema の `parse` で既定値が入る。読み取りは `EventMemberOrderConverter` / `EventMenu` のコンストラクタを経由するため、**既存データのバックフィルは不要**（`bokudeli-event-batch` 側のタスクは不要）。

ただし Firestore の `where('item_type', '==', ...)` はフィールド未保持のドキュメントにマッチしないため、**`item_type` での絞り込みはクエリ条件に使わず、取得後のメモリ上で行う**。

### 5.3 判定ヘルパー（`common/src/utils/eventItemType.ts`・新規）

```typescript
/** 店舗に発注し、店舗へ支払う品目か（発注情報・主催者請求書の対象判定） */
export function isPartnerSuppliedItem(itemType: EventItemTypeType): boolean {
  return itemType === 'partner_menu'
}

/** イベントページのメニュー一覧に表示する品目か */
export function isMenuItem(itemType: EventItemTypeType): boolean {
  return itemType === 'partner_menu' || itemType === 'organizer_menu'
}

/** カート画面で加算される付加項目か */
export function isTicketItem(itemType: EventItemTypeType): boolean {
  return itemType === 'ticket'
}

/** 店舗発注・請求の対象となる注文のみを抽出する */
export function filterPartnerSuppliedOrders(orders: EventMemberOrder[]): EventMemberOrder[]
```

呼び出し側で `item_type === 'partner_menu'` と直接比較してはならない（値の追加時に判定漏れが発生するため）。

### 5.4 Functions 設計

新規の Callable / Trigger は追加せず、既存関数を拡張する。

#### 5.4.1 `updateEventMenus`（`functions/default/src/eventMenusSelection.ts`）

**予約 ID の分離（実装必須）**: Callable の `selectedMenuIds` 配列に `no_order_participation` が含まれる場合、冒頭で分離してから既存経路へ流す。`applyDefaultSelectedMenuIds`（`eventMenuConverter.ts`）は「`selectedMenuIds` と店舗メニュー ID に共通項がなければ店舗変更とみなして全選択」するため、予約 ID が混ざったまま渡すと店舗メニュー全選択が誤発火する。

```typescript
const noOrderSelected = selectedMenuIds.includes(NO_ORDER_PARTICIPATION_MENU_ID)
const partnerSelectedIds = selectedMenuIds.filter((id) => id !== NO_ORDER_PARTICIPATION_MENU_ID)
```

| 変更 | 内容 |
| :-- | :-- |
| 最低 1 件ガード | `selectedMenuIds.length === 0` を **`partnerSelectedIds.length === 0`** に変更（予約 ID のみのリクエストを拒否） |
| 予約ドキュメントの upsert | 保存時に `no_order_participation` ドキュメントが存在しなければ作成する。存在する場合は `is_selected` のみ更新する |
| 再生成対象の限定 | `shouldRegenerateFromPartnerMenus` が true のとき、`savePartnerMenusToEventMenus` へ **`partnerSelectedIds`** を渡す。再生成後に予約ドキュメントを upsert |
| 選択状態の更新 | `shouldUpdateExistingMenusOnly` が true のとき（`accepting_order`）も予約ドキュメントの `is_selected` を更新できる |

#### 5.4.1a `validateReservationRequest`（`common/src/utils/validateReservationRequest.ts`）

`validateMenus` の対象から `organizer_menu` を除外する。予約 ON のみで店舗メニュー 0 件のイベントが予約申請を通ってしまうのを防ぐ。

#### 5.4.1b `eventCopy`（`functions/default/src/eventCopy.ts`）

menus を直接コピーしていない。`savePartnerMenusToEventMenus` で店舗メニューを再生成するため、元イベントの予約ドキュメントの `is_selected` を引き継いで新イベントに **別途 upsert** する。

#### 5.4.1c `countOrderedFoodsForUser`（`functions/default/src/stores/memberOrder.ts`）

`.count()` 集約を使っているが、`item_type` はクエリ条件に使えない（未保持ドキュメントにマッチしない）。`.get()` + `filterPartnerSuppliedOrders` によるメモリフィルタに変更する。`countParticipatedEventsForUser` は全品目のまま変更しない。

#### 5.4.1d `orderCompletionMail.ts`

`dynamicTemplateData` にメニュー名・金額を含まないため**コード変更不要**。文言調整は SendGrid テンプレート側（リポジトリ外）。

#### 5.4.2 `convertPartnerMenusToEventMenus`（`common/src/utils/eventMenuConverter.ts`）

`PartnerMenu` を入力とする再生成関数であり、出力に予約ドキュメントは含まれない。呼び出し側（`updateEventMenus`）で**既存の `organizer_menu` を保持する**責務を持たせる。`applyDefaultSelectedMenuIds` の「空配列なら全選択」ロジックに予約 ID を混入させないこと（注文なし参加が既定 ON になってしまう）。

#### 5.4.3 `addToCart`（`functions/default/src/memberOrders.ts`）

| 変更 | 内容 |
| :-- | :-- |
| 排他チェック | 追加対象に注文なし参加が含まれる場合、カート内に他の品目があればエラー。逆に、カート内に注文なし参加がある状態で他の品目を追加する場合もエラー |
| 重複チェック | 注文なし参加が `in_cart` または `ordered` で既に存在する場合はエラー |
| 数量チェック | 注文なし参加の `count` は 1 のみ許可 |
| 割引計算のスキップ | `isPartnerSuppliedItem` が false の品目には `computePaymentCommunityBillOffAmount` を適用せず、`pay_community_bill_off_amount` を保存しない |
| エンプラ補助のスキップ | `event_payment === 'enterprise_subsidy'` でも、注文なし参加は `addEnterpriseSubsidyMenusToCart` の補助計算対象から除外し、`pay_enterprise_subsidy_amount` を付与しない |
| `item_type` の記録 | マスタの `item_type` を注文ドキュメントへコピーする |

`is_selected` チェック（現行の「メニューが選択されていません」判定）は予約ドキュメントにもそのまま適用され、主催者が OFF のままなら追加できない。定員チェック（`event.members.length >= event_max_people`）も現行のまま適用する。

#### 5.4.4 `confirmOrder`（`functions/default/src/memberOrders.ts`）

現行は `event_payment === 'user_advance'` を無条件で拒否するが、事前クレカ決済のイベントでも注文なし参加は 0 円のため Stripe を利用できない（`createStripeCheckoutSession` は合計 0 円を拒否する）。

| 変更 | 内容 |
| :-- | :-- |
| `user_advance` の例外 | 確定対象の全注文が `isPartnerSuppliedItem === false` かつ合計 0 円の場合に限り、`user_advance` でも確定を許可する |
| 割引整合チェックのスキップ | `isPaymentCommunityBillOffAmountConsistent` の検証対象から `organizer_menu` を除外する |
| エンプラ経路の分岐 | 注文なし参加のみの確定では `finalizeEnterpriseSubsidyZeroPaymentOrder`（補助 usage の確定処理）を経由させず、通常の 0 円確定として処理する |

確定後の副作用（`applyOrderConfirmedSideEffects` → `recalcEventMembers`）は現行のまま適用し、注文なし参加者を `event.members` に含める。

#### 5.4.5 混在カートの扱い

§5.4.3 の排他チェックにより、同一イベントのカート内に注文なし参加と店舗メニューが同時に存在することはない。したがって `cart.vue` の決済分岐は「そのイベントのカートが注文なし参加のみか」で判定できる。

#### 5.6.1 注文件数を人数として使っている箇所

「注文ドキュメントの件数」を人数の代理として定員判定に使っている箇所がある。注文なし参加は 1 人 = 1 ドキュメントであり件数と人数がずれないため**そのままで整合するが、意図が変わらないことを実装時に確認する**。

| 箇所 | 現状の判定 | 方針 |
| :-- | :-- | :-- |
| `functions/default/src/orderDeadlineMail.ts` のコミュニティ向けリマインド | 注文件数が `event_max_people` 以上なら送信をスキップ | 注文なし参加も**含める**（会場が埋まっていればリマインド不要という趣旨に合う） |
| `functions/default/src/eventInformationMail.ts` の週刊メール | 注文件数で満席のイベントを除外 | 注文なし参加も**含める**（同上） |
| `functions/default/src/popularEventMail.ts` | `event.members.length` の閾値 | 注文なし参加も**含める**（人数として数える） |

いずれも「会場が埋まっているか」を見る判定であり、`event_max_people` に注文なし参加を含める方針（§5.6 の定員チェック）と一致する。**店舗の最小注文数**を見る `minimumParticipantsJudgment` のみ除外する点に注意する。

### 5.8 領収書

注文なし参加は決済が発生せず `EventStripe` も作成されないため、領収書は発行しない。`functions/default/src/eventReceipt.ts` は `pay_amount === 0` を拒否する既存実装のままとする。

### 5.9 キャンセル

注文なし参加のキャンセルは `status: 'canceled'` への更新のみで、Stripe の返金は発生しない。`common/src/utils/orderStripeRefundRequirement.ts` は `menu_price` を基準に返金要否を判定するため、0 円の注文は既存実装のまま返金対象外となる。

一括中止（最小催行人数による自動中止・主催者による中止）では注文なし参加も `canceled` にし、中止メールの宛先に含める。

### 5.10 Firestore セキュリティルール

変更なし。

- `menus` は `allow read: if true`、write はクライアントから禁止（Callable 経由のみ）
- `member_orders` は read が本人・エンプラ分離条件付き、`allow write: if false`

### 5.11 Firestore インデックス

変更なし。`item_type` はクエリ条件に使わない（§5.2.4）。

### 5.12 イベントコピー

`functions/default/src/eventCopy.ts` でイベントを複製する際、コピー元の `menus` に予約ドキュメントが存在する場合は `is_selected` を含めて複製する。

## 6. 処理フロー

### 6.1 主催者による表示 ON

1. 主催者がイベント設定 Step 3 で「注文なしで参加」カードを選択する
2. 保存操作で `selectedMenuIds` に予約 ID を含めて Callable `updateEventMenus` を呼ぶ
3. Functions で認証・コミュニティ管理者権限を確認する
4. 予約ドキュメントが存在しなければ作成し、`is_selected: true` を設定する
5. 店舗メニューの再生成では予約ドキュメントを削除・上書きしない
6. 参加者側のイベントページに「注文なしで参加」が表示される

### 6.2 参加者による注文なし参加（エラーハンドリング含む）

1. 参加者がイベントページで「注文なしで参加」を選択する
   - 未ログイン時: ログイン画面へ誘導して処理を停止
   - イベントが注文受付中でない場合: エラー表示して停止
2. カート追加ダイアログで確認し、Callable `addToCart` を `count: 1` で呼ぶ
3. Functions で認証を確認する
4. イベントの状態を検証する（キャンセル済み / 注文期限 / 定員）
   - 失敗時: `failed-precondition` を返す
5. 予約ドキュメントの `is_selected` を確認する
   - OFF の場合: `failed-precondition`（「メニューが選択されていません」）
6. 排他・重複・数量を検証する（§5.4.3）
   - カートに他の品目がある: `failed-precondition`
   - 既に注文なし参加が存在する: `failed-precondition`
7. `member_orders` に `status: 'in_cart'`、`item_type: 'organizer_menu'`、`menu_price: 0` のドキュメントを 1 件作成する
8. 参加者がカート画面で「参加を確定する」を押す
9. カート内が注文なし参加のみであるため Stripe を経由せず Callable `confirmOrder` を呼ぶ
10. Functions で合計 0 円かつ全件が店舗発注対象外であることを確認し、`status: 'ordered'` に更新する
11. `applyOrderConfirmedSideEffects` → `recalcEventMembers` により `event.members` / `event_num_members` を更新する
12. 注文完了メール・Slack 通知を送信する（文言は注文なし参加用に分岐）
13. 注文完了画面を表示する

## 9. 注意事項

### 9.1 既存システムへの影響

#### 9.1.1 データベース構造への影響

- **新規コレクション**: なし
- **既存コレクションの変更**: `menus` と `member_orders` に `item_type` を追加（既定値により後方互換）。`menus` に予約ドキュメント 1 件を追加
- **インデックス追加**: なし
- **マイグレーション**: 不要（§5.2.4）

#### 9.1.2 アプリケーションへの影響

- **フロントエンド**: イベント設定 Step 3、イベントページのメニュー一覧、カート追加ダイアログ、カート画面、partner の注文一覧・詳細
- **バックエンド**: `updateEventMenus` / `addToCart` / `confirmOrder`、店舗向けメール各種、名札 PDF、請求書 PDF、最小催行人数判定、プロフィール集計
- **既存機能**: 参加者集計・定員・キャンセル・返金は変更しない

#### 9.1.3 運用への影響

- 店舗から「¥0 の注文が混ざっている」と指摘された場合、§5.6 の除外漏れを疑う
- 主催者請求書の金額は注文なし参加によって変動しない（0 円のため）が、明細行に現れないことを確認する

### 9.2 将来の拡張性

- 注文なし参加から有料注文への切り替えは、排他制御により「注文なし参加をキャンセルしてから注文」の 2 段階になる。専用の切り替え導線は Phase 2 以降で検討する
- 同伴者分の複数枚取得は数量 1 固定の前提を緩める必要があり、Phase 2 以降で検討する
- チケット（Phase 3）とは併用可とする方針のため、排他制御は品目同士に限定して実装する（`isTicketItem` を排他判定に含めない）

### 9.3 セキュリティ考慮事項

- 主催者による表示 ON / OFF は Callable `updateEventMenus` の既存の権限チェック（コミュニティ管理者）に従う
- 参加者からの `menus` / `member_orders` への書き込みは従来どおり禁止
- 価格はサーバー側でマスタ（予約ドキュメント）を参照して 0 円を設定し、クライアントから受け取った金額を信頼しない
- 同一ユーザーの重複取得はサーバー側（`addToCart`）で防止する
