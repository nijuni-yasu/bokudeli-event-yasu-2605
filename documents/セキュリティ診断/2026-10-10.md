## アプリ上の不備

### S-1 コミュニティメンバー作成で roles を制約していない

- 重大度: high
- 層: Rules
- 箇所: `firestore.rules:358-362`
- 内容: `communities/{community}/members/{memberId}` の create は、サポート、既存マネージャ、またはログインユーザー自身の uid と `memberId` が一致すれば許可される。`roles` の中身は見ていない。update はサポートとマネージャに限られ、本人は自分の `roles` を update できない。
- 影響: ログイン済みのユーザーが、読めるコミュニティに自分のメンバー文書を作り、マネージャ権限を自分に付けられる。PF のコミュニティは `enterprise_id == null` なら未認証でもコミュニティ文書を読める。エンタープライズは同じテナントの従業員がコミュニティを読める。マネージャになると、そのコミュニティのイベント更新やメンバー更新に進める。
- 根拠: create 条件は上記の 3 つだけ。`isManager()` は当該メンバー文書の `roles` に `manager` があるかで判定している（同ファイル 262 行付近）。Rules テストは管理者として用意したメンバーを前提にしており、本人作成時に `roles` を拒否するテストは見当たらない。
- 推奨: このリポジトリで、本人作成時は `roles` を空、または `manager` を含めないよう Rules で制約する。拒否する Rules テストを足す。
- この診断では修正していない

### S-2 友人一覧が未ログインの Callable から返る

- 重大度: high
- 層: アプリ
- 箇所: `functions/default/src/userFriends.ts:70-107`、`functions/default/src/userProfile.ts:209-236` と `366-447`
- 内容: `getUserFriends` と `getUserProfilePreview` は `invoker: 'public'` で、PF 経路は `request.auth` が無くても対象ユーザーの友人を返す。返る項目はユーザー ID、表示名、画像 URL、一緒に食事した回数と日時。プロフィールプレビューは友人に加え、参加コミュニティと管理コミュニティの名前と説明も返す。注文プレビューだけ本人に限っている。友人サブコレクションの Rules は本人の read だけである（`firestore.rules:398-400`）。
- 影響: Rules で本人に閉じた友人関係と、非公開コミュニティの名前・説明が、ユーザー ID を知っていれば未ログインの呼び出しで見える。`userFriends.ts` には公開範囲のオプトアウトを Phase 2 で見る TODO がある。
- 根拠: `resolveUserFriendsList` の `viewerUid` はリンク可否に使い、一覧そのものは落としていない。`fetchFriendPreviews` は所有者かどうかで分岐しない。
- 推奨: このリポジトリで、未ログインには友人と非公開コミュニティを返さない。仕様が公開でよいなら、Rules の「本人のみ」と Callable の差を仕様書に書く。
- この診断では修正していない

### S-3 PF の member_orders は未認証で読める

- 重大度: medium
- 層: Rules
- 箇所: `firestore.rules:493-502`
- 内容: `member_orders` の collection group は、`enterprise_id == null` の文書を未認証で読める。Rules のコメントは、`stripe_id` と `processing_payment_intent` も文書に含まれること、機微項目を足さないこと、公開範囲の見直しは #2282 であることを書いている。
- 影響: PF の注文文書に入っている決済識別子が、未ログインの collection group クエリで読める。カード番号そのものではない。
- 根拠: 上記コメントと allow 条件。
- 推奨: #2282 の範囲で直す。この診断では新規 Issue を作っていない。
- この診断では修正していない

### S-4 Dependabot の npm 対象が `/user` だけ

- 重大度: medium
- 層: 設定
- 箇所: `.github/dependabot.yml:8-9`、ルート `package.json` の `workspaces`
- 内容: npm の `directory` は `/user` のみ。lockfile はルートの `package-lock.json` 一つで、workspace は `common`、`base`、`user`、`enterprise`、`partner`、`support`、`terms`、`functions/default`、`tests/firestore-rules`。GitHub Actions の更新はルートで有効。
- 影響: Functions や `base` の依存（axios、sharp、firebase-admin など）が、Dependabot の npm 更新から外れている可能性がある。今回の CVE 件数はルートで `npm audit` したもの。
- 根拠: 上記ファイルの突き合わせ。
- 推奨: このリポジトリで、npm エコシステムの対象をルート lockfile に合わせる。
- この診断では修正していない

### S-5 LINE の一斉配信用 HTTP にアプリ内の検証が無い

- 重大度: low
- 層: 設定
- 箇所: `functions/default/src/lineBroadcast.ts:11-26`
- 内容: `broadcast_event_message_request` は `onRequest` で、リクエストの署名や共有秘密を見ていない。`invoker: 'public'` は付いていない。第 2 世代 Functions の既定は呼び出しに IAM 認証が要る、という理解で書いている。この既定がデプロイ設定で外れていれば、誰でも配信用の処理を起動できる。
- 影響: 既定 IAM のままなら外部からは呼べない。公開 invoker に変えた時点で、認証なしの配信トリガーになる。
- 根拠: ハンドラは `broadcastEventConcludedMessage()` をそのまま呼ぶ。推測: デプロイ後の invoker はコード上の未指定に従う。
- 推奨: このリポジトリで、スケジュール実行だけに寄せるか、共有秘密を確認する。
- この診断では修正していない

## 確認して所見にしなかったもの

- 追跡ファイルに `.env`、`.secret`、`.firebaserc`、`credentials.json` は無い。トークン形式の `git grep -l` も、禁止パスを除外した対象ではファイル名が 0 件だった。
- `.secret` と `.env` は開いていない。値は記録していない。
- `users_personal_information` の read は本人のみ。write は拒否。メールアドレスはこの分離に乗っている。
- Stripe Webhook は `req.rawBody` と `constructEvent` で署名を見ている。失敗は 400。同一 payment intent の stripe 文書がある場合はトランザクションをスキップする。
- Slack の HTTP は `invoker: 'public'` だが、`ExpressReceiver` に `signingSecret` を渡している。
- `recallChatMessage` はログインと送信者本人を見ている。`invoker: 'public'` は Callable をブラウザから呼ぶための指定。
- App Check を付けているのは enterprise の一部 Callable だけ。user のプロフィール系は仕様コメントで未強制。未設定を high にはしていない。
- Storage の `users` / `communities` / `partners` / `assets` の公開 read、エンタープライズロゴの公開 read は、現状の公開ファイルとして info に留めた。チャット添付の read はルームメンバー判定がある。
- `v-html` の大半は `$t` の静的文言。`ManageTopCard` の description も翻訳文を渡している。ユーザー入力の HTML を未サニタイズで渡している箇所は、今回の検索範囲では切り出せなかった。
- メニュー、アルバム、店舗、アセットの公開 read は、画面が公開情報を見せるためのルールとして info に留めた。アルバムはコメントで、公開設定にかかわらず閲覧可と書いている。
