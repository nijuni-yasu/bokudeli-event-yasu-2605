## アプリ上の不備

### S-1 コミュニティメンバー作成で roles を制約していない

- 重大度: high
- 実装工数: M。本人作成時の `roles` 制約と Rules テスト。参加時の作成経路が空の `roles` で通るかの確認を含む
- 層: Rules
- 箇所: `firestore.rules:358-362`
- 内容: `communities/{community}/members/{memberId}` の create は、サポート、既存マネージャ、またはログインユーザー自身の uid と `memberId` が一致すれば許可される。`roles` の中身は見ていない。update はサポートとマネージャに限られ、本人は自分の `roles` を update できない。
- 影響: ログイン済みのユーザーが、読めるコミュニティに自分のメンバー文書を作り、マネージャ権限を自分に付けられる。PF のコミュニティは `enterprise_id == null` なら未認証でもコミュニティ文書を読める。エンタープライズは同じテナントの従業員がコミュニティを読める。マネージャになると、そのコミュニティのイベント更新やメンバー更新に進める。
- 根拠: create 条件は上記の 3 つだけ。`isManager()` は当該メンバー文書の `roles` に `manager` があるかで判定している（同ファイル 262 行付近）。Rules テストは管理者として用意したメンバーを前提にしており、本人作成時に `roles` を拒否するテストは見当たらない。
- 推奨: このリポジトリで、本人作成時は `roles` を空、または `manager` を含めないよう Rules で制約する。拒否する Rules テストを足す。
- この診断では修正していない

### S-2 友人一覧が未ログインの Callable から返る

- 重大度: high
- 実装工数: L。現行仕様は未ログインを含む公開。閉じるなら仕様、`getUserFriends` と `getUserProfilePreview`、プロフィール画面を揃える
- 層: アプリ
- 箇所: `functions/default/src/userFriends.ts:70-107`、`functions/default/src/userProfile.ts:209-236` と `366-447`
- 内容: `getUserFriends` と `getUserProfilePreview` は `invoker: 'public'` で、PF 経路は `request.auth` が無くても対象ユーザーの友人を返す。返る項目はユーザー ID、表示名、画像 URL、一緒に食事した回数と日時。プロフィールプレビューは友人に加え、参加コミュニティと管理コミュニティの名前と説明も返す。注文プレビューだけ本人に限っている。友人サブコレクションの Rules は本人の read だけである（`firestore.rules:398-400`）。
- 影響: Rules で本人に閉じた友人関係と、非公開コミュニティの名前・説明が、ユーザー ID を知っていれば未ログインの呼び出しで見える。`userFriends.ts` には公開範囲のオプトアウトを Phase 2 で見る TODO がある。
- 根拠: `resolveUserFriendsList` の `viewerUid` はリンク可否に使い、一覧そのものは落としていない。`fetchFriendPreviews` は所有者かどうかで分岐しない。
- 推奨: このリポジトリで、未ログインには友人と非公開コミュニティを返さない。仕様が公開でよいなら、Rules の「本人のみ」と Callable の差を仕様書に書く。
- この診断では修正していない

### S-5 LINE の一斉配信用 HTTP にアプリ内の検証が無い

- 重大度: high
- 実装工数: M。週次スケジュールは既にある。外部から叩く HTTP を残すなら共有秘密、やめるなら呼び出し手順の更新
- 層: 設定
- 箇所: `functions/default/src/lineBroadcast.ts:11-26`
- 内容: `broadcast_event_message_request` は `onRequest` で、リクエストの署名や共有秘密を見ていない。コード上の `invoker` は未指定。このリポジトリのデプロイは Firebase CLI 15.15.0 を使う。この CLI は、HTTPS 関数の新規作成時に `endpoint.httpsTrigger.invoker` が空なら `public` を invoker にする（`firebase-tools` v15.15.0 の `fabricator.ts`）。初版の記録は、第 2 世代の既定で IAM 認証が要ると書いていた。その理解は、このデプロイ経路には当てはまらない。
- 影響: 通常のデプロイでは、未認証の HTTP が配信処理を起動できる。本番に今付いている invoker の実値は、この診断では見ていない。
- 根拠: ハンドラは `broadcastEventConcludedMessage()` をそのまま呼ぶ。invoker の既定は上記 CLI の作成処理。
- 推奨: このリポジトリで、スケジュール実行だけに寄せるか、共有秘密を確認する。公開 invoker のまま残さない。
- この診断では修正していない

### S-6 名簿とチラシの PDF がログイン確認だけで返る

- 重大度: high
- 実装工数: M。チラシは請求書 PDF と同じ権限確認を足す。名簿印刷は仕様の案 A が JWT 確認だけなので、仕様の更新を含む
- 層: アプリ
- 箇所: `functions/default/src/namesPrint.ts` の `namesprint`、`functions/default/src/flyer.ts` の `flyer`
- 内容: どちらも `onRequest` で、`Authorization` の JWT を `verifyIdToken` したあとに、パスの `eventId` でイベントを読む。店舗、コミュニティのマネージャ、サポートかは見ていない。`namesprint` は注文から参加者の表示名、画像、メニューを PDF にする。呼び出し元の画面は partner の注文画面。`flyer` はイベントの説明、カバー画像、イベント URL の QR を PDF にする。同じ種類の `eventBillInvoice` は、サポートかコミュニティのマネージャでなければ 403 を返す。
- 影響: ログイン済みで `eventId` を知っていれば、名簿 PDF を受け取れる。チラシは、公開前の説明文も返す。別テナントのイベントも、この確認だけでは止まらない。本番の invoker 実値は見ていない。
- 根拠: 上記二つのハンドラと、`eventBillInvoice` の権限チェックの差。初版の診断範囲に入っていなかった。PR #2439 のレビューで追加した。
- 推奨: このリポジトリで、イベントに対する管理権限を確認してから PDF を返す。対応は [#2440](https://github.com/nijuniinc/bokudeli-event-new/issues/2440)。
- この診断では修正していない

### S-9 メールログインの確認コードに試行制限が無い

- 重大度: high
- 実装工数: M。有効期限、失敗回数、未登録メールの応答、`Math.random()` の置き換え。スキーマと関数テスト
- 層: アプリ
- 箇所: `common/src/schemas/PassCode.ts` の `generatePassCode`、`functions/default/src/user.ts` の `requestEmailLogin` と `confirmEmailLogin`
- 内容: 確認コードは `Math.random()` の 6 桁で、有効期限は 24 時間。`confirmEmailLogin` は不一致でもコードを消さず、試行回数と App Check を見ていない。`requestEmailLogin` は未登録メールに `not-found` を返す。成功時はカスタムトークンを返す。
- 影響: 登録済みメールへのログイン要求のあと、有効期限まで照合を繰り返せる。未登録かどうかも応答で分かる。
- 根拠: 上記の生成、要求、照合。プロフィール系 Callable の App Check 未設定とは別の経路。PR #2439 の再レビューで追加した。
- 推奨: 有効期限と失敗回数を制限し、未登録メールの応答を登録済みと揃える。コード生成に `Math.random()` を使わない。対応は [#2443](https://github.com/nijuniinc/bokudeli-event-new/issues/2443)。
- この診断では修正していない

### S-10 イベント説明の HTML をサニタイズせず表示している

- 実装工数: M。`TinyMCEViewer` の利用はイベント詳細だけ。表示時に許可するタグを決め、通常の本文が残ることを確認する

- 箇所: `base/src/components/TinyMCEViewer.vue`、`base/src/components/EventDetailsCard.vue`

- 推奨: 表示前か保存時に、スクリプト実行につながる HTML を落とす。対応は [#2444](https://github.com/nijuniinc/bokudeli-event-new/issues/2444)。
- この診断では修正していない

## 確認して所見にしなかったもの

- 追跡ファイルに `.env`、`.secret`、`.firebaserc`、`credentials.json` は無い。トークン形式の `git grep -l` も、禁止パスを除外した対象ではファイル名が 0 件だった。
- `.secret` と `.env` は開いていない。値は記録していない。
- `users_personal_information` の read は本人のみ。write は拒否。メールアドレスはこの分離に乗っている。
- Stripe Webhook は `req.rawBody` と `constructEvent` で署名を見ている。失敗は 400。同一 payment intent の stripe 文書がある場合はトランザクションをスキップする。
- Slack の HTTP は `invoker: 'public'` だが、`ExpressReceiver` に `signingSecret` を渡している。
- `recallChatMessage` はログインと送信者本人を見ている。`invoker: 'public'` は Callable をブラウザから呼ぶための指定。
- App Check を付けているのは enterprise の一部 Callable だけ。user のプロフィール系は仕様コメントで未強制。未設定を high にはしていない。
- Storage の `users` / `communities` / `partners` / `assets` の公開 read、エンタープライズロゴの公開 read は、現状の公開ファイルとして info に留めた。チャット添付の read はルームメンバー判定がある。
- `v-html` の大半は `$t` の静的文言。`ManageTopCard` の description も翻訳文を渡している。開催内容の HTML は S-10。
- メニュー、アルバム、店舗、アセットの公開 read は、画面が公開情報を見せるためのルールとして info に留めた。アルバムはコメントで、公開設定にかかわらず閲覧可と書いている。
